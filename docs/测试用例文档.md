# 测试用例文档

项目名称：新就业群体友好驿站服务与诉求响应平台

本文档记录本系统的测试范围、测试环境、功能测试用例、自动化测试清单、缺陷回归记录与测试结论。

> 数据边界说明：本文档中出现的驿站、预约、诉求、活动、评价、资讯与公告记录，均来自本项目数据库或服务端内存中的**演示/模拟数据**；统计指标是后端对系统内已记录数据的实时聚合结果，**不代表真实服务人次或真实业务成效**。驿站名录为 **7 个城市、1344 条公开来源名录**，逐条可溯源，但**不等于完整清单**；**7 个城市的公开来源都没有提供点位坐标**，现有坐标是**高德地图地理编码的派生结果**（1247/1344 条，来源单独记在 `geocode_source` / `geocode_at`），**属于派生数据、不是来源给出，也不能当作精确位置**。驿站的**营业时间以高德地图 POI（第三方数据）为准**（实测高德给出营业时间 **386 条**，其中 **227 条**覆盖了来源原值），高德未提供营业时间的 **760 条**回退来源文本，合并后全库**有营业时间 1146 条**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，实测 **408 条全部来自高德**）。来源单独记在 `business_source` / `business_synced_at`，高德覆盖来源原值时会同时写明来源原文；高德**不提供**「服务设施」这类结构化字段，也**没有**「此刻是否营业」的实时状态字段——界面上的实时状态由前端按营业时间文本推算（仅用于展示），服务项目仍然只能来自公开来源文本。详见 [驿站数据来源.md](驿站数据来源.md) 与 [AUDIT_AND_EVIDENCE.md](../AUDIT_AND_EVIDENCE.md)。

## 一、测试目标与范围

### 1.1 测试目标

1. 验证 7 个业务模块（友好驿站、服务预约、诉求反馈、活动报名、政策资讯与通知公告、服务评价、统计分析与报表）在内存演示配置与 MySQL 配置下的功能正确性。
2. 验证认证与权限体系：JWT 登录、路由守卫、后端 `@RequireRole` 角色校验、未登录 401、越权 403，以及驿站管理员「按负责驿站的数据范围」（预约按 `station.manager_id` 限定的驿站编号集合过滤，诉求按负责驿站所在区域做近似过滤）。
3. 验证业务规则与状态机约束：预约审核流转、诉求处理流转与办结后评价、活动名额与重复报名校验。
4. 验证接口契约与前端接口封装的一致性，验证关键页面在真实浏览器中可打开并渲染。
5. **验证「多城市与定位判断」**：`GET /api/city/list` 返回平台已覆盖的多个城市（首项为平台默认城市杭州）、`GET /api/city/nearest` 按浏览器定位坐标判断最近城市、`GET /api/city/locate` 用高德逆地理编码得到用户**真实所在城市**并判断是否已覆盖（未覆盖时返回真实城市名与最近的已覆盖城市），驿站查询、区域分布与首页地图按 `cityCode` 过滤，且不出现跨城市串数据。
6. **验证「驿站数据来源可追溯」**：1344 条名录取自 7 个城市的公开发布来源，逐条保存来源名称、链接、发布日期与核对日期，`data_status` 区分字段可核对程度；服务项目经规范化后均为短名称，可正常导入并作为预约的最小单位。
7. **验证「坐标回填与派生口径」**：公开来源不含点位坐标，坐标由高德地图地理编码派生并单独记录 `geocode_source`（`AMAP_POI` / `AMAP_GEOCODE`）与 `geocode_at`，不参与 `data_status` 判定；派生坐标经过「区县一致性 + 名称相似度 + 地址相似度」校验与「行政区冲突 / 距城市中心超 120 公里」复核，不合格的坐标宁可丢弃也不画到地图上，并在 `data_note` 中逐条标注。
8. **验证「营业信息同步与预约时段约束」**：驿站营业时间与联系电话由高德地图 POI 同步（结果缓存在入仓的 `data/station-business.json`），并复用与坐标相同的三重校验只接受可信匹配（实测可信匹配 **921 条**）。**营业时间以高德为准、来源兜底**：高德给出营业时间 **386 条**（其中 227 条覆盖了来源原值），未提供的 **760 条**回退来源文本，合并后**有营业时间 1146 条**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，408 条全部来自高德）。系统据此校验预约时段——时段必须落在驿站营业时间内，超出返回 400 与中文提示；**营业时间缺失或无法解析时不拦截**（判断不了就不挡）。高德**不提供**「服务设施」结构化字段，也**没有**「此刻是否营业」的实时状态字段；服务项目仍来自公开来源文本。
9. 记录本轮发现的缺陷及其回归验证方式，作为交付质量证据。
10. **验证「营业状态、未读角标与趋势图空状态」**：营业状态按**当前时间与营业时间文本实时判断**，分「营业中 / 已打烊 / 营业时间待核验」三态并每分钟刷新，**没有营业时间时显示「营业时间待核验」而不是「营业中」**；顶栏未读角标与消息中心**读同一份已读状态**（角标数字等于消息中心未读条数）；服务数据全为 0 时趋势图显示空状态说明而不是退化成 0~0 的空白坐标轴。

### 1.3 不在本次范围内

- 真实生产环境的多实例部署、容器编排与灰度发布。
- 驿站点位的实地核实与运营状态复核（驿站名录虽来自公开来源，但未逐点实地核实）。
- 驿站**精确**位置的实测核实：**7 个城市的公开来源都没有提供点位坐标**，现有坐标是高德地图地理编码的派生结果，名称泛化的驿站与地址只到路口/社区级的记录误差可达数百米，因此**只用于地图展示与就近参考，不能当作精确位置**。需要精确定位时仍应使用高德地图搜索驿站名称或走官方渠道。
- 驿站**实时营业状态的第三方同步**与**服务设施**：高德 POI **不提供这两类结构化字段**（`type` / `tag` 只是「生活服务 / 政府机构」这种粗分类），因此饮水、充电、热饭等服务项目**仍然只能来自公开来源文本**。「此刻是否营业」**没有第三方数据源**：界面上的营业状态由前端按营业时间文本**本地推算**（见 4.12），只用于展示，**不代表第三方实时状态，也不作为预约是否放行的依据**（预约校验以后端为准）。**本轮不做也不声称做到第三方同步**。
- 等保、渗透与安全合规测评。
- 移动端原生 App、微信小程序等非 Web 端。

> `source_published_at`、`verified_at`、`data_status`、`data_note`；核对日期 2026-10-14。
> 以杭州为例：267 条中 4 家「小哥驿站」为 `VERIFIED`（名称、地址、区域、服务设施均可逐条核对），
> 263 座城管驿站为 `PARTIAL`（名称与地址来自来源名录，服务设施是来源对该批驿站的统一描述、未逐站核实）。
> 全平台 `data_status` 为 `VERIFIED` 682 条、`PARTIAL` 662 条；各城市对同类驿站的叫法不同
> （杭州「小哥驿站 / 城管驿站」、北京「工会驿站 / 暖新驿站」、上海「户外职工爱心接力站」、深圳「暖蜂驿站」、
> 成都「职工驿站」、武汉「临空港湾」等），系统按来源原文记录名称与类型，不统一改名。
> **7 个城市的公开来源都没有提供点位坐标：坐标是高德地图地理编码的派生结果（1247/1344 条），单独记在 `geocode_source` / `geocode_at` 两列、不参与 `data_status` 判定，并在每条记录的 `data_note` 中标注「坐标为高德地图地理编码派生，非来源给出」；95 条因复核不合格（行政区冲突 / 距城市中心过远）被丢弃、坐标保持为空，2 条未能定位。派生坐标误差可达数百米，不能当作精确位置。567 条只有名称没有地址的记录未导入系统。**

## 七、测试结论与局限

### 7.1 结论

1. 7 个业务模块的接口与页面功能通过功能用例与自动化测试验证，核心业务闭环（提交→流转→办结→评价、报名→记录、导出→核对）均可复现。
2. 认证与权限体系通过验证：未登录与无效 token 返回 401，角色越权返回 403，前端路由守卫与管理端标签页按角色显隐，后端 `@RequireRole` 为最终拦截点。
3. **驿站名录已接入全国多城市公开来源并可逐条溯源**：**7 个城市、1344 条**名录（杭州 267、北京 550、上海 36、深圳 117、广州 28、成都 172、武汉 174）取自各城市公开发布的权威来源，每条记录保存 `city_code`、来源名称、链接、发布日期与核对日期，`data_status` 区分字段可核对程度（`VERIFIED` 682 条、`PARTIAL` 662 条）；各城市对同类驿站的叫法不同，系统按来源原文记录名称与类型；前台改为服务端分页与筛选并在详情中展示来源，管理端新增类型与来源列。同时如实标注字段级边界（服务设施为批次级描述、公开来源不提供电话（仅高德补空 408 条）、567 条无地址记录未导入、状态需重新核实）。
4. **驿站坐标已通过高德地图地理编码补齐，地图可以标出真实点位**：7 个城市的公开来源都不提供点位坐标，因此坐标统一由高德地图地理编码派生——先用驿站名称做 POI 搜索并做「区县一致性 + 名称相似度 + 地址相似度」三重校验，校验不通过回退详细地址地理编码，再对结果做「行政区冲突」「距城市中心超 120 公里」复核。最终 **1247/1344 条拿到可信坐标（93%）**（POI 匹配 922 条 + 地址地理编码保留 325 条），**95 条因复核不合格被丢弃**（84 条行政区冲突、11 条超距）、2 条未能定位，另有 44 条缺失的所属行政区由地理编码补齐。坐标来源单独记在 `geocode_source` / `geocode_at`，**不参与 `data_status` 判定**，并在每条 `data_note` 中标注「非来源给出」。前端地图改为**高德地图 JS API 2.0**（GCJ-02 坐标，与地理编码结果一致；旧开源瓦片方案在本机会连接超时），随所选城市自动定位，只对带坐标的驿站打点，未配置 Key 时显示降级提示。
5. **多城市与定位能力通过验证**：`city` 表维护 7 个城市及其中心点，`GET /api/city/list` 提供带驿站数量的城市清单（首项为平台默认城市杭州），`GET /api/city/nearest` 按浏览器定位坐标用 Haversine 距离判断最近城市，`GET /api/city/locate` 用高德逆地理编码得到用户**真实所在城市**并判断是否已覆盖（未覆盖时返回真实城市名与最近的已覆盖城市，前端据此给出「您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市」的明确提示）；驿站查询、区域分布与首页地图按 `cityCode` 过滤，跨城市不串数据，未指定城市的新建驿站落到平台默认城市。
6. **按负责驿站的数据范围已实现并验证**：驿站管理员通过 `station.manager_id` 解析出自己负责的驿站，预约管理列表只返回负责驿站的预约，诉求管理列表只返回负责驿站所在区域的诉求；平台管理员与超级管理员不受限制，普通用户仍只能查看本人数据。
7. 状态机约束通过验证：预约仅待确认状态可审核、仅待确认可取消；诉求仅待受理/已分派/处理中可继续处理，已办结或关闭不可重复处理，办结后才可评价；上述流转在并发下由带状态条件的 `UPDATE` 保证只成功一次。
8. 数据口径一致：统计概览、月度趋势、服务排行与 5 类 CSV 导出均来自同一批业务数据，`dataScope` 与 `dataStatus` 明确标注数据来源与计算属性。
9. **营业信息已同步，且预约时段已与驿站营业时间绑定**：驿站的营业时间与联系电话由高德地图 POI 同步（可信匹配 **921/1344 条**）。**营业时间以高德为准**：高德给出 **386 条**（其中 **227 条**覆盖了来源原值，`data_note` 同时保留来源原文与「营业时间以高德地图为准（第三方数据）」），高德未提供的 **760 条**回退来源文本，合并后**有营业时间 1146 条**、仍有 198 条没有；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，**408 条全部来自高德**）。`business_source` 取值四种（`AMAP_POI` / `AMAP_POI+SOURCE` / `SOURCE+AMAP_POI` / `SOURCE`），实测分布为 `AMAP_POI` 386 条、`SOURCE+AMAP_POI` 178 条、`SOURCE` 604 条、`AMAP_POI+SOURCE` 0 条。预约提交时由 `common/BusinessHours.java` 校验时段是否落在营业时间内：**营业时间外的时段一律返回 400 并给出中文提示**（如「大悦城小哥驿站」现取高德值 `10:00-22:00`，预约 `22:00-23:00` 被拒绝）；营业时间缺失或无法解析时**不拦截**，属于有意为之的兜底。
10. **营业状态按当前时间实时判断**（回归 BUG-19）：新增前端 `frontend/src/utils/business-hours.js`，按当前时间与营业时间文本判定「营业中 / 已打烊 / 营业时间待核验」三态并每分钟刷新，驿站列表、驿站详情与地图气泡三处一致；**没有营业时间时显示「营业时间待核验」而不是「营业中」**。该状态是**本地推算的展示值**，不代表第三方实时营业状态，预约放行仍以后端为准。
11. **未读角标与消息列表同源**（回归 BUG-20）：消息派生与已读状态统一收敛到 `frontend/src/stores/message.js`，顶栏角标与消息中心读同一份数据，点「全部标为已读」后角标同步清零。
12. **趋势图有空状态**（回归 BUG-21）：服务数据全为 0 时不再初始化 ECharts，改显示 `.chart-empty` 空状态说明；某月无诉求时办结率断线而不是 `0%`。

| 坐标来源与精度（重要边界） | **7 个城市的公开来源都没有提供点位坐标**，现有坐标是高德地图地理编码的**派生结果**，不是在来源里查到的，也**没有经过实地核实**：`geocode_source` / `geocode_at` 单独记录来源与时间，`data_note` 逐条标注「非来源给出」。**坐标只可用于地图展示与就近参考，不能当作精确位置**——名称泛化的驿站（如只叫「暖新驿站」）与地址只到路口/社区级的记录，误差可达数百米 |
| 坐标覆盖率与丢弃记录 | 全库 **1247/1344 条有坐标（93%）**；**95 条因复核不合格被丢弃**（84 条「地理编码结果的行政区与来源标注不一致」、11 条「距城市中心超过 120 公里」），**2 条未能定位**，这些记录坐标保持为空而不是用推测值填充；另有 44 条缺失的所属行政区由地理编码补齐，同样属于派生数据。区县补齐本身也可能偏差（例如来源只给到「杭州市」的「杭州城管驿站风景区孤山驿站」，地理编码补齐的所属行政区是临安区，而孤山实际位于西湖区），说明派生数据的边界需要保留人工复核 |
| 坐标重合 | 去重后 **1170 个不同坐标点**，其中 **51 个坐标点被多条驿站共用（共涉及 128 条记录）**：这些驿站通常本就在同一栋楼或同一个院落（真实情况），也可能是泛化名称匹配到了同一个高德 POI，需要就具体点位单独核实，不能据此认为它们是同一个服务点 |
| 营业信息来源与优先级（重要边界） | **营业时间以高德地图 POI 为准**，高德未提供营业时间的驿站**回退来源文本**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话）。两项都是**第三方数据**（商户认领与用户上报），**不是驿站官方提供的**。实测：高德提供营业时间 **386 条**（其中 **227 条**覆盖了来源原值），未提供的 **760 条**回退来源，合并后全库**有营业时间 1146 条**、**198 条没有**；**有联系电话 408 条，全部来自高德**。同步只接受「区县一致性 + 名称相似度 + 地址相似度」三重校验通过的可信匹配（实测可信 **921 条**），营业时间还要求形如 `HH:mm-HH:mm` 或「24小时」。实例：「大悦城小哥驿站」来源写「每日 8:30-22:00」，高德给的是商场时间 `10:00-22:00`，系统**以高德为准**（`business_source=AMAP_POI`、`openTime=10:00-22:00`），并在 `data_note` 中写「营业时间以高德地图为准（第三方数据）」+「来源原文的开放时间为「每日 8:30-22:00」」留痕 |
| 营业时间可能失真（第三方数据 + 可能过期） | 高德的营业时间与电话是商户认领与用户上报的结果，**可能过期或与实际不符**，**使用前宜再核实**；因此按营业时间文本推算出的营业状态（营业中 / 已打烊）只是**界面提示**，不能证明「驿站此刻确实开门」，也不作为预约放行的唯一依据——预约校验是「营业时间外拒绝、缺失或无法解析放行」的宽松口径。高德 POI **不提供**「服务设施」结构化字段（`type` / `tag` 只是「生活服务 / 政府机构」这类粗分类），因此饮水 / 充电 / 热饭等服务项目**仍然只能来自公开来源文本**（6413 条服务项目全部来自公开来源）；高德也**没有**「此刻是否营业」的实时状态字段，**不是第三方实时状态** |
| 前端营业状态的判断依据与边界 | 列表、详情与地图气泡上的「营业中 / 已打烊 / 营业时间待核验」由前端 `utils/business-hours.js` 按**当前时间 + 营业时间文本**本地推算（每分钟自动刷新），依据就是高德或来源给出的**营业时间文本**，因此**可能与驿站实际情况不符**（营业时间本身是第三方数据、可能过期；临时闭馆与节假日调整也无法反映）。**没有营业时间或文本无法解析时显示「营业时间待核验」**，不猜成「营业中」。该状态**只用于展示**，预约是否放行**以后端 `common/BusinessHours.java` 为准**（前端不参与校验） |
| 「只显示已启用」筛选口径 | 驿站查询的复选框已由「只看营业中」更名为「**只显示已启用**」并加 tooltip：它实际按**服务端的 `status` 字段**过滤（附加 `status=OPEN`；全库 1344 条名录的 `status` 均为 `OPEN`，反映的是各来源发布时的状态），**不是按当前时刻是否营业过滤**。「此刻是否营业」由每行右侧的实时状态标签表达，两者含义不同，因此筛选后列表中出现「已打烊」的行是正确的 |
| 营业时间缺失时不做拦截（有意为之） | `common/BusinessHours.java` 在营业时间缺失、营业时间文本无法解析、或预约时段文本本身无法解析时，一律返回「放行」，即 **判断不了就不挡**（`MysqlWorkflowService` 与 `DemoWorkflowStore` 两套实现行为一致）。这是为避免因数据缺失误拒正常预约而做的取舍。**代价是约束范围有限**：全库 1344 条中，**960 条（71%）的开放时间能解析出营业区间、真正参与时段校验**，其余 **384 条（29%）实际上不受时段约束** —— 其中 **198 条没有开放时间**、**12 条开放时间是「预计10月底正式对外开放」这类无法解析的文本**（含 `周一至周日7:00--24:00`、`08:30——17:30` 这类双连接符写法）、**174 条为「24小时营业 / 全天」**（全天开放，任意合法时段都放行）。因此**不能宣称「所有预约都被营业时间覆盖」** |
| 地图依赖 | 地图依赖**高德地图 JS API 2.0 与 Key**（前端 Web 端 Key + 安全密钥放在 `frontend/.env.local`，后端 Web 服务 Key 由环境变量 `AMAP_WEB_KEY` 注入）：未配置 Key、脚本加载失败或离线时地图只显示降级提示（不白屏），此时点位不可见；底图与坐标依赖高德服务，不能离线使用 |
| 数据来源形态 | 深圳 105 条、武汉 132 条来自官方发布的**图片表格**（名单本身以图片形式发布），由逐行读取还原为文本，可信度略低于直接可复制的文本来源；其余城市来源为网页文本或结构化表格 |
| 城市口径 | **统计指标仍是全平台口径，只有驿站查询与地图按城市过滤**（首页已标注「驿站点位（全平台）」与「为全平台汇总」）；用户定位由 `GET /api/city/locate` 用高德逆地理编码判断真实城市，**未覆盖时会明确提示**（例如苏州 → 「您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市」），但前端展示的仍是最近的已覆盖城市，用户所在城市的本地数据并不存在；管理端驿站管理未提供城市筛选列，新增驿站默认落在平台默认城市杭州；`city` 表未参与资讯、公告、活动等其他业务数据的归属 |
| 统计结论 | 统计指标是对系统内已记录数据的实时聚合，不能据此推导真实业务成效、增长率或满意度结论 |
| 数据规模 | 驿站名录为 1344 条公开来源数据，但预约、诉求、报名、评价等业务数据量仍远小于真实业务规模，索引与查询计划未在真实业务量下验证 |
| 前端兼容性 | 浏览器走查在本机 Chrome 上完成，未覆盖 Firefox、Safari、移动端浏览器与不同分辨率下的完整回归；地图为高德地图 JS API 2.0，需可访问高德 CDN 并配置有效 Key，未配置时只显示降级提示 |
| 未实现能力 | `/api/station/nearby` 与分页查询同源，**不是真实距离排序**（未使用坐标做距离排序）；用户端的服务预约、服务评价、我的收藏三处驿站下拉**只取前 50 条**，未接入分页或远程搜索；消息中心为本人预约、诉求、报名的客户端汇总，已读状态保存在浏览器本地；收藏功能保存在浏览器本地，未持久化到数据库；无短信、邮件、站内推送等消息通道 |
| 数据范围覆盖度 | 已实现按负责驿站的数据范围，但目前只作用于 `GET /api/appointment/admin/page` 与 `GET /api/appeal/admin/page` 两个列表接口；报表导出（`/api/stat/export/{type}`）、报名记录（`/api/activity/admin/signups`）、驿站后台分页（`/api/station/admin/page`）与评价分页等接口仍返回平台全域数据，只做角色校验、未做驿站范围过滤 |
| 诉求范围精度 | `appeal` 表没有 `station_id` 字段，诉求只能按负责驿站的 `area`（区域）做近似范围限定：同一区域内非本人负责驿站的诉求仍会出现在列表中，属于已知精度损失 |
| 持久化验证 | MySQL profile 已接入预约、诉求、活动报名、评价、资讯、公告与统计 Mapper，并使用本机 MySQL 8.0 完成初始化与核心接口回归；生产环境的凭据管理、备份与迁移策略仍需单独配置 |
