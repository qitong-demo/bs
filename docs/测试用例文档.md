# 测试用例文档

项目名称：新就业群体友好驿站服务与诉求响应平台

本文档记录本系统的测试范围、测试环境、功能测试用例、自动化测试清单、缺陷回归记录与测试结论。

> 数据边界说明：本文档中出现的驿站、预约、诉求、活动、评价、资讯与公告记录，均来自本项目数据库或服务端内存中的**演示/模拟数据**；统计指标是后端对系统内已记录数据的实时聚合结果，**不代表真实服务人次或真实业务成效**。驿站名录为 **7 个城市、1344 条公开来源名录**，逐条可溯源，但**不等于完整清单**；**7 个城市的公开来源都没有提供点位坐标**，现有坐标是**高德地图地理编码的派生结果**（1247/1344 条，来源单独记在 `geocode_source` / `geocode_at`），**属于派生数据、不是来源给出，也不能当作精确位置**。驿站的**营业时间以高德地图 POI（第三方数据）为准**（实测高德给出营业时间 **386 条**，其中 **227 条**覆盖了来源原值），高德未提供营业时间的 **760 条**回退来源文本，合并后全库**有营业时间 1146 条**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，实测 **408 条全部来自高德**）。来源单独记在 `business_source` / `business_synced_at`，高德覆盖来源原值时会同时写明来源原文；高德**不提供**「服务设施」这类结构化字段，也**没有**「此刻是否营业」的实时状态字段——界面上的实时状态由前端按营业时间文本推算（仅用于展示），服务项目仍然只能来自公开来源文本。**政策与资讯已接入真实公开来源**：`data/policy-sources.json` 为**人工逐条打开页面核实**的清单，经 `scripts/generate-news-seed.mjs` 生成 `backend/src/main/resources/db/news.sql` 与 [政策资讯来源.md](政策资讯来源.md)，**实测导入 94 条**（官方 90 + 平台发布 4），其中**不限城市 60 条、城市相关 34 条**（杭州 8、上海 6、深圳 6、北京 4、广州 4、成都 3、武汉 3）。另有 **10 条被排除**：**6 条未能打开页面核实**（超时 / 412 反爬 / 重定向次数过多）、**4 条城市不在平台覆盖范围**（南京 3、珠海 1，导入后不会在任何城市显示），逐条原因见该文档第三节。**这些条目来自公开发布的政策文件与平台公告，系统只做摘录与归类，不代表已获得发布方授权，也不代表对政策内容的解释，具体执行以原文为准。** 详见 [驿站数据来源.md](驿站数据来源.md) 与 [AUDIT_AND_EVIDENCE.md](../AUDIT_AND_EVIDENCE.md)。

## 一、测试目标与范围

### 1.1 测试目标

1. 验证 7 个业务模块（友好驿站、服务预约、诉求反馈、活动报名、政策资讯与通知公告、服务评价、统计分析与报表）在内存演示配置与 MySQL 配置下的功能正确性。
2. 验证认证与权限体系：JWT 登录、路由守卫、后端 `@RequireRole` 角色校验、未登录 401、越权 403，以及驿站管理员「按负责驿站的数据范围」（预约按 `station.manager_id` 限定的驿站编号集合过滤，诉求按负责驿站所在区域做近似过滤）。
3. 验证业务规则与状态机约束：预约审核流转、诉求处理流转与办结后评价、活动名额与重复报名校验。
4. 验证接口契约与前端接口封装的一致性，验证关键页面在真实浏览器中可打开并渲染。
5. **验证「多城市与定位判断」**：`GET /api/city/list` 返回平台已覆盖的多个城市（首项为平台默认城市杭州）、`GET /api/city/nearest` 按浏览器定位坐标判断最近城市、`GET /api/city/locate` 用高德逆地理编码得到用户**真实所在城市**并判断是否已覆盖（未覆盖时返回真实城市名与最近的已覆盖城市），驿站查询、区域分布与首页地图按 `cityCode` 过滤，且不出现跨城市串数据。
6. **验证「驿站数据来源可追溯」**：1344 条名录取自 7 个城市的公开发布来源，逐条保存来源名称、链接、发布日期与核对日期，`data_status` 区分字段可核对程度；服务项目经规范化后均为短名称，可正常导入并作为预约的最小单位。
7. **验证「坐标回填与派生口径」**：公开来源不含点位坐标，坐标由高德地图地理编码派生并单独记录 `geocode_source`（`AMAP_POI` / `AMAP_GEOCODE`）与 `geocode_at`，不参与 `data_status` 判定；派生坐标经过「区县一致性 + 名称相似度 + 地址相似度」校验与「行政区冲突 / 距城市中心超 120 公里」复核，不合格的坐标宁可丢弃也不画到地图上，并在 `data_note` 中逐条标注。
8. **验证「营业信息同步与预约时段约束」**：驿站营业时间与联系电话由高德地图 POI 同步（结果缓存在入仓的 `data/station-business.json`），并复用与坐标相同的三重校验只接受可信匹配（实测可信匹配 **921 条**）。**营业时间以高德为准、来源兜底**：高德给出营业时间 **386 条**（其中 227 条覆盖了来源原值），未提供的 **760 条**回退来源文本，合并后**有营业时间 1146 条**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，408 条全部来自高德）。系统据此校验预约时段——时段必须落在驿站营业时间内，超出返回 400 与中文提示；**营业时间缺失或无法解析时不拦截**（判断不了就不挡）。高德**不提供**「服务设施」结构化字段，也**没有**「此刻是否营业」的实时状态字段；服务项目仍来自公开来源文本。
9. 记录本轮发现的缺陷及其回归验证方式，作为交付质量证据。
10. **验证「营业状态、未读角标与趋势图空状态」**：营业状态按**当前时间与营业时间文本实时判断**，分「营业中 / 已打烊 / 营业时间待核验」三态并每分钟刷新，**没有营业时间时显示「营业时间待核验」而不是「营业中」**；顶栏未读角标与消息中心**读同一份已读状态**（角标数字等于消息中心未读条数）；服务数据全为 0 时趋势图显示空状态说明而不是退化成 0~0 的空白坐标轴。
11. **验证「政策资讯的真实来源与分城市展示」**：`GET /api/news/page` 新增 `cityCode` 与 `sourceType` 参数；`city_code IS NULL` 表示**不限城市、在所有城市都可见**，非空时**只在该城市可见且排在最前面**，其他城市的内容不出现；导入的 94 条逐条带可打开的原文链接，系统只做摘录与归类，**不声称已获发布方授权**（详见 4.6 与 4.13）。
12. **验证「诉求与反馈的两种受理方、随分类变化的状态文案与回复即结果」**：受理方由用户提交时在 `STATION`（驿站管理员）/ `PLATFORM`（平台管理员）之间**显式选择**，未传时按分类与子类型推断（表扬感谢默认驿站；子类型含「驿站」「设施」的给驿站）；用户端状态文案**随分类变化**（同一状态机，反映问题 / 表扬感谢 / 提出建议各一套措辞），管理端通过新增字段 `statusLabelStandard` 保留「待受理 / 已分派 / 处理中 / 已办结」标准术语，**开题报告与中期报告要求的闭环术语在管理端完整可见**；管理端「给用户的回复（必填）」提交后，用户端以**独立突出的回复区块**展示回复人、原文与时间，未回复时显示「XX 尚未回复」加当前状态（详见 4.5）。
13. **验证「预约语义重构」**：服务预约定位为「**有事提前联系驿站确认是否可行**」，预约事项由用户**自行填写**（`serviceName`，≤100 字，必填），联系电话 `contactPhone` 可选但格式受校验；预约时段**必须落在驿站营业时间内**，超出返回 400；前端**时段选项按营业时间自动生成**（不再写死 09:00 / 14:00 / 18:00）；服务排行改为**按驿站**统计（详见 4.4）。
14. **验证「首页布局与手机端适配」**：首页主区为「地图占最大空间（1.85:1，高度 `clamp(420px, 56vh, 620px)`）+ 右侧驿站列表」，列表按定位**距离排序**并显示实时营业状态与营业时间，提供「地图定位」「提前联系」两个动作；预约 / 诉求 / 资讯等次要信息压到一行，趋势图**默认收起**；手机端按 **1180 / 900 / 640 三档断点**适配，侧栏在窄屏变为浮层抽屉且默认收起（详见 4.13）。

### 1.3 不在本次范围内

- 真实生产环境的多实例部署、容器编排与灰度发布。
- 驿站点位的实地核实与运营状态复核（驿站名录虽来自公开来源，但未逐点实地核实）。
- 驿站**精确**位置的实测核实：**7 个城市的公开来源都没有提供点位坐标**，现有坐标是高德地图地理编码的派生结果，名称泛化的驿站与地址只到路口/社区级的记录误差可达数百米，因此**只用于地图展示与就近参考，不能当作精确位置**。需要精确定位时仍应使用高德地图搜索驿站名称或走官方渠道。
- 驿站**实时营业状态的第三方同步**与**服务设施**：高德 POI **不提供这两类结构化字段**（`type` / `tag` 只是「生活服务 / 政府机构」这种粗分类），因此饮水、充电、热饭等服务项目**仍然只能来自公开来源文本**。「此刻是否营业」**没有第三方数据源**：界面上的营业状态由前端按营业时间文本**本地推算**（见 4.12），只用于展示，**不代表第三方实时状态，也不作为预约是否放行的依据**（预约校验以后端为准）。**本轮不做也不声称做到第三方同步**。
- 等保、渗透与安全合规测评。
- 移动端原生 App、微信小程序等非 Web 端（**响应式适配只覆盖 Web 页面在手机浏览器下的布局**，不包含原生能力）。
- 政策与资讯的**发布方授权**与政策解读：系统只对公开来源做摘录与归类并给出来源链接，**不声称已获授权、也不对政策内容作解释**；具体执行以原文为准。

### 4.4 服务预约（APPT）

> 语义说明（本轮重构）：服务预约**不是**「预约使用饮水 / 空调」这类设施，而是「**有事提前联系驿站确认是否可行**」。
> 因此 `serviceName`（想提前沟通什么）由**用户自行填写**，`≤100` 字且必填，**不再从固定服务项目里选**；
> 新增可选字段 `contactPhone`（联系电话，格式校验：数字、`+`、`-`、`()` 与空格组成，长度 5～30）。
> 预约时段**必须落在驿站营业时间内**，超出返回 400；前端时段选项**按驿站营业时间自动生成**
> （`frontend/src/utils/business-hours.js` 的 `buildSlots`，默认步长 120 分钟、最多 4 个），不再是写死的 09:00 / 14:00 / 18:00。
> `service_appointment` 表的 `service_id` 改为**可空**（仅为兼容历史数据保留），并新增 `service_name`（`VARCHAR(100) NOT NULL`）
> 与 `contact_phone`（`VARCHAR(30)`）两列。由于事项已是自由文本，**服务排行改为按驿站统计**（见 TC-APPT-17）。

## 七、测试结论与局限

### 7.1 结论

1. 7 个业务模块的接口与页面功能通过功能用例与自动化测试验证，核心业务闭环（提交→流转→办结→评价、报名→记录、导出→核对）均可复现。
2. 认证与权限体系通过验证：未登录与无效 token 返回 401，角色越权返回 403，前端路由守卫与管理端标签页按角色显隐，后端 `@RequireRole` 为最终拦截点。
3. **驿站名录已接入全国多城市公开来源并可逐条溯源**：**7 个城市、1344 条**名录（杭州 267、北京 550、上海 36、深圳 117、广州 28、成都 172、武汉 174）取自各城市公开发布的权威来源，每条记录保存 `city_code`、来源名称、链接、发布日期与核对日期，`data_status` 区分字段可核对程度（`VERIFIED` 682 条、`PARTIAL` 662 条）；各城市对同类驿站的叫法不同，系统按来源原文记录名称与类型；前台改为服务端分页与筛选并在详情中展示来源，管理端新增类型与来源列。同时如实标注字段级边界（服务设施为批次级描述、公开来源不提供电话（仅高德补空 408 条）、567 条无地址记录未导入、状态需重新核实）。
4. **驿站坐标已通过高德地图地理编码补齐，地图可以标出真实点位**：7 个城市的公开来源都不提供点位坐标，因此坐标统一由高德地图地理编码派生——先用驿站名称做 POI 搜索并做「区县一致性 + 名称相似度 + 地址相似度」三重校验，校验不通过回退详细地址地理编码，再对结果做「行政区冲突」「距城市中心超 120 公里」复核。最终 **1247/1344 条拿到可信坐标（93%）**（POI 匹配 922 条 + 地址地理编码保留 325 条），**95 条因复核不合格被丢弃**（84 条行政区冲突、11 条超距）、2 条未能定位，另有 44 条缺失的所属行政区由地理编码补齐。坐标来源单独记在 `geocode_source` / `geocode_at`，**不参与 `data_status` 判定**，并在每条 `data_note` 中标注「非来源给出」。前端地图改为**高德地图 JS API 2.0**（GCJ-02 坐标，与地理编码结果一致；旧开源瓦片方案在本机会连接超时），随所选城市自动定位，只对带坐标的驿站打点，未配置 Key 时显示降级提示。
5. **多城市与定位能力通过验证**：`city` 表维护 7 个城市及其中心点，`GET /api/city/list` 提供带驿站数量的城市清单（首项为平台默认城市杭州），`GET /api/city/nearest` 按浏览器定位坐标用 Haversine 距离判断最近城市，`GET /api/city/locate` 用高德逆地理编码得到用户**真实所在城市**并判断是否已覆盖（未覆盖时返回真实城市名与最近的已覆盖城市，前端据此给出「您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市」的明确提示）；驿站查询、区域分布与首页地图按 `cityCode` 过滤，跨城市不串数据，未指定城市的新建驿站落到平台默认城市。

| 营业时间可能失真（第三方数据 + 可能过期） | 高德的营业时间与电话是商户认领与用户上报的结果，**可能过期或与实际不符**，**使用前宜再核实**；因此按营业时间文本推算出的营业状态（营业中 / 已打烊）只是**界面提示**，不能证明「驿站此刻确实开门」，也不作为预约放行的唯一依据——预约校验是「营业时间外拒绝、缺失或无法解析放行」的宽松口径。高德 POI **不提供**「服务设施」结构化字段（`type` / `tag` 只是「生活服务 / 政府机构」这类粗分类），因此饮水 / 充电 / 热饭等服务项目**仍然只能来自公开来源文本**（6413 条服务项目全部来自公开来源）；高德也**没有**「此刻是否营业」的实时状态字段，**不是第三方实时状态** |
| 前端营业状态的判断依据与边界 | 列表、详情与地图气泡上的「营业中 / 已打烊 / 营业时间待核验」由前端 `utils/business-hours.js` 按**当前时间 + 营业时间文本**本地推算（每分钟自动刷新），依据就是高德或来源给出的**营业时间文本**，因此**可能与驿站实际情况不符**（营业时间本身是第三方数据、可能过期；临时闭馆与节假日调整也无法反映）。**没有营业时间或文本无法解析时显示「营业时间待核验」**，不猜成「营业中」。该状态**只用于展示**，预约是否放行**以后端 `common/BusinessHours.java` 为准**（前端不参与校验） |
