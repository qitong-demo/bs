## 一、角色模型重构（本次最大的改动）

### 1.1 澄清后的模型

需求方原文：

> "管理员的概念就是管理员唯一统筹管理用户端和驿站端，但是可以在管理端新建子账号，分发不同的管理功能，选择管理员端登录使用唯一管理员给予的账号可以进行登录"

即：**只有一个"管理员"身份，通过子账号 + 功能授权来分工**，而不是层层分级。

### 1.2 现状与问题

| 现状 | 问题 |
| --- | --- |
| `RoleCatalog` 定义了 4 个角色：`USER` / `STATION_ADMIN` / `PLATFORM_ADMIN` / `SUPER_ADMIN` | 与"三个身份"不符 |
| `SUPER_ADMIN` **没有种子化、没有演示账号**，但被 **27 个文件**的 `@RequireRole` 引用 | 幽灵角色，从未真正启用，却让权限矩阵看起来有四级 |
| 没有"子账号 + 功能授权"机制 | 无法实现"分发不同的管理功能" |

### 1.3 新角色模型

**系统只有三个身份：**

| 身份 | `role_code` | 说明 |
| --- | --- | --- |
| 普通用户 | `USER` | 使用驿站服务、提交诉求、报名活动 |
| 驿站管理员 | `STATION_ADMIN` | 运营本驿站（预约审核、诉求处理、活动与报名管理） |
| **管理员** | `ADMIN` | **统一统筹平台**，可创建子账号并分发功能权限 |

`PLATFORM_ADMIN` 与 `SUPER_ADMIN` 合并为 `ADMIN`。

**子账号 = 由管理员创建、被授予部分功能的账号**，角色同样是 `ADMIN`，但功能权限是子集。子账号用管理员给的账号登录管理端，只看到被授权的标签页。

你上一轮提到的"添加员"，在这个模型里就是**一个只被授予「驿站管理 + 资讯公告管理」的子账号**——不需要单独的角色。

### 1.4 功能权限目录

每个权限对应管理端的一个标签页或关键操作：

| 权限编码 | 名称 | 覆盖的功能 |
| --- | --- | --- |
| `STATION_MANAGE` | 驿站管理 | 新增 / 修改 / 删除驿站 |
| `SERVICE_MANAGE` | 服务项目管理 | 服务项目增删改 |
| `NEWS_MANAGE` | 资讯公告管理 | 政策与公告的增删改、**声明与建议创作**、状态变更 |
| `ACTIVITY_MANAGE` | 活动管理 | 活动增删改、取消活动 |
| `SIGNUP_MANAGE` | 报名记录 | 查看报名、联系与审核、给出反馈 |
| `APPOINTMENT_AUDIT` | 预约审核 | 确认 / 拒绝预约、标记爽约 |
| `APPEAL_HANDLE` | 诉求处理 | 分派、回复、办结 |
| `CHANGE_APPROVE` | 变更审批 | 审批驿站提交的信息/位置变更申请 |
| `ACCOUNT_MANAGE` | 账号管理 | 新建子账号、改账号 ID、重置密码、分发权限 |
| `DATA_REVIEW` | 数据复核 | 处理"来源待核对""坐标为高德派生"的驿站 |
| `REPORT_EXPORT` | 报表导出 | 导出各类台账 |

**约束**：`ACCOUNT_MANAGE` 属于**管理员本人专属**，不可授予子账号——否则子账号可以自我提权，等于没有权限体系。

### 1.5 数据库改动

| 表 | 改动 |
| --- | --- |
| `sys_role` | 由 4 行改为 **3 行**，删除 `SUPER_ADMIN`，`PLATFORM_ADMIN` 改名为 `ADMIN` |
| `sys_permission` | **新增**：权限目录（`permission_code` / `permission_name` / `remark`） |
| `sys_user_permission` | **新增**：`user_id` / `permission_code`，多对多 |

### 1.6 鉴权改动

- 现有 `@RequireRole({"PLATFORM_ADMIN", "SUPER_ADMIN", ...})` 共 27 处 → `@RequireRole({"ADMIN"})`
- 新增 `@RequirePermission({"STATION_MANAGE"})`，在原有角色校验之上再检查功能权限
- 前端管理端标签页可见性由"角色"改为**由后端返回的权限列表**驱动，不再前端硬编码 `platformOnly`

## 二、邮箱验证码（替代短信）

### 2.1 为什么不能做短信

阿里云明确公告：[【2025年6月6日】关于短信服务不支持申请个人自用资质的公告](https://help.aliyun.com/zh/sms/product-overview/announcement-on-sms-not-supporting-application-for-personal-use-qualification)。短信**签名需实名制报备**且要求企业资质（[2025年4月8日公告](https://help.aliyun.com/zh/sms/product-overview/notice-on-compliance-verification-of-sms-signature)）。

**个人开发者拿不到真实短信通道。** 因此改用邮箱验证码——个人可用 QQ / 163 邮箱的 SMTP 授权码真实发信。

### 2.2 设计

| 项目 | 设计 |
| --- | --- |
| 新增字段 | `sys_user.email VARCHAR(120)` |
| 新增表 | `verification_code`（`purpose` / `target` / `code_hash` / `expire_at` / `used` / `attempt_count` / `create_time`） |
| 发信 | Spring Boot Mail（`spring-boot-starter-mail`）+ SMTP 配置放环境变量，**不入库** |
| 有效期 | 5 分钟；同一邮箱 60 秒内不可重复发送；最多 5 次校验机会，超出作废 |
| 存储 | 只存**哈希**，不存明文验证码 |

### 2.3 使用场景

| 场景 | 是否需要邮箱验证码 |
| --- | --- |
| 本人修改账号 ID | ✅ 需要 |
| 本人修改密码 | ✅ 需要 |
| 管理员改他人账号 ID | ✅ 需要（发给**被改账号**的邮箱，同时要求管理员输入自己的密码） |
| 管理员重置他人密码 | ✅ 同上 |
| 首次绑定邮箱 | 需当前密码验证（此时还没有邮箱可发） |

### 2.4 演示环境的诚实处理（重要）

若未配置 SMTP，**不能假装发了邮件**。设计三级降级：

| 情形 | 行为 |
| --- | --- |
| 已配置 SMTP | 真实发信 |
| 未配置 SMTP，且为演示模式 | 生成验证码并**写入后端日志**，界面明确提示「**演示环境未真实发送邮件，验证码见后端控制台**」 |
| 未配置 SMTP，且用户未绑定邮箱 | 拒绝该操作并提示先绑定邮箱 |

这条必须写进文档与界面——本项目一贯不允许把不可用的能力说成可用。

## 三、政策的「声明与建议」创作

### 3.1 澄清

需求方原文：

> "政策备注的意思是管理员在发布政策的时候，可以进行声明和建议等内容创作，不要局限在备注两个字"

所以这**不是内部便签**，而是**管理员对政策的内容创作，用户可见**。

### 3.2 设计

| 字段 | 含义 | 界面位置 |
| --- | --- | --- |
| `statement` 平台声明 | 平台对该政策的立场、适用范围提醒 | 政策详情页「平台声明」区块 |
| `advice` 行动建议 | 给新就业群体的具体可执行建议 | 政策详情页「行动建议」区块 |
| `editor_name` 整理人署名 | 让用户知道是谁整理的 | 详情页落款 |

**示例**（以已收录的杭州政策为例）：

> **平台声明**：本条为杭州市级政策，仅适用于杭州市。政策实施日期以原文为准，平台不对执行结果负责。
>
> **行动建议**：符合条件的骑手可通过「浙里办」在线申请，建议提前准备劳动合同、考勤记录与银行流水；如遇驿站或平台推诿，可在本站「诉求与反馈」中提交，由平台协助转达。

### 3.3 状态扩展

当前 `news.status` 只有 `PUBLISHED`（已发布）与 `DRAFT`（草稿）。政策会失效，建议补充：

| 状态 | 含义 | 用户端表现 |
| --- | --- | --- |
| `PUBLISHED` | 已发布 | 正常展示 |
| `DRAFT` | 草稿 | 不展示 |
| **`EXPIRED` 已失效**（新增） | 政策已过期或被新政策取代 | 展示但打「已失效」标签，并提示查看最新政策 |

## 四、驿站端功能补全

### 4.1 与用户端的功能对应关系

| 用户端功能 | 驿站端现状 | 需补 |
| --- | --- | --- |
| 驿站查询 | ❌ 驿站管理员**看不到自己的驿站信息** | **我的驿站**：查看并维护本驿站（营业时间、联系电话、地址、简介） |
| 服务预约 | ✅ 预约审核 | 补：**爽约标记**、**暂停服务**（并通知已预约用户） |
| 诉求与反馈 | ✅ 诉求处理 | 补：**超时提醒**（超 N 小时未回复高亮） |
| 活动报名 | ✅ 活动管理 + 报名记录 | 补：**取消活动并通知已报名者**、**候补名单** |
| 服务评价 | ❌ 看不到本站评价 | **本驿站评价查看与回复** |
| 消息中心 | ❌ 不能主动发 | **向本站用户发通知** |
| 政策资讯 | — 只读即可 | — |
| 个人中心 | 仅改资料 | **账号安全**（改账号/密码，邮箱验证码） |

### 4.2 实际使用中会出现的问题与对策

这一节是针对"实际使用中可能会产生的问题"的填补：

| # | 实际问题 | 对策 |
| --- | --- | --- |
| 1 | 用户预约了但不来，占着时段 | 驿站可标记**爽约**；同一用户累计爽约 3 次后提交预约需管理员确认 |
| 2 | 驿站临时关门 / 装修，已有人预约 | 驿站可设**暂停服务**状态（起止时间），系统自动通知该时段已预约用户 |
| 3 | 活动因故取消 | 驿站/管理员可**取消活动**，自动通知全部已报名者并说明原因 |
| 4 | 名额满了但有人退出 | **候补名单**：名额满后可登记候补，有人取消时按顺序通知 |
| 5 | 报名了但联系不上人 | 已有「联系与审核」流程，可标记未通过并说明 |
| 6 | 驿站营业时间临时变更 | 走**变更申请**（第五章），或允许驿站直接改并留痕 |
| 7 | 同一个诉求被重复提交 | 管理端可**标记为重复**并关联到主诉求 |
| 8 | 政策失效但仍被当作依据 | `EXPIRED` 状态 + 用户端「已失效」标签 |
| 9 | 驿站地址搬迁 | 走**位置变更申请** |
| 10 | 数据来源过期（驿站点位已变） | 管理员端**数据复核工作台**集中处理 |

## 五、驿站信息变更申请（审批流）

驿站最清楚自己门口在哪，但坐标是权威数据，不能自改。因此走审批。

### 5.1 新表 `station_change_request`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `station_id` | 申请变更的驿站 |
| `applicant_id` | 提交人（驿站管理员） |
| `change_type` | `LOCATION` 位置 / `BUSINESS_HOURS` 营业时间 / `PHONE` 联系电话 / `ADDRESS` 地址 / `OTHER` 其他 |
| `old_value` | 变更前（留痕） |
| `new_value` | 变更后 |
| `reason` | 申请理由（必填） |
| `status` | `PENDING` / `APPROVED` / `REJECTED` |
| `reviewer_id` / `review_note` / `review_time` | 审批留痕 |
| `create_time` | 提交时间 |

### 5.2 流程

```
驿站管理员提交申请（新值 + 理由）
        ↓
管理员在「变更审批」中查看，可对比新旧值
        ↓
通过 → 写入 station 对应字段，geocode_source = 'MANUAL_APPROVED'，data_note 追加说明
驳回 → 记录驳回原因，驿站可见
```

**为什么通过后要改 `geocode_source`**：现有 1247/1344 条坐标是高德 POI 派生并经过三重置信度校验的。手工变更不留痕会让来源标注失真——而"数据来源可核对"是本项目一直坚持的口径。

### 5.3 权限

| 操作 | 谁能做 |
| --- | --- |
| 提交申请 | 驿站管理员（只能给自己负责的驿站） |
| 审批 | 拥有 `CHANGE_APPROVE` 权限的账号 |

## 八、改动规模与风险

| 项 | 规模 | 主要风险 |
| --- | --- | --- |
| 角色模型重构（3 角色 + 权限体系） | **大** | 27 处 `@RequireRole`、前端标签可见性、种子数据、测试断言全需同步 |
| 邮箱验证码 | 中 | SMTP 配置与**演示降级的诚实处理**；验证码表与频率限制 |
| 政策声明与建议 | 小~中 | 表结构 + 详情页展示 |
| 驿站端功能补全 | **大** | 我的驿站、评价查看与回复、发通知、爽约、暂停服务、活动取消、候补 |
| 变更申请审批 | 中 | 新表 + 审批界面 + 权限 |
| 数据复核工作台 | 小~中 | 主要是查询与批量操作界面 |

**建议分两批做**：
- **第一批**（结构性与高价值）：角色模型重构 → 邮箱验证码 → 账号安全 → 政策声明与建议
- **第二批**（驿站端补全）：我的驿站 → 变更申请审批 → 评价回复 → 发通知 → 爽约与暂停服务 → 活动取消与候补

## 九、已确认的设计决策（需求方 2026-10-14 确认）

| # | 问题 | 确认结果 |
| --- | --- | --- |
| 1 | 角色命名 | **保留编码 `PLATFORM_ADMIN`，仅把显示名改为「管理员」；删除 `SUPER_ADMIN`**。编码改名属于纯机械的大范围改动，放到功能完成后再评估 |
| 2 | `ACCOUNT_MANAGE` 不可授予子账号 | **同意**（防止子账号自我提权） |
| 3 | 邮箱验证码的演示降级 | **同意**：未配 SMTP 时验证码写后端日志，界面显著标注「演示环境未真实发送邮件」 |
| 4 | 政策 `EXPIRED` 已失效状态 | **需要** |
| 5 | 驿站改营业时间/电话 | **可直接改，但需邮箱验证**（不走审批）；**只有位置变更走审批** |
| 6 | 实施批次 | **两批一起做**（角色体系 + 邮箱验证码 + 账号安全 + 政策创作 + 驿站端补全 + 变更审批） |

### 由此确定的实现顺序

1. 角色模型：3 角色、删除 `SUPER_ADMIN`、显示名改「管理员」、权限表与子账号
2. 数据库：邮箱字段、验证码表、权限表、变更申请表、政策创作字段、爽约与暂停服务字段
3. 邮箱验证码服务（含演示降级）
4. 账号安全：改账号 ID / 改密码 / 绑邮箱（三端）
5. 账号管理：子账号创建与权限分发、改他人账密
6. 政策声明与建议创作 + `EXPIRED` 状态
7. 驿站端补全：我的驿站、变更申请（位置走审批、营业时间电话直接改+邮箱验证）、评价查看与回复、向本站用户发通知、爽约标记、暂停服务、活动取消与候补
8. 管理员端：变更审批、数据复核工作台
9. 测试与文档同步

## 十、原始待确认清单（已全部确认，见第九节）

1. **角色命名**：管理员用 `ADMIN`，还是保留 `PLATFORM_ADMIN` 这个名字只删 `SUPER_ADMIN`？（我建议 `ADMIN`，更贴合"唯一管理员"）
2. **`ACCOUNT_MANAGE` 不可授予子账号**（防自我提权），同意吗？
3. **邮箱验证码的演示降级**：未配 SMTP 时写日志 + 界面显著标注，可以吗？
4. **政策状态加 `EXPIRED`** 需要吗？
5. **驿站能否直接改营业时间与电话**，还是也走变更申请？（位置我按走审批设计）
6. **先做第一批还是两批一起**？
