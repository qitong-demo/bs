# 系统使用说明

项目名称：新就业群体友好驿站服务与诉求响应平台

本文档面向系统使用者与验收人员，说明运行环境、启动步骤、各角色的操作流程、接口调试入口与常见问题处理方法。

> 数据边界说明：**驿站名录已接入全国多城市公开来源**，覆盖 **7 个城市、共 1344 条**公开来源名录
> （杭州 267、北京 550、上海 36、深圳 117、广州 28、成都 172、武汉 174）。每条记录都保存了 `city_code`、
> 来源名称、来源链接、发布日期与核对日期，并可用 `data_status` 区分字段的可核对程度
> （`VERIFIED` / `PARTIAL` / `MANUAL`）；逐城市来源清单见 [驿站数据来源](驿站数据来源.md)。
> **7 个城市的公开来源都没有提供点位坐标**：现有坐标由**高德地图地理编码派生**（全库 **1247/1344 条**，93%），
> 坐标来源单独记录在 `geocode_source` / `geocode_at`，**不参与 `data_status` 判定**，每条记录的 `data_note` 会标注
> 「坐标为高德地图地理编码派生，非来源给出」；**坐标属于派生数据、误差可达数百米，只能用于地图展示与就近参考，
> 不能当作精确位置**。95 条因复核不合格（行政区冲突 / 距城市中心过远）被丢弃、2 条未能定位，坐标保持为空。
> 驿站的**营业时间以高德地图 POI（第三方数据）为准**：高德未提供具体营业时间的驿站才**回退来源文本**
> （实测高德给出营业时间 **386 条**，其中 **227 条**覆盖了来源原值；**760 条**回退来源，合并后**有营业时间 1146 条**）。
> **联系电话为来源优先、高德补空**：公开来源完全不提供电话，实测 **408 条全部来自高德**。
> 来源字段单独记在 `business_source`（`AMAP_POI` / `AMAP_POI+SOURCE` / `SOURCE+AMAP_POI` / `SOURCE`，
> 实测分布为 `AMAP_POI` 386 条、`SOURCE+AMAP_POI` 178 条、`SOURCE` 604 条、`AMAP_POI+SOURCE` 0 条）与 `business_synced_at`；
> 高德覆盖来源原值时会同时写明「营业时间以高德地图为准（第三方数据）」与「来源原文的开放时间为「…」」，
> 电话取自高德时写「联系电话来自高德地图 POI（第三方数据），非来源给出」。因此**不是每个驿站都有营业时间或电话**
> （仍有 **198 条**没有营业时间，其中 **176 条**连电话也没有）。高德 **不提供**「服务设施」结构化字段，也**没有**「此刻是否营业」的实时状态字段：
> 界面上的「营业中 / 已打烊 / 营业时间待核验」标签是**前端按营业时间文本本地推算**的展示值，**不是第三方实时状态**；
> 饮水 / 充电 / 热饭等服务项目**仍然只能来自公开来源文本**；营业时间与电话也**不是驿站官方提供的**。
> 另有 **567 条**记录因来源只给名称、没有地址而**未导入系统**；深圳 105 条、武汉 132 条来自官方发布的
> **图片表格**，属于从图片提取，可信度略低于文本来源。**名录不等于已实地核实，也不等于各城市驿站的完整清单**，
> 点位 `status` 反映各来源发布时的状态，**使用前需要重新核实**。
> 演示账号、演示活动以及预约、诉求、报名、评价等为运行时记录；统计指标是后端对系统内已记录数据的
> 实时聚合结果，**不代表真实服务人次、真实业务成效或增长结论**。详见 [AUDIT_AND_EVIDENCE.md](../AUDIT_AND_EVIDENCE.md)。
>
> **政策与资讯同样接入了真实公开来源**：`data/policy-sources.json` 为**人工逐条检索并打开页面核实**的清单，
> 经 `scripts/generate-news-seed.mjs` 生成 `backend/src/main/resources/db/news.sql` 与 [政策资讯来源](政策资讯来源.md)，
> **实测导入 94 条**（官方 90 + 平台发布 4），其中**不限城市 60 条、城市相关 34 条**
> （杭州 8、上海 6、深圳 6、北京 4、广州 4、成都 3、武汉 3），每条都带**可打开的原文链接**。
> **分城市规则**：`city_code` 为空表示**不限城市、在所有城市都可见**；非空时**只在该城市可见且排在最前面**。
> 另有 **10 条被排除**：6 条未能打开页面核实（超时 / 412 反爬 / 重定向次数过多）、4 条城市不在平台覆盖范围
> （南京 3、珠海 1，导入后在任何城市都不会显示），逐条原因见 [政策资讯来源](政策资讯来源.md) 第三节。
> **这些条目来自公开发布的政策文件与平台公告，系统只做摘录与归类，不代表已获得发布方授权，
> 也不代表对政策内容的解释；具体执行以原文为准。**

## 一、系统简介与适用对象

### 1.1 系统简介

本系统是一个「新就业群体友好驿站服务与诉求响应平台」的毕业设计原型，采用前后端分离架构：

- 后端：Spring Boot 3.3.5 提供 REST API，共 **73** 个接口、**14** 个分组（含公开的「城市」分组），统一返回 `{ code, message, data }` 结构，使用 JWT 鉴权并按角色校验。
- 前端：Vue 3 + Vite + Element Plus 单页应用，提供用户端 11 个功能模块与管理端 11 个标签页；首页地图使用 **高德地图 JS API 2.0**（中文底图，随所选城市自动定位，未配置 Key 时显示降级提示）；**布局按 1180 / 900 / 640 三档断点自适应，手机端不再出现横向滚动，侧栏在窄屏变为浮层抽屉**（见 5.14）。
- 数据：驿站名录来自 7 个城市公开发布的权威来源（**1344 条**，见 [驿站数据来源](驿站数据来源.md)）；**公开来源不含点位坐标，坐标由高德地图地理编码派生**（1247/1344 条，`geocode_source` / `geocode_at` 单独记录、不参与 `data_status` 判定，精度边界见 5.3 与第十章）；**营业时间以高德地图 POI（第三方数据）为准、高德未提供时回退来源文本；联系电话为来源优先、高德补空**（高德提供营业时间 386 条、其中 227 条覆盖了来源原值；未提供的 760 条回退来源，合并后全库有营业时间 1146 条；有电话 408 条且全部来自高德；`business_source` / `business_synced_at` 单独记录，边界见 5.3、5.6 与第十章）；**政策与资讯来自人工逐条核实过的公开来源，共 94 条**（官方 90 + 平台发布 4），每条带可打开的原文链接，见 [政策资讯来源](政策资讯来源.md)；业务数据默认提供内存演示实现（无需数据库即可运行），另提供 MySQL 8.0 持久化实现，两者对外接口口径一致。
- 城市：**面向全国的多城市平台**，`city` 表保存 7 个城市及其中心点，顶栏可按城市切换驿站查询与首页地图；用户所在城市按「手动选择 > 浏览器定位 > 平台默认城市」的顺序判定，定位由 `GET /api/city/locate` 调用高德逆地理编码得到**真实城市名**并判断是否已覆盖（未覆盖时提示并展示最近的已覆盖城市）。

系统覆盖 7 个业务模块：友好驿站、服务预约、诉求反馈、活动报名、政策资讯与通知公告、服务评价、统计分析与报表。

### 1.2 适用对象

| 对象 | 使用内容 |
| --- | --- |
| 普通用户（新就业群体，如外卖骑手、快递员、网约车司机） | 查询驿站、预约服务、提交诉求、报名活动、阅读政策资讯、评价服务、查看个人数据 |
| 驿站管理员 | 审核预约（仅本人负责驿站，按 `station.manager_id` 判定）、处理诉求（仅负责驿站所在区域，且只处理受理方为驿站的诉求）、维护活动、查看报名记录、导出报表 |
| 平台管理员 | 不受驿站范围限制，可见平台全域数据；在驿站管理员能力之上管理驿站、服务项目、资讯公告、账号与角色权限 |
| 超级管理员 | 拥有平台管理员的全部能力，并可调整任意账号的角色与启用状态 |
| 验收 / 答辩人员 | 按第四章启动系统，按第八至十一章进行接口调试与验证 |

| 功能 | 普通用户 | 驿站管理员 | 平台管理员 | 超级管理员 |
| --- | --- | --- | --- | --- |
| 访问用户端工作台（11 个模块） | 可用 | 可用 | 可用 | 可用 |
| 进入管理工作台 `/admin` | 不可用（路由跳回首页） | 可用 | 可用 | 可用 |
| 运营概览（工作流与统计指标） | — | 可见（平台全域口径） | 可见（平台全域） | 可见（平台全域） |
| 预约审核（确认 / 拒绝） | 不可用（403） | 可用（仅本人负责驿站的预约，按 `manager_id`） | 可用（全部驿站） | 可用（全部驿站） |

| 驿站管理（新增 / 修改 / 状态 / 逻辑删除） | 不可用（403） | 前端隐藏；后端接口允许 | 可用 | 可用 |
| 服务项目管理 | 不可用（403） | 前端隐藏；后端接口允许 | 可用 | 可用 |

| 角色权限 | 不可用（403） | 不可用（403） | 可用 | 可用 |
| 个人资料读写 | 可用（本人） | 可用（本人） | 可用（本人） | 可用（本人） |
| 查询本人预约 / 诉求 / 报名 / 评价 | 可用（本人） | 可用（本人） | 可用（本人） | 可用（本人） |

### 2.1 各角色的数据范围

| 角色 | 数据范围 | 实现位置与说明 |
| --- | --- | --- |
| 普通用户 | 仅本人数据 | `/api/appointment/my`、`/api/appeal/my`、`/api/activity/my`、`/api/evaluation/my` 等接口按当前登录账号编号过滤；无管理端入口 |
| 驿站管理员 | 预约：仅本人负责驿站（`station.manager_id`）的预约；诉求：仅负责驿站所在区域的诉求 | `backend/src/main/java/com/friendlystation/platform/auth/DataScopeService.java`：平台级角色返回 `null` 表示不限制，驿站管理员按 `StationService.listByManager(managerId)` 解析负责驿站，投影为**驿站编号集合**与**区域集合**（空集合表示范围内没有可见数据）。`AppointmentController` / `AppealController` 的 `/admin/page` 在调用前计算范围并传入 `WorkflowService.appointmentPage(..., stationIds)` / `appealPage(..., areas)` |
| 平台管理员 | 平台全域，不受驿站范围限制 | `DataScopeService.isPlatformLevel(user)` 对非 `STATION_ADMIN` 角色判定为平台级，`stationIds()` / `areas()` 均返回 `null` |
| 超级管理员 | 全系统最高权限，不受驿站范围限制 | 与平台管理员同一判定口径，并额外可在「账号管理」调整任意账号的角色与启用状态 |

说明：

1. 管理端标签页的显隐是前端体验优化，**后端每个接口都带有 `@RequireRole` 校验**，越权请求会被拒绝（HTTP 403），前端隐藏不构成安全边界。
2. 「驿站管理、服务项目管理、资讯公告管理」三个标签页仅对 `PLATFORM_ADMIN` 与 `SUPER_ADMIN` 显示；对应后端接口的 `@RequireRole` 实际值为 `{"STATION_ADMIN", "PLATFORM_ADMIN", "SUPER_ADMIN"}`（见 `StationController`、`StationServiceController`、`NewsController`、`NoticeController`、`ActivityAdminController` 与 `AdminController` 类级注解），因此直接用 `STATION_ADMIN` 的 token 调用这些接口仍会成功。账号管理与角色权限是例外：`AdminController` 的 `/api/admin/users`、`/api/admin/users/{id}`、`/api/admin/roles` 等方法级 `@RequireRole` 为 `{"PLATFORM_ADMIN", "SUPER_ADMIN"}`，驿站管理员请求会被拒绝（403）。
3. 数据范围当前只作用于「预约审核」与「诉求处理」两个列表接口（`GET /api/appointment/admin/page`、`GET /api/appeal/admin/page`）。报表导出、报名记录、驿站后台分页与评价分页等接口仍不按驿站范围过滤，只做角色校验。
4. `appeal` 表没有 `station_id` 字段，因此诉求只能用负责驿站的 `area`（区域）做近似限定：同一区域内非本人负责驿站的诉求仍会出现在列表中，这是已知的精度损失。
5. 演示数据未预置超级管理员账号，其权限口径与平台管理员一致（并额外可调整任意账号角色与状态）。

## 四、启动步骤

以下命令均以项目根目录 `C:\Users\Lenovo\Desktop\bs` 为基准，路径使用相对项目根的形式。所有命令可在 PowerShell 中直接执行。

### 4.1 方式一：默认演示模式（内存，无需 MySQL）

后端默认配置（`application.yml`）已排除 DataSource 自动配置，业务数据保存在服务端内存中，**重启后端后新增数据会清空**。

步骤 1：构建并启动后端

```powershell
cd backend
mvn -q -DskipTests package
java -jar target/platform-0.0.1-SNAPSHOT.jar
```

启动成功后后端地址为 `http://127.0.0.1:8080/`。

步骤 2：安装依赖并启动前端（开发模式）

```powershell
cd frontend
npm install
npm run dev
```

访问地址：`http://127.0.0.1:5174/`。Vite 开发服务器已把 `/api` 代理到 `http://127.0.0.1:8080`。

也可以使用生产构建方式启动前端静态服务：

```powershell
cd frontend
npm install
npm run build
cd ..
node scripts/serve-dist.mjs
```

`scripts/serve-dist.mjs` 会托管 `frontend/dist` 并把 `/api` 反向代理到后端，默认监听 `127.0.0.1:5174`；可用 `--port` 与 `--api` 覆盖：

```powershell
node scripts/serve-dist.mjs --port 5174 --api http://127.0.0.1:8080
```

### 4.2 方式二：MySQL 模式

步骤 1：初始化数据库（会创建库、建表，导入 1344 条真实驿站名录、94 条政策资讯与演示账号、演示活动）

```powershell
$env:MYSQL_USER = "root"
$env:MYSQL_PASSWORD = "你的真实密码"
pwsh -File scripts/init-mysql.ps1 -Reset
```

初始化脚本按 **`schema.sql` → `stations.sql` → `news.sql` → `data.sql`** 的顺序执行：

1. `schema.sql`：建库建表，含新增的 `city` 表与 `station.city_code` 列，以及 `news` 表新增的 6 个来源字段（共 15 张表）；
2. `stations.sql`：导入 **`city` 表（7 个城市）与 1344 条驿站名录**，先清理 `station_service` / `station` / `city` 再插入，避免重复导入；
3. `news.sql`：导入 **94 条政策与资讯**（官方 90 + 平台发布 4；不限城市 60 + 城市相关 34）。脚本开头先 `DELETE FROM news` 再插入，可重复执行；文件由 `scripts/generate-news-seed.mjs` 生成，**请勿手工编辑**；
4. `data.sql`：导入演示账号与演示活动（活动记录引用驿站编号，因此驿站名录必须先于它执行）。

脚本显式使用 `--default-character-set=utf8mb4` 避免中文乱码，执行结束会回显**数据库字符集、驿站数量、
服务项目数量、1 号驿站名称与来源核对日期**，可据此自检（正常输出形如「驿站数量：1344 条，服务项目：N 条」）。

> 注意：`schema.sql` 使用 `CREATE TABLE IF NOT EXISTS`，不会为已存在的表补充新增字段。
> 数据库结构有调整时（例如新增 `city` 表与 `station.city_code` 列，或为 `news` 表新增
> `source_type` / `publisher` / `platform` / `city_code` / `published_at` / `source_url` 六个来源字段），
> 必须使用 `-Reset` 重建数据库。

脚本参数说明：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-User` | 环境变量 `MYSQL_USER` | 数据库账号 |
| `-Password` | 环境变量 `MYSQL_PASSWORD` | 数据库密码 |
| `-HostName` | `localhost` | 数据库主机 |
| `-Port` | `3306` | 数据库端口 |
| `-MysqlExe` | `C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe` | mysql 客户端路径 |
| `-Reset` | 关闭 | 是否先 `DROP DATABASE friendly_station` 再重建 |

```powershell

node scripts/geocode-stations.mjs --limit 50 # 只处理 50 条（调试用）
```

结果写入**入仓的缓存** `data/station-geocode.json`（保证结果可复现、重跑不必再调接口），再由 `node scripts/generate-station-data.mjs` 把缓存合并进 `db/stations.json` / `db/stations.sql`，并在输出中给出可信度统计（POI 可信命中、地理编码保留、复核丢弃、未定位）。

5. 回填驿站**营业信息**（营业时间 `open_time` 与联系电话 `tel`）的命令（**需先设置 Web 服务 Key**，与坐标回填用同一把 Key）：

```powershell
$env:AMAP_WEB_KEY = "你的高德 Web 服务 Key"
node scripts/sync-station-business.mjs            # 增量：只处理缓存里没有的
node scripts/sync-station-business.mjs --refresh  # 全量重跑
node scripts/sync-station-business.mjs --limit 50 # 只处理 50 条（调试用）
```

结果写入**入仓的缓存** `data/station-business.json`（同样是为了可复现、重跑不必再调接口），再由 `node scripts/generate-station-data.mjs` 合并进 `db/stations.json` / `db/stations.sql`。要点：

- **只同步高德真有的两个字段**：`biz_ext.open_time`（营业时间）与 `tel`（电话）。高德 POI **没有**「服务设施」结构化字段（`type` / `tag` 只是「生活服务 / 政府机构」这种粗分类），也**没有**「此刻是否营业」的实时状态字段，所以饮水 / 充电 / 热饭等服务项目**仍然只能来自公开来源文本**；界面上的实时营业状态由前端按营业时间文本本地推算（见 5.3），**不是高德提供的实时状态**，预约时段的校验仍以后端为准。
- **优先级（本轮口径）：营业时间以高德为准、高德未提供时才回退来源文本**；**联系电话为来源优先、高德补空**（公开来源完全不提供电话，因此 408 条电话全部来自高德）。合并后 `business_source` 取值四种：`AMAP_POI`（营业时间与电话均来自高德）/ `AMAP_POI+SOURCE`（营业时间来自高德、电话来自来源）/ `SOURCE+AMAP_POI`（营业时间来自来源、电话来自高德）/ `SOURCE`；实测分布为 `AMAP_POI` **386 条**、`SOURCE+AMAP_POI` **178 条**、`SOURCE` **604 条**、`AMAP_POI+SOURCE` **0 条**（不存在「电话来自来源」的情形），另有 176 条两项都没有。
- **只接受可信匹配**：复用与坐标回填相同的三重校验（**区县一致性 + 名称相似度 + 地址相似度**），营业时间还要求形如 `HH:mm-HH:mm` 或「24小时」，过滤明显不属于驿站的取值（例如把菜鸟驿站的营业时间误配回来）。实测全库 1344 条中可信匹配 **921 条**：高德提供营业时间 **386 条**（其中 **227 条**覆盖了来源原值，`data_note` 会保留「来源原文的开放时间为「…」」留痕）、提供电话 **408 条**；高德未提供营业时间的 **760 条**回退来源文本，合并后全库**有营业时间 1146 条**。
- **属于第三方数据**：高德的营业时间与电话来自商户认领与用户上报，**不是驿站官方提供的**，**可能过期或与实际不符，使用前宜再核实**。

## 五、普通用户操作指引

普通用户登录后进入用户端工作台，左侧导航包含 11 个模块，顶栏提供**城市选择器**。

### 5.1 用户城市如何确定（定位优先，四级顺序）

进入首页时会依次按以下顺序确定「当前城市」，**顺序严格固定**，并且全程静默兜底、不阻塞页面：

| 顺序 | 判定条件 | 行为 | 说明 |
| --- | --- | --- | --- |
| 1 | 浏览器 `localStorage` 中存在用户**手动**选过的城市（键 `friendly_station_city_code`）且该城市仍在城市列表中 | 直接使用该城市，**不再请求浏览器定位** | 尊重用户已有的主动选择，避免每次打开都被定位覆盖 |
| 2 | 否则请求浏览器定位（`navigator.geolocation`，超时 8000ms、低精度、10 分钟缓存） | 定位成功后用经纬度调用 `GET /api/city/locate`，由后端用**高德逆地理编码**得到**真实城市**，并判断该城市是否在平台已覆盖范围内；**未覆盖时**用返回的最近已覆盖城市展示，同时保留真实城市名用于提示 | 定位最贴近用户真实所在城市，未覆盖时也不会静默把用户当成别的城市的人 |
| 3 | 定位被拒绝 / 超时 / 失败 / `GET /api/city/locate` 调用失败 | 回退到城市列表第 1 项（平台默认城市杭州 330100） | 定位不可用时仍有城市可用，首页数据与地图能正常展示 |
| 4 | 城市列表为空（`GET /api/city/list` 失败） | 保持空城市，页面只提示、不渲染地图 | 不抛错，不阻塞其他模块 |

补充说明：

1. 城市列表来自公开接口 `GET /api/city/list`（无需登录），按 `sort_no` 升序，**第 1 项就是平台默认城市**。
2. 用户可以**随时在顶栏手动切换城市**，下拉选项文案为「城市名（驿站数）」，例如「北京市（550）」。
3. 手动选择会被记住：切换后写入 `localStorage`，之后打开系统都会优先使用该城市，直到用户再次手动切换。
4. 切换城市会立即刷新「驿站查询」与首页地图；**统计指标仍是全平台口径**（见第 5.2 节首页说明）。
5. 定位未覆盖时的提示：用户在苏州打开平台，后端 `GET /api/city/locate` 返回 `cityName=苏州市`、`covered=false`、`nearest=上海市`，前端据此给出提示「您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市」，而不是静默把用户当成别的城市的人（提示文案实现见 `frontend/src/stores/user.js` 的 `coverageHint`）。
   **这条提示在界面上是能直接看到的**：顶栏城市选择器右侧会出现一个橙色的「**未覆盖**」标签（`el-tag`，见 `frontend/src/views/DashboardView.vue`），**鼠标悬停会弹出完整提示文案**（`el-tooltip` 气泡）；用户手动切换城市后标签自动消失。此前这条文案只写在状态里、**没有渲染到任何组件**，界面看不到，属已修复的缺陷（见 [测试用例文档](测试用例文档.md) 的 BUG-18）。
   若未配置高德 Web 服务 Key，接口返回 `cityName` 为空、`covered=false`，前端使用返回的「最近已覆盖城市」且不显示未覆盖提示；若定位被拒绝、超时或接口失败，则回退城市列表第一项（杭州 330100）。

3. **统计指标仍是全平台口径**：切换城市只会改变「驿站查询」的列表与「附近友好驿站」地图的内容，

### 5.3 驿站查询与筛选

1. **先在顶栏选择城市**：下拉选项来自 `GET /api/city/list`，文案为「城市名（驿站数）」，例如「杭州市（267）」

2. 点击左侧「驿站查询」。系统内置 **7 个城市、1344 条公开来源的驿站名录**，通过 `GET /api/station/page`
   分页查询，请求会带上当前城市的 `cityCode`（例如北京 `110100`）。
3. 顶部**区域下拉框**的数据来自 `GET /api/station/areas?cityCode={当前城市}`，只统计当前城市的区县，
   选项形如「朝阳区（109）」，括号内为该区域的驿站数量；因此不会出现其他城市的区县。
4. 「服务类型」下拉会把选中的服务名作为 `service` 参数传给后端，**由服务端过滤**，而不是只筛当前页。
5. 关键字输入框匹配驿站名称、详细地址与服务项目名称；勾选「**只显示已启用**」会附加 `status=OPEN`。
   该复选框原先叫「只看营业中」，但它实际过滤的是**服务端的 `status` 字段（是否启用）**，与「此刻是否营业」无关，
   因此已改名并在悬停提示中说明；全库 1344 条名录的 `status` 均为 `OPEN`（反映各来源发布时的状态），所以勾选前后条数一致，
   **「此刻是否营业」请看每行右侧的实时状态标签**。
6. 列表为**服务端分页（每页 12 条）**，底部显示总条数与页码；页码与总数随所选城市变化
   （杭州 267 条、北京 550 条，全平台 1344 条）。
7. 点击任一驿站可查看右侧**详情面板**，面板按「可验证字段优先」的顺序展示：
   - **标题区**：驿站名称、区域 · 驿站类型、**实时营业状态标签**（三态见下方「实时营业状态」说明）。
   - **地址**：详细地址；来源未给地址的显示「地址待核验」。
   - **营业信息**（开放时间与联系电话合并为一行）：逐项显示，缺失时显示「开放时间待核验」「联系方式待核验」；
     右侧带**来源标签**——绿色「公开来源」（`businessSource=SOURCE`，开放时间取自来源文本）、橙色「高德同步」（`businessSource=AMAP_POI`，
     开放时间取自高德）、灰色「来源 + 高德」（`businessSource=SOURCE+AMAP_POI`，开放时间取自来源、电话来自高德），
     无营业信息时不显示标签。**灰色「来源 + 高德」标签反映的是字段级来源（营业时间取自来源、电话来自高德），
     并不表示「营业时间以来源为准」**：本系统的营业时间一律以高德为准、高德未提供时才回退来源。
   - **坐标**：经度 / 纬度（保留 5 位小数）并标注「**高德地图派生**」标签，仅在同时有经纬度时显示；
     坐标为高德地理编码的派生结果、不是来源给出，也不能当作精确位置。
   - **导航**：「在高德地图中搜索该驿站」外链（关键词为「驿站名称 + 地址」，新窗口打开
     `https://www.amap.com/search?query=...`）。
   - **服务设施**：以**虚线、弱化**的区块展示（不再与可验证字段争夺注意力），标题旁注明「**来自公开来源文本，
     高德地图未提供该字段**」；该驿站没有服务项目时显示「来源未逐条给出服务设施」。
   - **数据来源区块**：数据状态标签、来源名称、来源链接（新窗口打开）、来源发布日期与核对日期，
     必要时显示补充说明（例如「坐标为高德地图地理编码派生，非来源给出」「开放时间来自高德地图 POI（第三方数据），
     非来源给出」「所属行政区由高德地图地理编码补齐，非来源给出」「坐标已丢弃：<原因>」）。
8. 详情中提供**「导航：在高德地图中搜索该驿站」外链**（用「驿站名称 + 地址」作为关键词，在新窗口打开
   `https://www.amap.com/search?query=...`），以及「预约服务」与「收藏驿站」两个入口。
9. **首页/列表中的地图（高德地图 JS API 2.0）**：地图中心为所选城市的中心点，切换城市时会自动移动到
   新城市；只有同时带坐标的驿站才会打点，点击标记可查看名称与地址，并标注「（坐标为高德地图派生）」。
   未配置高德 JS API Key 或脚本加载失败时，地图会显示降级提示而不是空白；列表本身仍可正常查询与筛选。
10. **实时营业状态（按当前时间判断，三态）**：驿站**列表行、详情面板与地图气泡**三处的状态标签都由前端
    `frontend/src/utils/business-hours.js` 按**当前时间与营业时间文本**实时判断，**每分钟自动刷新一次**，
    因此到点或打烊后会自行变化，无需刷新页面：
    - **营业中**（绿色）：当前时刻落在营业时间内，或营业时间是「24 小时营业 / 24 小时开放 / 全天」；
    - **已打烊**（橙色）：有可解析的营业时间，但当前时刻不在其中（凌晨、打烊后自然显示「已打烊」，这是正确行为）；
    - **营业时间待核验**（灰色）：**没有营业时间**或营业时间文本无法解析——此时**绝不显示「营业中」**，不猜测。
    驿站被停用（`status=CLOSED`）时优先显示「已停用」。说明：这只是**按营业时间文本推算的展示值**，
    **不是第三方实时营业状态**（高德也没有该字段），**预约时段是否放行仍由后端校验决定**（见 5.6）。

> 数据边界：来源未提供、高德也没能补出的字段（例如 **198 条**驿站的开放时间、**936 条**驿站的联系电话）显示为「待核验」，
> 系统不做推测填充。**营业时间以高德地图 POI 为准，高德未提供具体营业时间的驿站才回退来源文本**
> （实测高德提供营业时间 386/1344 条、其中 227 条覆盖了来源原值；回退来源 760 条，合并后有营业时间 1146 条；
> 有电话 408/1344 条且**全部来自高德**，公开来源完全不提供电话）。营业时间取自高德时，`data_note` 会写明
> 「营业时间以高德地图为准（第三方数据）」；覆盖了来源原值时还会保留「来源原文的开放时间为「…」」以便回查；
> 电话取自高德时写明「联系电话来自高德地图 POI（第三方数据），非来源给出」——
> 这两项**不是驿站官方提供的**，可能过期或与实际不符，使用前宜再核实。
> 高德**没有**「服务设施」结构化字段，所以服务设施**只来自公开来源文本**，界面上也是弱化展示并注明出处；
> 高德也**没有**「此刻是否营业」的实时状态字段：界面上的「营业中 / 已打烊 / 营业时间待核验」是**前端按营业时间文本
> 本地推算**的展示值（见本节第 10 条），**不代表第三方实时状态**；预约时段的**校验在后端**，前端只负责展示。
> **点位坐标不是来源给出的**，而是高德地图地理编码的派生结果（1247/1344 条），
> 因此详情中的数据来源区块会明确标注「坐标为高德地图地理编码派生，非来源给出」，
> 精度只到「可用于地图展示与就近参考」，**不能当作精确位置**（误差可达数百米）。
> `PARTIAL` 记录的服务设施来自来源对该批驿站的统一描述，未逐站核实；
> 各城市对同类驿站的叫法不同（杭州「小哥驿站 / 城管驿站」、北京「工会驿站 / 暖新驿站」、
> 上海「户外职工爱心接力站」、深圳「暖蜂驿站」、成都「职工驿站」、武汉「临空港湾」等），
> 系统按来源原文记录，不统一改名。另有 567 条只有名称、没有地址的记录**未导入系统**。详见
> [驿站数据来源](驿站数据来源.md)。

### 5.4 收藏

1. 在驿站详情中点击「收藏驿站」，提示「已收藏该驿站」；再次点击可取消收藏。
2. 点击左侧「我的收藏」，集中查看已收藏的驿站，点击任一记录可直接进入预约。
3. 说明：收藏数据保存在本机浏览器 `localStorage`（键名 `friendly_station_favorites`），未写入后端数据库；更换浏览器或清理浏览器数据后收藏会丢失。

### 5.5 服务预约（提前联系驿站）

> **语义说明（重要）**：服务预约**不是**「预约使用饮水 / 空调」这类设施——饮水、休息这类随时可用的小事可以直接前往，驿站也没法逐个受理。
> 它的实际含义是「**我有一件事，想提前联系驿站确认是否可行**」，例如借用场地开安全培训、团体到访、咨询政策、需要特定帮助等。
> 因此**预约事项由你自己填写**（不再从固定服务项目里选），驿站管理员看到后在后台确认或拒绝，必要时按你留的电话回电。

1. 点击左侧「服务预约」，或在首页驿站列表点「提前联系」、在驿站详情点「提前联系」。页面标题为「**提前联系驿站**」，
   副标题为「说明你的情况，由驿站确认是否可行」。
2. 按下面的顺序填写表单：

   | 字段 | 是否必填 | 说明 |
   | --- | --- | --- |
   | 服务驿站 | 必填 | 可搜索选择；选定后会显示该驿站的**营业时间**提示（如「该驿站营业时间：10:00-22:00」） |
   | **想提前沟通什么** | **必填** | **自行填写**，最多 100 字（带字数统计）。占位提示：「例如：我们 10 人想借用驿站场地开一次安全培训，能否安排？」未填写提交会返回 400 与「请填写想提前沟通的事项…」 |
   | 联系电话（便于驿站回复确认） | 选填 | 最多 30 字，只能填数字、空格与 `+ - ( )`，长度 5～30（座机与手机号都可以）。格式不合法会返回 400 与「联系电话格式不正确…」 |
   | 希望联系的日期 | 必填 | 日期选择器，格式 `yyyy-MM-dd` |
   | 方便联系的时段 | 必填 | **选项按该驿站营业时间自动生成**（见第 3 条）。未选驿站时显示「该驿站暂无可选时段，请先选择驿站」 |

3. **时段选项是算出来的，不是写死的**：原先界面写死 `09:00 / 14:00 / 18:00` 三个时段，而系统又要求时段必须落在营业时间内，
   于是 10 点开门的驿站选了 `09:00-11:00` **必然被后端拒绝**（点了就报错）。现在改为按该驿站**当前生效的营业时间文本**
   自动生成：以营业开始时刻为起点、默认每 2 小时一段、最多给出 4 段（`buildSlots`）。
   - 营业时间 `10:00-22:00` → 时段从 **10:00** 起，不会出现 `09:00-11:00`；
   - 营业时间为「24 小时营业 / 24 小时开放 / 全天」 → 按全天处理；
   - 营业时间缺失或无法解析 → 不给出任何时段选项，此时也不会有可用时段可提交。
4. 点击「**提交联系申请**」，成功后回到表单右侧的「预约记录」列表，新记录的状态为「**待驿站确认**」，
   列表里显示你填写的**沟通事项**与驿站名称。
5. 在页面右侧可查看本人全部预约及其状态：待驿站确认、已确认、已拒绝、已取消、已完成。
6. 待驿站确认的预约可点击「取消」撤回；其他状态不可取消（重复取消返回 400「只有待确认的预约可以取消」）。
7. 说明：预约编号由服务端生成，审核由驿站管理员或平台管理员在管理端「预约审核」完成（见 6.1）。
   驿站不受理时可在拒绝时填写审核说明，你会在「预约记录」与「消息中心」看到结果。
8. **数据表变化**：`service_appointment` 表的 `service_id` 改为**可空**（仅为兼容历史数据保留），
   新增 `service_name`（`VARCHAR(100) NOT NULL`，即你填写的沟通事项）与 `contact_phone`（`VARCHAR(30)`）两列。
   因此导出预约台账 CSV 的表头已同步变为「编号,服务驿站,**想提前沟通的事项**,**联系电话**,预约日期,预约时段,当前状态,预约人,审核说明,提交时间」。
9. **「数据统计」里的排行仍是按驿站**：由于事项已是自由文本（每条都不同），按服务项目排行不再成立，
   排行改为「**驿站联系申请排行**」——回答「哪些驿站被联系得最多」（见 5.12）。

### 5.6 预约时段与营业时间

预约时段（如 `09:00-11:00`）**必须落在所选驿站的营业时间内**，这条规则由后端统一校验，用户端与管理端两套实现（MySQL 的 `MysqlWorkflowService.addAppointment` 与内存的 `DemoWorkflowStore.addAppointment`）行为一致。

1. **校验规则**：提交预约时，后端用 `backend/src/main/java/com/friendlystation/platform/common/BusinessHours.java` 解析该驿站的营业时间文本，判断所选时段是否被完整包含在某个营业区间内。
2. **营业时间支持的写法**：`07:00-18:00`、`8:30-22:00`、`09:00-12:00 14:00-18:00`（多区间，午休时段不算营业）、**全角冒号** `8：30-17：30`、以及「`24小时营业`」「`24 小时开放`」「`全天`」等全天开放写法；连接符支持 `-`、`—`、`~`、`至`。
3. **超出营业时间会被拒绝**：返回 **HTTP 400**，提示形如
   「所选时段 22:00-23:00 不在该驿站的营业时间内（10:00-22:00）」（括号内回显该驿站**当前生效的**营业时间原文）；此时**不会生成预约记录**。
   实测：「大悦城小哥驿站」的营业时间现在取高德值 `10:00-22:00`，预约 `14:00-15:00` 返回 200 通过、预约 `22:00-23:00` 返回 400 被拒绝；
   「钱江苑小哥驿站」（`24 小时开放`）预约 `23:00-23:30` 返回 200 通过。注意：营业时间口径改为**以高德为准**后，
   该驿站由来源的 `8:30-22:00` 变为高德的 `10:00-22:00`，因此原先可用的 `09:00-10:00` 现在会被拒绝——
   预约前请以详情里显示的营业时间为准。
4. **兜底原则（营业时间缺失时不做限制）**：如果该驿站**没有营业时间**、营业时间**无法解析**（例如「开放时间待核验」、
   「预计10月底正式对外开放」），或者填写的**时段文本本身无法解析**，系统一律**放行、不拦截**——原则是
   「判断不了就不挡」，宁可放行也不因为数据缺失误拒正常预约。
   因此**只有开放时间能解析成营业区间的驿站（全库 960/1344 条，约 71%）才真正受这条规则约束**；
   另有 174 条为「24 小时营业 / 全天」（任意合法时段都放行）、198 条没有开放时间、12 条开放时间无法解析。
5. **营业时间从哪里来、可能不准**：**以高德地图 POI（第三方数据）为准**；高德未提供具体营业时间的驿站才
   **回退来源文本**（实测高德提供营业时间 **386/1344 条**，其中 **227 条**覆盖了来源原值；回退来源 **760 条**，
   合并后**有营业时间 1146 条**）。例如「大悦城小哥驿站」来源写 `每日 8:30-22:00`、高德给的是商场时间 `10:00-22:00`，
   系统**取高德值**并在 `data_note` 中保留来源原文留痕。营业时间**不是驿站官方提供的**，
   且**可能过期或与实际不符**，必要时请再核实（配置与同步方式见第 4.5 节，字段边界见第十章）。
6. **校验在后端、展示在前端**：预约时段是否落在营业时间内，一律由后端
   `common/BusinessHours.java` 判定（内存与 MySQL 两套实现口径一致），前端**不参与放行或拒绝**；
   驿站列表、详情与地图气泡上的「营业中 / 已打烊 / 营业时间待核验」只是前端按同一份营业时间文本
   **本地推算的展示值**（每分钟刷新，见 5.3 第 10 条），两者可能在同一时刻给出不同观感
   （例如文本无法解析时前端显示「营业时间待核验」，后端则按兜底原则放行）。

### 5.7 诉求提交、进度查看与评价

> **这个模块不只承载「提出问题」**：骑手与驿站之间还有大量正向的互助需要被记录和转达，例如「驿站放了免费雨衣，
> 骑手用过之后自己买了补上」「骑手受伤，驿站工作人员帮忙包扎，骑手来道谢」。这类内容既不是问题也不是投诉，
> 却是平台里最值得留存的部分。因此模块扩成**三类内容**：**反映问题 / 表扬感谢 / 提出建议**。

1. 点击左侧「诉求反馈」。页面标题为「提交诉求或反馈」，副标题为「问题、建议、感谢都可以提交，提交后在『我的诉求』跟踪进度」。
2. **先选分类**（三个卡片，选中后表单的措辞与子类型会跟着变）：

   | 分类 | 表单措辞 | 子类型 |
   | --- | --- | --- |
   | 反映问题 | 问题标题 / 问题类型 / 具体内容 | 驿站服务、权益保障、设施建议、其他问题 |
   | 表扬感谢 | 想感谢谁 · 一句话概括 / 感谢类型 / 想说的话 | 热心帮助、互帮互助、拾金不昧、暖心服务 |
   | 提出建议 | 建议标题 / 建议类型 / 具体建议 | 服务时间、设施配置、流程优化、其他建议 |

3. **选择「反馈给谁」**（受理方有两种，由你选择，不再由系统按类型写死）：

   | 受理方 | 由谁受理 | 适用情形（界面提示） |
   | --- | --- | --- |
   | **驿站**（由驿站管理员受理） | 该驿站的驿站管理员 | 「由该驿站的驿站管理员受理；涉及驿站设施与服务的问题走这里。」 |
   | **平台管理员** | 平台管理员 | 「由平台管理员受理；涉及跨驿站、政策或权益保障的问题走这里。」 |

   选择「表扬感谢」分类时，受理方会**自动置为驿站**并提示「表扬感谢建议反馈给驿站，会直接转达给当时帮助你的工作人员」
   （要谢的是具体帮助过你的那个驿站）。若你不改，系统在未收到受理方时也会按规则推断：
   **表扬感谢一律给驿站；子类型里带「驿站」或「设施」的给驿站；其余给平台管理员**。
4. 填写**所属区域**与**具体内容**，如需匿名勾选「匿名提交」，后台列表中将显示为「匿名用户」，不展示提交人姓名。
5. 提交成功后进入「我的诉求」跟踪进度。**注意：状态文案会随分类变化**——同一个状态，三类内容读起来完全不同：

   | 阶段（状态机） | 反映问题 | 表扬感谢 | 提出建议 |
   | --- | --- | --- | --- |
   | 待处理（`PENDING_ACCEPTANCE`） | 已收到，会有人跟进 | 心意已收到 | 建议已收到 |
   | 已分派（`ASSIGNED`） | 已安排专人对接 | 正在转达给驿站 | 已转达相关同事 |
   | 处理中（`PROCESSING`） | 正在处理中 | 驿站正在回应 | 正在评估可行性 |
   | 完成（`RESOLVED`） | 已处理并回复你 | 驿站已回应，谢谢你的心意 | 已回复处理意见 |
   | 结束（`CLOSED`） | 本次跟进已结束 | 这段心意已存档 | 本次建议已归档 |

   界面上之所以不用「已提交 / 已受理 / 处理中 / 已办结」这套工单腔：骑手写下「感谢驿站帮我包扎伤口」，
   回一句「已办结」并不合适；驿站回一句「举手之劳，不必客气」才是这段互动真正的样子。
   **管理端仍显示「待受理 / 已分派 / 处理中 / 已办结」标准术语**（后端为管理端单独返回 `statusLabelStandard` 字段），
   因为开题报告与中期报告都要求「提交 → 受理 → 分派 → 处理 → 办结 → 评价」的闭环术语必须可见；
   **两套文案对应同一个状态机，不是两套流程**。
6. **回复才是这条反馈的「结果」**：在「我的诉求」点击记录查看进度时，流程图下方有一个**独立突出的「回复」区块**，
   显示**回复人**（「<处理人>的回复」）、**回复原文**与**时间**——不再把回复埋在处理记录时间线里。
   如果受理方还没有回复，该区块显示「**<受理方>尚未回复**」并附当前状态，你能一眼看出「有没有人回过我」。
7. **流程步骤标题也随分类变化，最后一步落在「回复」上**（表扬感谢为「心意已送达 / 已转达驿站 / 驿站查看中 / **驿站的回应**」；
   提出建议为「建议已提交 / 已转达相关同事 / 评估中 / 处理意见」；反映问题为「已提交 / 已受理 / 处理中 / 处理结果」）。
8. **只有状态为「已办结」（即用户端的「已处理并回复你」等完成态）的诉求可以评价**：点击「评价」，选择 1 到 5 分
   并填写评价内容后提交；未办结时提交会被拒绝并提示「诉求办结后才能评价」。

### 5.9 政策资讯

页面标题为「政策与资讯」。这里的内容**已接入真实公开来源**（不再是自编的演示标题）：清单来自
`data/policy-sources.json`，由**人工逐条检索并打开页面核实**，再经 `scripts/generate-news-seed.mjs` 生成
`backend/src/main/resources/db/news.sql` 与 [政策资讯来源](政策资讯来源.md)。**实测导入 94 条**
（官方 90 + 平台发布 4），其中**不限城市 60 条、城市相关 34 条**（杭州 8、上海 6、深圳 6、北京 4、广州 4、成都 3、武汉 3）。

1. 点击左侧「政策资讯」。
2. **筛选条有三组控件**：
   - **来源筛选（全部 / 官方 / 平台）**：对应接口参数 `sourceType`。选「平台」时只显示由平台企业自有渠道
     （官网新闻中心）直接发布的条目（实测 4 条，均为美团）。
   - **平台下拉（全部平台 / 具体平台）**：选项由 `frontend/src/constants/news-platforms.js` 生成，共 12 个
     （滴滴出行、饿了么、高德打车、货拉拉、京东外卖、京东物流、满帮、美团、顺丰、顺丰同城、中通、T3出行）；
     对应接口参数 `platform`，用于只看某个平台的动态。注意它与「来源筛选」不是同一个维度：
     官方媒体转述某平台举措时，来源仍是「官方」，但平台筛选可以命中它。
   - **分类筛选（全部 / 政策 / 通知 / 动态）**：作用于公告类型；资讯条目自身携带的是来源侧的分类
     （权益保障、职业伤害、劳动报酬、驿站服务、算法与规则、社会保险、福利补贴、技能培训、子女关爱），
     这些分类会以**行首的分类标签**原样显示。
3. **每一行显示五段信息**：**分类标签 · 来源标签 · 标题 · 城市标签 · 发布日期**。其中来源标签在平台条目上为橙色并显示平台名
   （如「美团」），官方条目为灰色「官方」；**城市标签**有值时显示城市名，为空时显示「**全国**」。
4. **分城市展示规则**：页面会带上当前城市的 `cityCode`，后端**只返回「该城市 + 不限城市」的内容，并把该城市的内容排在最前面**
   （其次按发布日期倒序）。也就是说：**不限城市的内容在所有城市都能看到**（国家层面政策、全国性平台规则），
   而某城市的专属政策**只在那个城市出现**，切到其他城市就看不到——因此不会出现「在杭州看到只属于深圳的政策」。
5. 前台列表只展示「已发布」的内容，草稿不在前台出现。
6. 点击记录打开详情查看正文；正文下方提示「该条内容暂无正文，请以官方来源为准」时，请以来源链接为准。

> **来源与授权边界（重要）**：这些条目来自公开发布的政策文件与平台公告，系统**只做了摘录与归类**——
> 摘要由编者整理，不是原文全文。系统**不声称**这些条目已获得发布方授权，也**不对政策内容作解释**；
> **具体执行以原文为准**。每条都可点开原文链接逐条核对。
>
> **另有 10 条被排除，原因如实列出**（完整清单见 [政策资讯来源](政策资讯来源.md) 第三节）：
> · **6 条未能打开页面核实**——3 条多次重试均超时、1 条抓取时抛出「尝试自动重定向的次数太多」、2 条服务器返回
>   `412 Precondition Failed`（反爬）；其中 2 条同题内容已改用其他已核实版本收录。
> · **4 条城市不在平台覆盖范围**——南京 3 条、珠海 1 条。平台只覆盖 7 个城市，这 4 条的 `city_code` 既不是空值、
>   也不属于已覆盖城市，**即使导入也不会在任何城市显示**，因此按口径直接排除。**排除不等于内容不存在或不实**，
>   只是本项目未能完成核实或不在覆盖范围内。
>
> 另外说明：资讯条目的分类取自来源侧归类，与筛选条上的「政策 / 通知 / 动态」按钮不是同一套取值，
> 因此**分类按钮主要影响公告**；想按主题浏览资讯时，用来源筛选与平台下拉更直接。

### 5.11 消息中心与未读提醒

1. 点击左侧「消息中心」，或点击顶部铃铛图标进入。
2. **消息是派生出来的，没有独立消息表**：消息列表由本人的**预约、诉求与报名记录**在前端汇总生成
   （预约与诉求各取最近 4 条、报名记录取最近 4 条），因此消息条数会随业务记录变化。
3. **未读状态与顶栏角标读同一份数据**：消息派生与已读状态统一由 `frontend/src/stores/message.js` 管理，
   顶栏铃铛角标（`el-badge`）与消息中心列表都读它的 `unreadCount`，**两处数字必然一致**；
   消息中心标题旁还会显示「N 条未读」徽标。
4. **已读状态保存在本机浏览器**：点击「全部标为已读」后，未读行变为 **0**、按钮变为「已全部读完」（禁用），
   顶栏角标同步清零；已读键写入 `localStorage`（键名 `friendly_station_read_messages`），刷新页面后仍然有效；
   读取失败时按「全部未读」处理，避免误标为已读。更换浏览器或清理浏览器数据后已读状态会丢失。
5. 说明：系统当前没有独立的站内消息表，也没有短信、邮件或推送通道，消息中心是客户端汇总视图。

> 历史缺陷（已修复，见 BUG-20）：消息列表与已读状态原先只存在于消息中心组件内部，而顶栏角标另按
> 「待处理预约 + 待处理诉求」算一套，两者毫无关联，因此点了「全部标为已读」角标数字依旧挂着；
> 现已统一到同一个 store，实测以 `rider_xiaowang` 登录（8 条消息）时角标为 8，全部标为已读后角标为 0。

### 5.14 手机端使用

**这一轮修复的最重要缺陷就是手机端不可用**：页面样式表里原先写着 `body { min-width: 1180px }`，1280px 断点内又写了
`min-width: 1024px`，等于把整页最小宽度钉死在桌面尺寸——手机（390px 宽）打开时页面宽 1180px，只能横向拖动，
侧栏还固定占位，模块标题会被挤成竖排单字。**问题不在「没写断点」，而是第一行就把宽度锁住了**。现已移除，
断点改为 **1180 / 900 / 640 三档**。

| 断点 | 布局变化 |
| --- | --- |
| 桌面（≥1181px） | 主区「地图 1.85 : 1 列表」并排；指标卡 6 列自适应；侧栏常驻 |
| ≤1180px | 主区改**上下堆叠**（地图在上、列表在下）；地图改为固定高度 `clamp(300px, 46vh, 420px)` 并取消弹性伸缩（否则父容器 `height: auto` 时会把地图压成 0 高）；指标网格 3 列；两栏页面改单列 |
| ≤900px | **侧栏改为浮层抽屉**（`position: fixed`，默认 `translateX(-100%)` 收起，展开时带阴影并有遮罩层承接点击）；顶栏允许换行、搜索框独占一行、城市选择器收窄；活动与分析网格单列 |
| ≤640px | 手机单列布局；指标卡 2 列并缩小内边距与字号；地图固定 260px；面板标题允许换行，避免被按钮挤成竖排 |

使用提示：

1. **窄屏首次进入时侧栏是收起的**，点顶栏左上角的汉堡按钮（`aria-label="切换菜单"`）展开；点导航项或点遮罩层自动收起，
   内容立刻可见。
2. **页面不应出现横向滚动条**。如果你在手机上仍要左右拖动才能看全，请先确认没有使用旧版本缓存
   （强制刷新或清空站点数据后重试）。
3. 手机端的自动化验证只用 **390×844 一个视口**（Playwright 无头 Chrome）完成，
   断点边界（1180 / 900 / 640 附近）与 640px 以下的小屏、横屏**未逐档回归**，也未在真机与 iOS Safari 上验证——
   **「无横向滚动」是在该单一视口下测得的结果**，不能推断为所有手机浏览器都正常。

## 六、驿站管理员操作指引

使用 `station_admin_01 / password` 登录后，点击右上角「管理工作台」进入 `/admin`。驿站管理员可见 6 个标签页：运营概览、预约审核、诉求处理、活动管理、报名记录、报表导出（驿站管理、服务项目管理、资讯公告管理、账号管理、角色权限 5 个标签页仅对平台管理员与超级管理员显示）。

> 数据范围提示：演示配置中 `station_admin_01` 负责 **1~4 号驿站**（`station.manager_id = 2`，即杭州的四家「小哥驿站」），
> 它们分别位于上城区、拱墅区、拱墅区与西湖区；其余点位未分配负责人。因此该账号在「预约审核」中
> 只能看到这四家驿站的预约，在「诉求处理」中只能看到上城区、拱墅区与西湖区的诉求（按区域近似，见第 2.1 节）。
> **这是杭州的演示配置**，属于演示数据、不属于公开来源内容；多城市名录导入后该配置保持不变。

### 6.1 预约审核

1. 打开「预约审核」标签页。
2. 顶部工具条支持按关键字（预约人、驿站或服务项目）搜索、按状态筛选、查询与重置；表格底部显示分页与总条数。
3. **列表只包含当前账号负责驿站（`station.manager_id`）的预约**：驿站管理员看到的是自己负责驿站的预约，平台管理员与超级管理员看到全部驿站的预约。若负责驿站下没有预约，列表为空而不是显示其他驿站的数据。
4. 列表展示编号、预约人、服务驿站、**沟通事项**（用户自行填写的 `serviceName`）、**联系电话**、预约日期、预约时段、状态、审核说明与提交时间。
   说明：预约事项本轮已由「从固定服务项目里选」改为「**用户自行填写想提前沟通什么**」，因此列名与导出表头同步由「服务项目」改为「沟通事项 / 想提前沟通的事项」并新增「联系电话」列（见 5.5）。
5. 对状态为「待驿站确认」的记录，点击「确认」或「拒绝」；拒绝时可填写审核说明。已处理过的记录不可重复审核，重复操作会返回「该预约已处理，不能重复审核」。
6. 点击「详情」查看单条预约的完整字段。

### 6.2 诉求处理

1. 打开「诉求处理」标签页，按状态或关键字筛选诉求。**状态列显示的是标准术语**（待受理 / 已分派 / 处理中 / 已办结 / 已关闭）——
   用户端看到的是按分类改写的温暖措辞（「心意已收到」等），管理端保留闭环术语，两者是同一个状态机，
   前端取后端的 `statusLabelStandard` 字段（缺失时回退本地常量表）。
2. **列表只包含当前账号负责驿站所在区域的诉求**：驿站管理员只能看到自己负责驿站所在区域（演示配置为上城区、拱墅区、西湖区，见第 2.1 节与第六章开头）的诉求，平台管理员与超级管理员可看到全部区域。说明：`appeal` 表没有 `station_id` 字段，无法精确到驿站，因此按负责驿站的 `area` 做近似限定，同一区域内非本人负责驿站的诉求仍会出现在列表中。
3. 对未办结的诉求可执行三类操作，**三种操作填写的都是要给用户看的话，不是内部备注**：

   | 操作 | 对话框标题 | 字段标签 | 提交后状态 |
   | --- | --- | --- | --- |
   | 分派 | 分派处理人 | 分派说明（可留空，留空时系统记录为「已分派处理人」） | 已分派 |
   | 处理中 | **给用户回复进展** | 给用户的进展回复（占位提示「填写当前进展，用户能看到」） | 处理中 |
   | 办结 | **回复并结束** | **给用户的回复（必填）** | 已办结，并写入办结时间 |

4. **「给用户的回复（必填）」是本轮最重要的界面变化**：
   - 字段名由原先的「处理说明」改为「**给用户的回复（必填）**」，按钮由「办结诉求」改为「**回复并结束**」。
   - 占位提示为「**这段话会直接展示给用户，请用你自己的话写。例如：举手之劳，不必客气，欢迎常来。**」
   - 回复是**自由输入的 300 字文本，没有预设选项**——驿站想感谢骑手的反馈，就得能自己打出想说的话，
     而不是从「已处理 / 已致谢 / 已回复」这类结论里挑一个。
   - 这段文本会出现在**用户端独立的回复区块**里（显示回复人、原文与时间），不再只躺在处理记录时间线中。
   - **注意实际约束位置**：必填是**前端校验**（内容为空时提示后不提交）；后端 `handleAppeal` 在内容为空时会把记录
     写成状态标签文本（如「已办结」）而不是返回 400。因此**请勿直接调接口跳过这一步**，否则用户会收到一条
     没有实质内容的「回复」。
5. 已办结或已关闭的诉求不可再次分派或处理，重复操作返回「该诉求已办结或关闭，不能重复处理」；并发提交时只有一次会成功，其余请求返回同样的中文提示。
6. 点击记录可在详情弹窗中查看诉求内容、**受理方**、处理人与办结时间，以及完整的处理时间线（含每一步的操作人与内容）。
7. 匿名诉求在列表中显示为「匿名用户」。
8. **受理方在看板上的位置**：列表「受理边界」列与详情里的「受理方」来自用户提交时选择的反馈对象

6. 页面下方展示数据口径说明（`dataScope`、`dataStatus`、`generatedAt`）与各项指标的取值与口径。

1. 打开「账号管理」标签页，可按角色与关键字筛选账号，列表展示账号、姓名、角色名称、手机号与状态。

3. 点击状态开关启用或停用账号，状态只接受「正常」与「停用」。
4. 说明：停用账号会更新账号状态字段；当前版本未在登录环节拦截已停用账号，需要在后续版本补充登录校验。

### 7.6 角色权限

1. 打开「角色权限」标签页，表格展示系统内置的 4 个角色：角色编码、角色名称、角色说明、账号数量、可见标签页与数据范围。
2. 数据范围已落到实现：普通用户仅本人数据；驿站管理员的**预约**范围为其负责驿站（`station.manager_id`）的预约，**诉求**范围为其负责驿站所在区域的诉求（`appeal` 表没有 `station_id`，只能按区域近似）；平台管理员与超级管理员不受驿站范围限制。判定逻辑见 `backend/src/main/java/com/friendlystation/platform/auth/DataScopeService.java`，详细口径见第 2.1 节。
3. 角色调整入口在「账号管理」标签页：选中账号后设置角色，角色编码必须是 4 个内置编码之一（`USER`、`STATION_ADMIN`、`PLATFORM_ADMIN`、`SUPER_ADMIN`），至少保留 1 个。
4. 非法角色编码返回「角色编码无效：xxx」，空角色数组返回「至少需要保留一个角色」。
5. 页面提示：前端按角色隐藏标签页只是体验优化，后端每个接口都带 `@RequireRole` 校验，越权请求会被拒绝。
6. 数据范围的当前覆盖边界：只有 `GET /api/appointment/admin/page` 与 `GET /api/appeal/admin/page` 按驿站范围过滤；报表导出、报名记录、驿站后台分页等接口仍返回平台全域数据。

### 7.7 报表导出

操作方式与第 6.5 节一致。平台管理员与超级管理员可导出平台全域数据；驿站管理员虽然也能调用导出接口（后端 `@RequireRole` 含 `STATION_ADMIN`），但导出内容当前同样是平台全域数据，尚未按负责驿站过滤。

### 7.8 超级管理员补充说明

超级管理员拥有平台管理员的全部能力，并可在「账号管理」中调整任意账号的角色与启用状态。当前演示数据未预置超级管理员账号；如需演示，可由平台管理员在「账号管理」中为某个账号设置 `SUPER_ADMIN` 角色后重新登录。

## 九、常见问题

### 9.1 页面提示「无法连接服务端，请确认后端已启动（8080）」

原因：前端请求未到达后端，通常是后端未启动、端口被占用或代理配置不匹配。

处理：

1. 确认后端进程正在运行：访问 `http://127.0.0.1:8080/api/stat/overview`，应返回 JSON。
2. 若后端启动失败，检查控制台报错；数据库相关报错请确认是否误用了 `mysql` profile。
3. 开发模式下确认 `frontend/vite.config.mjs` 中的代理目标为 `http://127.0.0.1:8080`。
4. 静态服务方式下确认 `node scripts/serve-dist.mjs --api http://127.0.0.1:8080` 的 `--api` 参数正确。

### 9.2 接口返回 401（未登录或凭证失效）

1. 确认请求头携带 `Authorization: Bearer <token>`。
2. token 有效期为 120 分钟，过期后需重新登录或调用 `POST /api/auth/refresh` 刷新。
3. 浏览器中如出现 401，前端会自动清除本地 token 并跳回 `/login`。
4. 修改了 `app.security.jwt-secret` 后，此前签发的 token 全部失效，需要重新登录。

### 9.3 接口返回 403（当前角色无权执行此操作）

1. 确认当前登录账号的角色：普通用户不能访问 `/api/admin/users` 与导出接口。
2. 平台级功能（账号管理、角色权限）只允许 `PLATFORM_ADMIN` 与 `SUPER_ADMIN`（`AdminController` 方法级 `@RequireRole` 实际值）；驿站管理、服务项目管理、资讯公告管理、活动管理则同时允许 `STATION_ADMIN`。
3. 注意：前端隐藏标签页不等于后端放行，请以接口返回为准；如确需访问，请让平台管理员调整账号角色后重新登录。
4. 重新登录是必要的，因为前端角色取自登录响应并写入 `localStorage`。
5. 与 403 不同，**数据范围不产生 403**：驿站管理员调用 `/api/appointment/admin/page` 或 `/api/appeal/admin/page` 会正常返回 200，只是列表被限定在自己负责的驿站/区域内（范围内无数据时返回空列表与 `total=0`）；若需查看全量数据，请改用平台管理员账号。

### 9.4 MySQL 初始化后中文显示乱码

原因：Windows 控制台默认代码页为 936，mysql 客户端若按 GBK 解析 UTF-8 脚本会导致中文乱码。

处理：

1. 使用项目脚本初始化：`pwsh -File scripts/init-mysql.ps1 -Reset`，脚本已在公共参数中显式指定 `--default-character-set=utf8mb4`。
2. 手工执行 SQL 时，同样需要加上 `--default-character-set=utf8mb4`。
3. 初始化完成后检查脚本回读信息：「数据库字符集：utf8mb4」且 1 号驿站名称、1 号活动标题为正常中文。
4. 如已产生乱码数据，使用 `-Reset` 重建数据库后重新导入。

### 9.5 端口 8080 或 5174 被占用

1. 查看占用进程：

```powershell
netstat -ano | Select-String ":8080"
netstat -ano | Select-String ":5174"
```

2. 若为上一次未退出的进程，可用 `Stop-Process -Id <PID>` 结束；请先确认该 PID 确实是本项目进程。
3. 也可改用其他端口：后端用 `--server.port=8081` 启动，前端静态服务用 `node scripts/serve-dist.mjs --port 5180`；注意同步修改前端代理目标（开发模式在 `vite.config.mjs`，静态服务用 `--api` 指定后端地址）。
4. `frontend/vite.config.mjs` 设置了 `strictPort: true`，5174 被占用时 Vite 会直接报错退出，而不是自动切换端口。

### 9.6 前端构建或依赖相关提示

1. 首次运行需在 `frontend` 目录执行 `npm install`；出现依赖问题时删除 `node_modules` 后重新安装。
2. 构建产物缺失时，`node scripts/serve-dist.mjs` 会提示「未找到构建产物」，请先执行 `npm run build`。
3. 构建出现体积提示时，检查 `vite.config.mjs` 中的 `manualChunks` 分包配置（`vue`、`element`、`charts`）与 `chunkSizeWarningLimit`。
4. 执行 `npm test` 前无需启动后端；接口契约测试使用 mock，不发起真实网络请求。

### 9.7 执行 PowerShell 脚本报语法错误

1. 确认使用 UTF-8 BOM 保存的脚本版本（仓库内脚本已统一补 BOM，可同时被 PowerShell 5.1 与 7 正确解析）。
2. 如自行修改脚本，请保持 UTF-8 with BOM 编码。
3. 执行策略受限时，可用 `powershell -ExecutionPolicy Bypass -File <脚本路径>` 运行。

### 9.8 演示模式下重启后端后数据丢失

默认演示模式使用服务端内存存储，重启即清空。如需数据长期保留，请使用 MySQL 模式（第 4.2 节）。

### 9.9 地图上为什么没有驿站点位（或只有一部分）？

背景：**7 个城市的官方来源都没有公开的点位坐标数据集**，因此坐标改为**高德地图地理编码派生**：
先用驿站名称做 POI 搜索并做「区县一致性 + 名称相似度 + 地址相似度」校验，校验不通过回退详细地址地理编码，
再复核「行政区是否冲突」与「距城市中心是否超过 120 公里」。**目前大部分点位已经回填**：
全库 **1247/1344 条有坐标（93%）**，地图上可以正常标出点位。

如果地图上点位偏少或某条驿站没有标记，通常是下面几种情况（都属于如实标注的数据边界，不需要排查）：

1. **没有坐标的少量记录**：95 条因复核不合格被丢弃（84 条地理编码结果的行政区与来源标注不一致、
   11 条距城市中心超过 120 公里）、2 条未能定位，这些记录坐标保持为空，**系统不猜测、不编造**。
2. **地图不可用**：未配置高德 JS API Key、脚本加载失败或离线时，地图会显示「地图暂时不可用」的降级提示，此时不会打点。
3. **当前城市范围内本来没有带坐标的记录**：地图按所选城市过滤，切换到别的城市即可看到该城市的点位。

处理：点位是**派生坐标、误差可达数百米，只用于地图展示与就近参考，不能当作精确位置**。需要精确定位时，
请在驿站详情中使用**「导航：在高德地图中搜索该驿站」**外链（关键词为「驿站名称 + 地址」，在新窗口打开高德地图搜索页），
或走驿站所属官方渠道核实。若后续拿到可公开的**来源坐标**，可直接导入 `longitude` / `latitude` 两列并把
`geocode_source` 置空，地图会自动使用来源坐标打点，前端无需改动。

### 9.10 为什么不直接用来源给的坐标？

原因：**7 个城市的公开来源（政府公告、工会与媒体发布的名录）本身都没有提供点位经纬度**，
逐条来源里只有名称、地址、区域（部分还有电话与开放时间），因此不存在「来源坐标」可以直接用。

处理：系统只能通过**高德地图地理编码派生**坐标，并且必须如实处理这种派生数据：
`geocode_source`（`AMAP_POI` / `AMAP_GEOCODE`）与 `geocode_at` 两列单独记录坐标来源与时间，
**不参与 `data_status` 判定**（`data_status` 只回答「字段能否从公开来源逐条核对」），
每条记录的 `data_note` 会追加「坐标为高德地图地理编码派生，非来源给出」，
复核不合格的还会追加「坐标已丢弃：<原因>」。这样使用者一眼能分清「来源给的事实」与「系统派生的推测」。

### 9.11 切换城市后首页统计数字为什么没变？

原因：**目前只有「驿站查询」与首页地图按城市过滤，统计指标仍是全平台汇总口径**。首页的 6 张指标卡片
（驿站点位（全平台）、预约总量、诉求总量、诉求办结率、活动报名、服务评价均分）与月度趋势、报表导出都来自同一套
全平台聚合结果，页面提示条已标注「驿站点位（全平台）」与「为全平台汇总」。

处理：这是当前版本的已知口径边界，不是缓存问题。若要观察城市维度的数据变化，请查看「驿站查询」列表的
总数与区域分布（这些会随城市变化）。

### 9.12 为什么有的驿站没有营业时间或电话？营业时间到底以谁为准？

原因：驿站的**营业时间以高德为准、电话靠高德补空**，而**高德的覆盖率本来就不高**：全库 1344 条中，高德提供
**营业时间 386 条**（其余 760 条只能回退来源文本）、**电话 408 条**。高德没有给出、来源也没有写的字段，系统就**没有可填的值**。

**本轮口径（重要）**：**营业时间以高德为准，高德没有给出具体营业时间时才回退来源文本**；**联系电话为来源优先、高德补空**
（公开来源完全不提供电话，所以 408 条电话全部来自高德）。实测：高德给出营业时间 **386 条**，其中 **227 条覆盖了来源原值**；
未提供的 **760 条**回退来源文本，合并后全库**有营业时间 1146 条**、仍有 **198 条**没有营业时间。

处理：

1. 这是**如实标注的数据边界，不是缺陷**：没有数据的字段在界面上显示「开放时间待核验」「联系方式待核验」，
   **系统不做推测填充、不编造**，也不把附近商铺的营业时间硬套到驿站上。
2. **营业时间以高德为准、来源兜底**：高德有营业时间就用高德值（`business_source=AMAP_POI`），
   并在 `data_note` 中写「营业时间以高德地图为准（第三方数据）」；**覆盖了来源原值时**还会保留
   「来源原文的开放时间为「…」」以便回查。高德没有营业时间时用来源文本（`SOURCE` 或 `SOURCE+AMAP_POI`）。
   例如「大悦城小哥驿站」来源写「每日 8:30-22:00」、高德给的是商场时间「10:00-22:00」，系统**取高德的 10:00-22:00**，
   来源原文仅作留痕（这与上一轮文档里写的「保留来源值」**正好相反**，本轮已按实际数据改正）。
   `business_source` 的四种取值与实测分布：`AMAP_POI` 386 条 / `SOURCE+AMAP_POI` 178 条 / `SOURCE` 604 条 /
   `AMAP_POI+SOURCE` 0 条（公开来源不提供电话，因此不存在「电话来自来源」的情形）。
3. 想自己补数据时：配置 Web 服务 Key 后执行 `node scripts/sync-station-business.mjs`（增量）/ `--refresh`（全量），
   结果写入入仓的 `data/station-business.json`，再由 `node scripts/generate-station-data.mjs` 合并（见第 4.5 节）；
   也可以直接在管理端「驿站管理」里手工修改该驿站的开放时间与联系电话。
4. 注意：高德的营业时间与电话属于**第三方数据**（商户认领与用户上报），**不是驿站官方提供的**，
   可能过期或与实际不符，使用前宜再核实。

### 9.13 预约时提示「不在该驿站的营业时间内」怎么办？

原因：预约时段**必须完整落在所选驿站的营业时间内**，这是后端的固定校验规则
（`common/BusinessHours.java`，内存与 MySQL 两套实现一致）。例如驿站营业时间是「每日 8:30-22:00」，
提交 `22:00-23:00` 就会返回 **HTTP 400**，提示「所选时段 22:00-23:00 不在该驿站的营业时间内（每日 8:30-22:00）」。

处理：

1. 改选一个落在开放时间内的时段，再重新提交（营业时间见驿站详情的**营业信息**一行，旁边有来源标签）。
2. 如果营业时间是分段的（如 `09:00-12:00 14:00-18:00`），**午休时段不算营业**，跨越中午的时段（如 `11:00-15:00`）
   也会被拒绝，请分别选上午段或下午段。
3. 「24 小时营业」「24 小时开放」「全天」的驿站不受时段限制（如「钱江苑小哥驿站」预约 `23:00-23:30` 可通过）。
4. **兜底原则**：如果该驿站**没有营业时间**、营业时间**无法解析**，或填写的**时段文本本身无法解析**，
   系统**放行、不拦截**（判断不了就不挡，避免因数据缺失误拒正常预约）。所以并不是每个驿站的预约都会被这条规则约束。
5. 如果确有业务需要在营业时间外提供服务，请由管理员在「驿站管理」中把该驿站的开放时间改成包含该时段的写法，
   而不是绕过校验。

### 9.14 服务项目（饮水 / 充电 / 热饭等）能不能从高德同步？

**不能。** 高德 POI **没有**「服务设施」这类结构化字段——它的 `type` / `tag` 只是「生活服务 / 政府机构」
这种**粗分类**，无法据此判断某个驿站有没有饮水、充电、热饭、休息区等具体服务，因此**服务项目只能来自公开来源文本**。

处理：

1. 界面上的**服务设施**区块是弱化展示的虚线区块，标题旁直接注明「**来自公开来源文本，高德地图未提供该字段**」；
   来源没有逐条给出的显示「来源未逐条给出服务设施」，系统不做猜测。
2. 全库服务项目共 **6413 条，全部来自公开来源文本**（`PARTIAL` 记录的服务设施是来源对该批驿站的统一描述，未逐站核实）。
3. 需要补服务项目时，请走管理端「服务项目管理」手工新增，或在数据生成前补充来源文本；
   高德同步只解决营业时间（`open_time`）与电话（`tel`）两项，不会带来服务设施字段。
4. 同理，高德也**不提供**「此刻是否营业」的实时状态字段：因此系统**不声称**自己有第三方实时营业数据。
   界面上的「营业中 / 已打烊 / 营业时间待核验」是前端按**营业时间文本 + 当前时间**本地推算的**展示值**
   （每分钟刷新，见 5.3 第 10 条与 9.15 / 9.16）；**预约时段是否放行以后端 `common/BusinessHours.java` 为准**，
   前端只负责展示。

### 9.15 为什么有的驿站显示「已打烊」？

原因：营业状态是**按当前时间与该驿站的营业时间实时判断**的（前端 `frontend/src/utils/business-hours.js`），
分三态：「营业中」（绿）、「已打烊」（橙）、「营业时间待核验」（灰），并且**每分钟自动刷新一次**。
因此凌晨或营业时间结束之后再打开页面，营业时间为 `10:00-22:00` 的驿站自然会显示「已打烊」。

处理：

1. **这是正确行为，不是故障**：本轮修复的缺陷 BUG-19 正是「营业时间已过仍显示营业中」——原先标签直接取来源的静态
   `status` 字段（全库都是 `OPEN`），系统从不按时间判断，所以半夜也显示「营业中」，会让人跑空。
2. 判断依据是该驿站的**营业时间文本**（高德优先、来源兜底）与**你电脑上的当前时间**；
   如果本机系统时间不正确，标签也会跟着不准，请先校准系统时间。
3. 若驿站确实 24 小时开放，营业时间文本会写成「24 小时营业 / 24 小时开放 / 全天」，此时任意时刻都显示「营业中」。
4. 说明：该状态是**推算出来的展示值**，营业时间本身是第三方/来源文本、可能过期，也可能有临时闭馆与节假日调整，
   因此**不能当作驿站此刻确实开门的证明**；预约能否通过仍由后端按营业时间校验（见 5.6 与 9.13）。

### 9.16 为什么有的驿站显示「营业时间待核验」？

原因：该驿站**没有营业时间**（全库 198 条没有营业时间，其中 176 条连电话也没有），或者营业时间文本**无法解析**
（例如「预计10月底正式对外开放」「周一至周日7:00--24:00」这类双连接符写法）。

处理：

1. **这是有意为之的诚实显示**：无法判断时显示「营业时间待核验」（灰色），**绝不显示「营业中」**——
   数据缺失时猜测「营业中」会把用户引到已打烊的点位。
2. 想看该驿站到底有没有营业时间，请打开详情面板的**营业信息**一行：显示「开放时间待核验」即表示没有可用的营业时间。
3. 需要补数据时按 9.12 第 3 条处理（重新同步高德，或在管理端「驿站管理」手工填写开放时间）。
4. 注意：这类驿站在**预约时段校验上是放行的**（后端「判断不了就不挡」，见 9.13 第 4 条），
   即「营业时间待核验」只影响展示，不会导致预约被拒。

### 9.17 消息都标已读了，铃铛上的数字怎么还不消失？

原因：这是**已修复的缺陷（BUG-20）**。修复前，消息列表与已读状态只存在于消息中心组件内部，
而顶栏铃铛角标另按「待处理预约 + 待处理诉求」算一套，两者毫无关联，所以点了「全部标为已读」角标依旧挂着。

处理：

1. 现在两处**读同一份数据**（`frontend/src/stores/message.js`）：角标数字必然等于消息中心的未读条数，
   点击「全部标为已读」后未读行变为 0、按钮变为「已全部读完」，角标同步清零。
2. 如果角标与列表数字**对不上**，请先确认是不是在另一台设备/另一个浏览器上操作的——已读状态保存在本机浏览器
   `localStorage`（键名 `friendly_station_read_messages`），**不跨设备同步**。
3. 消息条数会随业务记录变化：提交新的预约、诉求或活动报名后会出现新的未读消息，角标随之增加（重复刷新不会重复计数）。
4. 若数字仍然异常，请清空该站点的浏览器数据后重新登录以排除本地缓存问题。

### 9.18 首页「服务数据趋势」是空白的？

原因：这是**已修复的缺陷（BUG-21）**的表现之一。数据库/内存刚初始化时，近 6 个自然月的预约、诉求、报名都是 0，
ECharts 的坐标轴会退化成 `0~0`，画面上几乎什么都不显示，看起来像图表坏了。

处理：

1. 现在数据全为 0 时**不再初始化图表**，而是显示明确的空状态说明：「还没有可统计的服务数据」
   （附「平台尚无预约、诉求或报名记录。产生业务数据后，这里会按自然月自动聚合。」），**不再出现空白坐标轴**。
2. 产生业务数据（提交预约、诉求或活动报名）后重新进入首页，图表会自动出图，无需额外操作。
3. 某个月没有诉求时，该月**办结率断线**而不是显示 `0%`，避免被误读为「办了 0%」；悬停 tooltip 可查看每月数值。
4. 图表容器改用 `ResizeObserver` 适配侧栏折叠等宽度变化，折叠/展开侧栏后图表会自动重绘，不需要刷新页面。

### 9.19 政策资讯里为什么有些内容换个城市就看不到了？有些来源为什么被排除？

原因：政策与资讯按城市分发，规则是——**不限城市的条目在所有城市都可见，某城市的专属条目只在该城市可见**，
并且在该城市里排在最前面。所以切到别的城市时地方政策「消失」是**设计行为**，不是数据丢失：
国家层面政策与全国性平台规则（`city_code` 为空，界面上标「全国」）在任何城市都能看到。

处理：

1. 想看某地的地方政策，请先在顶栏把城市切到该地（平台目前只覆盖 **7 个城市**：杭州、北京、上海、深圳、广州、成都、武汉）。
2. 想按来源区分，用「来源筛选」的**全部 / 官方 / 平台**；想只看某个平台的动态，用**平台下拉**（共 12 个平台）。
   注意平台下拉与来源筛选不是同一维度：官方媒体转述某平台举措时来源仍是「官方」，但平台筛选能命中它。
3. **被排除的 10 条是有意排除的**，逐条原因见 [政策资讯来源](政策资讯来源.md) 第三节：
   6 条**未能打开页面核实**（超时 / 412 反爬 / 重定向次数过多），4 条**城市不在平台覆盖范围**（南京 3、珠海 1）。
   后 4 条即使写进数据库也**不会在任何城市显示**（`city_code` 非空且不属于已覆盖的 7 个城市），因此按口径直接排除。
   **排除不等于内容不存在或不实**，只是本项目未能核实或不在覆盖范围内。
4. 若要补充条目：编辑 `data/policy-sources.json`（务必**先打开页面核实**并在 `note` 中写明核实方式与日期；
   打不开的条目放进 `unverified` 数组并注明失败原因），然后执行 `node scripts/generate-news-seed.mjs`
   重新生成 `db/news.sql` 与来源说明，再用 `pwsh -File scripts/init-mysql.ps1 -Reset` 重建导入。
5. **授权与解释边界**：系统只对公开来源做摘录与归类，**不声称已获发布方授权**，也**不对政策内容作解释**；
   具体执行以原文为准（每条都可点开原文链接核对）。

## 十、数据说明与边界

1. **数据来源（多城市口径）**：
   - **驿站名录来自 7 个城市公开发布的权威来源，共 1344 条**：杭州 267、北京 550、上海 36、深圳 117、
     广州 28、成都 172、武汉 174。每条记录保存 `city_code`、`source_name`、`source_url`、
     `source_published_at`、`verified_at`、`data_status`、`data_note`；数据文件为
     `backend/src/main/resources/db/stations.sql`（MySQL，含 `city` 表与 `station.city_code` 列）与
     `db/stations.json`（内存模式，同源）。逐城市来源清单与核对记录见 [驿站数据来源](驿站数据来源.md)，
     原始记录见 [station-sources.json](station-sources.json)。
   - **`data_status` 只表示「字段能否从来源逐条核对」**，不等于已实地核实，也不等于各城市驿站的完整清单。
     全平台 `VERIFIED` 682 条（名称、地址、区域、服务设施均可逐条核对）、`PARTIAL` 662 条（名称与地址来自
     来源名录，服务设施是来源对该批驿站的统一描述、未逐站核实）。
   - **各城市叫法不同**：杭州「小哥驿站 / 城管驿站」、北京「工会驿站 / 暖新驿站」、上海「户外职工爱心接力站」、
     深圳「暖蜂驿站」、成都「职工驿站」、武汉「临空港湾」等，系统按来源原文记录名称与类型，不统一改名。
   - **567 条记录未导入**：这些来源只给出驿站名称、没有详细地址（多为「最美驿站推荐名单」类公示），
     无法作为可用点位，保留在来源中供查证。
   - **部分名单来自官方图片表格**：深圳 105 条、武汉 132 条的来源名单以图片形式发布，由逐行读取还原，
     可信度略低于直接可复制的文本来源。
   - **坐标不是来源给出的，而是高德地图地理编码的派生结果**：7 个城市的来源都没有提供经纬度，
     因此坐标由 `scripts/geocode-stations.mjs` 通过高德 Web 服务回填（POI 名称匹配优先、否则详细地址地理编码），
     结果缓存在**入仓的** `data/station-geocode.json`，再由 `scripts/generate-station-data.mjs` 合并进数据文件。
     全库 **1247/1344 条有坐标（93%）**：POI 匹配 922 条 + 地址地理编码保留 325 条；**95 条因复核不合格被丢弃**
     （84 条「地理编码结果的行政区与来源标注不一致」、11 条「距城市中心超过 120 公里」）、2 条未能定位，
     这些记录坐标保持为空；另有 44 条缺失的所属行政区由地理编码补齐。坐标来源单独记在 `geocode_source` /
     `geocode_at`，**不参与 `data_status` 判定**，每条 `data_note` 会标注「坐标为高德地图地理编码派生，非来源给出」。
     **坐标只用于地图展示与就近参考，误差可达数百米（名称泛化的驿站、地址只到路口/社区级的记录尤甚），
     不能当作精确位置**；去重后 1170 个不同坐标点中有 51 个点被多条驿站共用（共涉及 128 条），
     它们通常本就在同一栋楼或院落，也可能是泛化名称匹配到了同一个高德 POI。联系电话的公开来源完全不提供、仅由高德补空（营业信息的来源与覆盖率见下一条）。
   - **营业信息（营业时间 / 联系电话）来源、优先级与覆盖率**：系统用 `scripts/sync-station-business.mjs` 通过高德 Web 服务同步
     `open_time` 与 `tel`，结果缓存在**入仓的** `data/station-business.json`，再由 `scripts/generate-station-data.mjs`
     合并进数据文件。**优先级（本轮口径）：营业时间以高德为准，高德未提供具体营业时间的驿站才回退来源文本；
     联系电话为来源优先、高德补空**。实测：高德提供营业时间 **386 条**（其中 **227 条**覆盖了来源原值，
     `data_note` 会保留「来源原文的开放时间为「…」」留痕）、提供电话 **408 条**；未提供营业时间的 **760 条**回退来源；
     合并后全库**有营业时间 1146 条**、**198 条没有**；**有电话 408 条且全部来自高德**（公开来源完全不提供电话）。
     可信匹配 **921 条**（三重校验通过）。
     来源单独记录在 **`business_source`** 与 **`business_synced_at`**（同步日期）两列，**不参与 `data_status` 判定**；
     `business_source` 四种取值与实测分布：`AMAP_POI` 386 条（营业时间与电话均来自高德）、`SOURCE+AMAP_POI` 178 条
     （营业时间来自来源、电话来自高德）、`SOURCE` 604 条、`AMAP_POI+SOURCE` 0 条（不存在「电话来自来源」的情形），
     另有 176 条两项都没有。`data_note` 中会写明「营业时间以高德地图为准（第三方数据）」
     「联系电话来自高德地图 POI（第三方数据），非来源给出」。**营业时间与电话属于第三方数据**
     （高德 POI 来自商户认领与用户上报，**不是驿站官方提供的**），**可能过期或与实际不符，使用前宜再核实**；
     同步只接受「区县一致性 + 名称相似度 + 地址相似度」三重校验通过的可信匹配，营业时间还要求形如
     `HH:mm-HH:mm` 或「24小时」，剔除明显不属于驿站的取值（例如把菜鸟驿站的营业时间误配回来）。
   - **高德不能提供什么（重要边界）**：高德 POI **没有**「服务设施」这类结构化字段（`type` / `tag` 只是
     「生活服务 / 政府机构」这种粗分类），所以饮水 / 充电 / 热饭等服务项目**仍然只能来自公开来源文本**
     （全库 6413 条服务项目全部来自公开来源）；高德也**没有**「此刻是否营业」的实时状态字段：界面上的营业状态是
     **前端按营业时间文本本地推算**的展示值（见 5.3 第 10 条与 9.15 / 9.16），**不是第三方实时状态**，
     **预约是否放行仍以后端校验为准**。**不得声称营业信息来自驿站官方，也不得声称高德提供服务设施或实时营业状态。**
   - **营业时间的行为边界（有意为之的兜底）**：预约提交时由 `common/BusinessHours.java` 校验时段是否落在营业时间内，
     营业时间外的时段返回 400 并给出中文提示；但**营业时间缺失或无法解析时不做拦截**（判断不了就不挡），
     避免因数据缺失误拒正常预约。因此**约束范围有限**：全库 1344 条中 **960 条（71%）的开放时间能解析出营业区间、
     真正参与时段校验**，其余 **384 条（29%）不受时段约束**（198 条没有开放时间、12 条开放时间无法解析、
     174 条为「24小时营业 / 全天」）；**不能宣称「所有预约都被营业时间覆盖」**。
   - **前端实时营业状态的边界**：驿站列表、详情与地图气泡上的「营业中 / 已打烊 / 营业时间待核验」由前端
     `utils/business-hours.js` 按**当前时间 + 营业时间文本**本地推算（每分钟自动刷新），依据就是高德或来源给出的
     **营业时间文本**，因此**可能与实际不符**（营业时间本身是第三方数据、可能过期；临时闭馆与节假日调整也无法反映）；
     **没有营业时间或文本无法解析时显示「营业时间待核验」**，不猜成「营业中」。该状态**只用于展示**，
     预约是否放行**以后端 `common/BusinessHours.java` 为准**（前端不参与校验）。
   - **「只显示已启用」筛选口径**：驿站查询的复选框按**服务端 `status` 字段**过滤（附加 `status=OPEN`），
     反映的是各来源发布时的状态（全库 1344 条均为 `OPEN`），**不是按当前时刻是否营业过滤**；
     「此刻是否营业」由每行的实时状态标签表达，两者含义不同。
   - 点位 `status` 统一记为 `OPEN`，反映的是**各来源发布时**的状态，**使用前必须重新核实**。
   - **演示账号与演示活动**：`backend/src/main/resources/db/data.sql` 提供 3 个演示账号与 2 场演示活动。
   - **政策与资讯来自真实公开来源**：94 条（官方 90 + 平台发布 4；不限城市 60 + 城市相关 34），
