## 一、演示环境准备

```powershell
# 1. 初始化数据库（仅首次或需要重置演示数据时执行）
powershell -ExecutionPolicy Bypass -File .\scripts\init-mysql.ps1 -User root -Password 你的密码 -Reset

# 2. 启动后端（MySQL 模式）
cd backend
$env:MYSQL_USER="root"; $env:MYSQL_PASSWORD="你的密码"
java -jar target\platform-0.0.1-SNAPSHOT.jar --spring.profiles.active=mysql

# 3. 启动前端（开发模式，或先 build 再用 scripts/serve-dist.mjs 提供静态站点）
cd ..\frontend
npm run dev
```

浏览器打开 `http://127.0.0.1:5174/`，使用 `platform_admin / password` 登录（管理端能力最完整）。

演示前建议先执行一次 `scripts/api-test.ps1`，确认 **14 组 132 项**接口断言全部通过，避免现场出现接口异常。

## 三、技术要点（用于回答"怎么实现的"）

| 主题 | 实现要点 | 可指出的代码位置 |
| --- | --- | --- |
| 双运行模式 | 同一套接口有两份实现：内存实现 `@Profile("!mysql")` 与 MySQL 实现 `@Profile("mysql")`，对外返回结构完全一致 | `backend/.../workflow/DemoWorkflowStore.java`、`MysqlWorkflowService.java` |
| 统一返回与异常 | `ApiResponse` 统一包装；`BusinessException` 由 `GlobalExceptionHandler` 转为 400 + 中文提示，未知路径返回 404 | `backend/.../common/` |
| 认证与权限 | JJWT 签发与解析 token，`AuthInterceptor` 依据 `@RequireRole` 校验角色，未登录 401、越权 403 | `backend/.../auth/` |
| 预约状态机 | `PENDING_STATION_CONFIRMATION → CONFIRMED / REJECTED / CANCELLED`，状态与标签集中在 `WorkflowStatus` | `backend/.../workflow/WorkflowStatus.java` |
| 诉求闭环 | `PENDING_ACCEPTANCE → ASSIGNED → PROCESSING → RESOLVED / CLOSED`，每次流转写入 `appeal_record` | `backend/.../workflow/MysqlWorkflowService.java` |
| 并发安全 | 状态变更使用带状态条件的 `UPDATE ... WHERE status = ?` 并检查影响行数；活动报名先对活动行加 `FOR UPDATE` 锁，再由唯一索引兜底 | `MysqlWorkflowService`、`activity_signup` 唯一键 |
| 统计口径 | 全部指标由数据库实时聚合，接口返回 `dataScope` / `dataStatus` / `generatedAt` 说明口径 | `backend/.../statistics/` |
| 前端接口层 | 按业务域拆分为 `src/api/*.js`（含 `city.js`），统一在 `http.js` 处理 token、401 跳转与中文错误 | `frontend/src/api/` |
| 多城市与定位 | `city` 表保存城市与中心点；`GET /api/city/list` 返回带驿站数的城市清单（首项为默认城市），`GET /api/city/nearest` 用 Haversine 距离判断定位所在城市；驿站查询与区域统计按 `cityCode` 过滤 | `backend/.../city/`、`backend/.../common/GeoUtils.java` |
| 前端真实地图 | Leaflet 1.9.4 + OpenStreetMap 瓦片，瓦片源按可用性排序并自动回退（主站在部分地区超时）；城市中心点变化时地图平滑移动，只有带经纬度的驿站才打点 | `frontend/src/components/StationMap.vue` |
| 前端分包 | `vue` / `element-plus` / `echarts` 拆分为独立 chunk，echarts 按需加载 | `frontend/vite.config.mjs` |

## 四、预期提问与回答要点

**1. 这些驿站数据是真实的吗？**
驿站名录来自 **7 个城市公开发布的权威来源**，是**真实的公开信息**，共 **1344 条**
（杭州 267、北京 550、上海 36、深圳 117、广州 28、成都 172、武汉 174），但**不等于已实地核实，也不等于完整清单**。
每条记录都保存了 `city_code`、来源名称、链接、发布日期与核对日期，页面上可以直接点开对照，
逐城市来源清单见 `docs/驿站数据来源.md`。
需要同时说明几项字段级与来源级差异：
① 全平台 `data_status` 为 `VERIFIED` 682 条、`PARTIAL` 662 条——`PARTIAL` 表示名称与地址来自来源名录，
服务设施是来源对该批驿站的**统一描述**、未逐站核实；
② **各城市叫法不同**（杭州「小哥驿站 / 城管驿站」、北京「工会驿站 / 暖新驿站」、上海「户外职工爱心接力站」、
深圳「暖蜂驿站」、成都「职工驿站」、武汉「临空港湾」等），系统按来源原文记录，不统一改名；
③ 有 **567 条**记录因来源只给名称、没有地址而**未导入系统**；
④ **所有城市都没有点位经纬度**，字段保持为空、没有用地址反推坐标；
⑤ 深圳 105 条、武汉 132 条来自官方发布的**图片表格**，属于从图片提取，可信度略低于文本来源。
除此之外的预约、诉求、报名、评价是系统运行记录，统计结论只针对系统内已记录数据。参见 `AUDIT_AND_EVIDENCE.md`。

**2. 首页的 18742 人次、95.2% 办结率是怎么来的？**
当前版本已经移除这些固定示例值。`/api/stat/overview` 返回的每一个指标都由数据库实时聚合，
并且在接口与页面上标注了数据口径（`dataScope`）与生成时间。

**3. 为什么地图上没有点位？**
因为**各城市官方都没有公开的点位坐标数据集**，1344 条名录里 `longitude` / `latitude` 全部为空，
系统没有用地址反推坐标（避免给出不可靠位置）。地图组件只对同时带经纬度的驿站打点，所以现在地图上
只有说明条、没有标记；导航改用驿站详情里的**「在高德地图中搜索该驿站」**外链（关键词是「驿站名称 + 地址」）。
如果之后拿到可公开的坐标，直接补 `longitude` / `latitude` 两列，地图就会自动开始打点，前端无需改动。

**4. 切换城市后统计为什么不变？**
这是当前版本的**已知口径边界**，不是缓存问题：目前只有「驿站查询」与首页地图按 `cityCode` 过滤，
统计指标仍是**全平台汇总**（首页已标注「驿站点位（全平台）」与「为全平台汇总」）。
要观察城市维度差异，请演示「驿站查询」的总数与区域下拉（会随城市变化）。
另外用户定位不在已覆盖的 7 个城市时，系统会回退到距离最近的已覆盖城市，**不会提示「未覆盖」**，这也是如实说明的边界。

**5. 为什么同时要内存实现和数据库实现？**
内存实现让系统在没有 MySQL 的环境下也能完整演示与联调，也便于前端独立开发；数据库实现用于
真实持久化。两者对外行为一致，接口回归脚本会在两套 Profile 下分别运行，驿站名录也共用同一份
`db/stations.json`。

**6. 并发下会不会重复报名、重复办结？**
不会。活动报名先对活动行加行锁 `SELECT ... FOR UPDATE`，串行化同一活动的报名，`activity_signup`
表对 `(activity_id, user_id)` 建唯一索引兜底；预约审核与诉求处理改为带状态条件的 `UPDATE`，
只有符合当前状态的记录会被更新。`scripts/perf-test.mjs` 用 10 并发验证过：报名、审核、办结
都只成功一次。

**7. 角色权限是怎么控制的？**
两层：前端按 `roleCode` 隐藏不可见的管理标签页（仅体验优化），后端在控制器方法或类上使用
`@RequireRole`，由 `AuthInterceptor` 校验，越权返回 403。除此之外还有数据范围：`DataScopeService`
按 `station.manager_id` 解析驿站管理员负责的驿站，预约按负责驿站过滤、诉求按负责驿站所在区域过滤。
测试用例覆盖了普通用户访问管理端、驿站管理员访问账号管理、跨驿站数据可见性等场景。

**8. 1344 条数据下前端会不会一次全拉下来？**
不会。驿站查询改成了服务端分页与筛选：每页 12 条、按当前城市（顶栏城市选择器）传 `cityCode`，
区域下拉来自 `/api/station/areas?cityCode=...`（带各区数量、只统计当前城市），
服务类型作为 `service` 参数、营业状态作为 `status` 参数传给后端，搜索也是服务端执行。
已知限制是服务预约、服务评价、收藏三处的驿站下拉仍只取前 50 条；管理端驿站管理列表也未提供城市筛选。

**9. 为什么用 MyBatis-Plus 而不是 JPA？**
项目对分页、条件查询与 SQL 可控性要求较高，MyBatis-Plus 提供 `LambdaQueryWrapper` 与分页插件，
既避免大量 XML，又能直接控制生成的 SQL（例如本次并发修复需要的条件更新与 `FOR UPDATE`）。

**10. 系统的局限是什么？**
驿站名录虽来自 7 个城市的公开来源（1344 条），但**未实地核实、不等于完整清单，有 567 条因缺地址未导入，
且所有城市都没有点位坐标**，点位是否持续开放需重新核实；多城市支持目前**只覆盖驿站查询与地图，
统计指标仍是全平台口径**；用户定位不在已覆盖城市时会回退到最近城市、不提示「未覆盖」；
未做生产级安全渗透测试与多实例分布式并发验证；数据量仍远小于真实业务规模，
索引与查询计划未在真实数据量下评估；诉求的数据范围按区域近似；
消息中心是基于业务记录派生的，没有独立的消息表与推送通道。

- **1344 条不等于各城市驿站的完整清单。**

## 七、多城市与用户城市判断（建议在上一节之后讲）

1. **平台已从「杭州单城市」升级为「全国多城市平台」**：覆盖 7 个城市、1344 条名录，顶栏可按城市切换；
   不同城市对同类驿站的叫法不同，系统按来源原文记录（见上一节）。
2. **数据层**：新增 `city` 表（`city_code`、`city_name`、`province`、`center_lng`、`center_lat`、
   `status`、`sort_no`），`station` 表新增 `city_code` 列与索引 `idx_station_city`；
   两个**公开接口**（无需 token）支撑城市选择与定位判断：
   - `GET /api/city/list` → `[{ cityCode, cityName, province, centerLng, centerLat, stationCount }]`，
     按 `sortNo` 升序，**第一项就是平台默认城市（杭州 330100）**；
   - `GET /api/city/nearest?lng=&lat=` → 单个城市对象或 `null`（Haversine 距离取最近）。
   同时 `GET /api/station/page`、`/api/station/nearby`、`/api/station/admin/page`、`/api/station/areas`
   都新增了 `cityCode` 参数，`StationDto` 新增 `cityCode`、`longitude`、`latitude`。
3. **用户城市四级判定顺序（定位优先）**：
   ① `localStorage`（键 `friendly_station_city_code`）里有用户**手动**选过、且仍在城市列表里的城市 →
   直接使用、**不再请求定位**；② 否则请求浏览器定位（`navigator.geolocation`，超时 8000ms），
   成功后调用 `/api/city/nearest` 取最近城市；③ 定位被拒绝 / 超时 / 失败 / 返回 `null` →
   回退到城市列表第一项（平台默认城市杭州）；④ 城市列表为空 → 保持空城市，只提示不渲染地图。
   全程 `try/catch` 静默兜底，不阻塞页面；用户可以随时在顶栏手动切换，手动选择会被记住。
4. **地图用 Leaflet 1.9.4 + OpenStreetMap 瓦片**（`frontend/src/components/StationMap.vue`）：
   地图中心为所选城市中心点、切换城市时平滑移动；只有带经纬度的驿站才打点（当前都没有坐标，
   因此显示说明条）；瓦片源做了**自动回退**——实测部分地区访问主站 `tile.openstreetmap.org` 会超时，
   因此优先使用 `tile.openstreetmap.de`，连续失败再切回主站，避免地图一片空白。
5. **必须主动说明的边界**：
   - 所有城市都没有点位坐标，地图标不出具体点位（没有用地址反推坐标）；
   - 567 条记录因缺地址未导入；
   - 深圳 105 条、武汉 132 条来自官方图片表格，可信度略低；
   - **统计指标仍是全平台口径，只有驿站查询与地图按城市过滤**（首页已标注）；
   - 用户定位不在已覆盖城市时回退到最近城市，不提示「未覆盖」。

## 八、权限与数据范围的现场演示建议

如果评委追问"驿站管理员到底能看多少数据"，可以现场切换演示：

1. 用 `platform_admin` 登录 → 管理端「预约审核」，记录列表总数。
2. 退出后改用 `station_admin_01` 登录 → 同一页面，列表只包含 **1~4 号驿站**（演示配置中
   `station.manager_id = 2` 的四家「小哥驿站」）的预约；「诉求处理」也只包含这几家驿站所在区域
   （上城区、拱墅区、西湖区）的诉求（`appeal` 表没有 `station_id`，按负责驿站所在区域近似）。
   > 注意：**这是杭州的演示配置**——1~4 号驿站都是杭州的「小哥驿站」，在多城市名录下该配置保持不变。
3. 用 `rider_xiaowang` 登录 → 「我的诉求」只返回本人提交的诉求。

对应实现：`DataScopeService` 解析负责驿站，`AppointmentController` / `AppealController` 的
`/admin/page` 把范围传入 `WorkflowService`。

需要如实说明的范围边界：数据范围目前只覆盖预约与诉求两个后台列表接口，
报表导出、报名记录、驿站后台分页与评价分页**没有**按驿站过滤，仍是平台全域数据。

## 九、活动模块：承办方与报名闭环（本轮新增，建议现场演示）

这个模块最能体现"平台不是简单地把信息聚在一起"，建议花 2 分钟走一遍。

### 1. 承办方分三类，第三类只做跳转

| 承办方 | 卡片标签 | 站内报名 | 界面表现 |
| --- | --- | --- | --- |
| 驿站 | 驿站 | ✅ | 「立即报名」+ 已报名 N / 上限 |
| 平台管理员 | 平台管理员 | ✅ | 同上 |
| 第三方机构 | 第三方机构 | ❌ | 「前往报名 ↗」+「由第三方机构举办，报名请前往来源页面」 |

**为什么第三方活动不做站内报名**（这是评委可能追问的点）：报名与审核都在对方平台进行，
我们既不掌握名单，也无法替对方联系报名人。在站内收下报名却没人能处理，比不收更糟。
因此创建第三方活动时**必须填 http(s) 链接**，否则报 400；反过来，非第三方活动**不接受外部链接**，
避免出现两套报名入口。

### 2. 站内报名必须填联系信息

点「立即报名」不是一键完成，而是弹出表单：**姓名、联系电话必填，备注选填**
（姓名与电话会默认带出个人中心已有信息）。

理由是这条链路的本质：驿站要**联系到人**才能确认时间与安排。
只存一条"某用户报名了"的记录，驿站拿不到联系方式，报名就落不了地。

### 3. 承办方处理与反馈

管理端「报名记录」列出报名人姓名、电话（可点击直接拨号）、备注、状态、审核反馈，
操作列「联系与审核」可标记 **已联系 / 审核通过 / 审核未通过** 并填写给报名人的反馈。

**审核未通过必须填写原因**，否则 400——报名人有权知道为什么。

### 4. 反馈回到报名人（关键，别漏）

用户端「活动报名」→「查看我的报名」，逐条显示报名状态与**承办方的回复**：

```
驿站冬季送温暖·免费理发                    [审核通过]
报名时间：2026-10-14 05:56:05
┃ 平台管理员的回复：已电话确认，周六上午 9 点在驿站集合，记得带身份证
```

尚未处理的显示「承办方还没有回复，可留意电话或消息」，不留空。

**这一步最容易被忽略**：如果只做到承办方能写反馈、而用户看不到，前面所有环节都白做。
接口回归里专门有断言 `我的报名能看到审核反馈` 守住这一点。

### 5. 顺带展示：管理员不是用户

用管理员账号登录，侧栏只有 6 项（首页 / 管理工作台 / 驿站查询 / 政策资讯 / 消息中心 / 个人中心），
**没有**服务预约、我的诉求、活动报名、服务评价、我的收藏；首页次要区是「待审核预约 / 待处理诉求」
两个待办卡片，而不是「我的预约 / 我的诉求进度」。

原因很直接：管理员是提供服务与处理诉求的一方，让他报名自己办的活动、给自己驿站写评价没有意义，
也会让权限边界变得含糊。切回 `rider_xiaowang` 即恢复完整用户侧栏，对比一目了然。
