## 编写说明

### 一、编写依据

本说明书以**开题报告**与**中期报告**为基点，逐条对照**程序实际实现**整理，三者的优先级关系如下：

| 优先级 | 依据 | 作用 |
| --- | --- | --- |
| 1（基点） | 开题报告《基于SpringBoot+Vue的新就业群体驿站服务平台设计与实现》——7 个模块、21 项功能 | 决定功能分类骨架，保证说明书与开题范围一致 |
| 2（基点） | 中期报告——普通用户 / 驿站管理员 / 平台管理员 三类角色、7 个模块 | 决定「三端」划分与角色职责边界 |
| 3（事实） | 程序实际实现（后端控制器与 `@RequireRole`、数据库 `schema.sql`、前端页面与接口封装、`docs/接口文档.md`） | 决定每个功能的真实玩法与规则，凡文档与代码不一致处一律以代码为准并另行标注 |

**核心结论**：开题报告提出的 **7 个模块、21 项功能全部有对应的程序实现**；中期报告提出的**三类角色**在代码中落地为 **4 个角色编码**（`USER` / `STATION_ADMIN` / `PLATFORM_ADMIN` / `SUPER_ADMIN`），其中 `SUPER_ADMIN` 与 `PLATFORM_ADMIN` 共用同一套界面，差异只在账号与角色管理范围。

### 二、三个端的划分与角色映射

| 端 | 角色编码 | 角色名称 | 演示账号 | 进入方式 |
| --- | --- | --- | --- | --- |
| **用户端** | `USER` | 普通用户（新就业群体） | `rider_xiaowang` | 登录后进入首页工作台 `/` |
| **驿站端** | `STATION_ADMIN` | 驿站管理员 | `station_admin_01` | 登录后点「管理工作台」进入 `/admin` |
| **管理员端** | `PLATFORM_ADMIN` / `SUPER_ADMIN` | 平台管理员 / 超级管理员 | `platform_admin` | 登录后进入 `/admin`，可见全部 11 个标签页 |

演示账号密码均为 `password`；生产配置下不会自动创建演示账号。

三个端的相互关系可以概括为一句话：**用户端提需求、驿站端办本驿站的事、管理员端管全局并督办闭环**。

- **用户端**：提交预约、提交诉求、报名活动、评价服务，是全部业务数据的起点。
- **驿站端**：只处理「本驿站」范围的事——预约按**驿站**过滤，诉求按**驿站所在区域**过滤。
- **管理员端**：维护驿站与服务项目、分派与督办诉求、管理资讯公告与活动、管理账号与角色、导出全平台报表。

### 三、标注约定

为了让说明书既能用于论文与答辩，又不夸大实现程度，全文使用以下标注：

| 标注 | 含义 |
| --- | --- |
| 【已实现】 | 前后端均有代码，可在系统中实际点通 |
| 【已实现·前端未开放】 | 后端接口已实现并放行该角色，但前端界面未对该角色开放入口 |
| 【设计延伸·待实现】 | 属于业务玩法设计，程序当前**没有**对应表结构与接口，答辩时须如实说明 |
| 【数据边界】 | 涉及数据来源与可信度的说明，不可作为结论性成绩表述 |

### 四、数据边界声明（重要）

本说明书描述的是**功能与规则**，不等于业务成效。引用时须遵守以下边界：

- 驿站名录共 **1344 条、覆盖 7 个城市**（北京 550、杭州 267、武汉 174、成都 172、深圳 117、上海 36、广州 28），逐条记录来源名称、链接、发布日期与核对日期；`data_status` 分 `VERIFIED`（可逐条核对）/ `PARTIAL`（部分字段为批次级描述）/ `MANUAL`（后台录入）三档。
- 7 个城市的公开来源**均未提供点位坐标**，坐标由高德地图地理编码派生（1247/1344，93%），以 `geocode_source` / `geocode_at` 单独记录、**不参与 `data_status` 判定**，误差可达数百米。
- 营业时间与联系电话为**第三方数据**（高德同步），合并后 1146 条有营业时间、408 条有电话；**没有营业时间时界面显示「营业时间待核验」，绝不显示「营业中」**。
- 服务设施（饮水/充电/热饭等）**全部来自公开来源文本**（共 6413 条服务项目记录），高德地图不提供该结构化字段。
- 演示账号、演示活动，以及预约、诉求、报名、评价等运行时数据均为**演示内容**；统计指标是「对系统内已记录数据」的实时聚合，**不代表真实业务成效**。
- 不得声称：已完成实地核实、是所在城市的完整清单、点位当前仍开放、坐标精确、已完成生产级安全审计或大规模并发验证。

# 第 1 章 用户端（普通用户 USER）

## 1.1 用户端定位与使用方式【已实现】

**功能定位**：用户端是外卖骑手、快递员、网约车司机等新就业群体使用的一侧，解决「附近有哪些友好驿站、能提供什么服务、有事怎么提前联系、遇到问题怎么反映、反映后办到哪一步」五个问题。

**玩法（怎么用）**：

1. 打开系统 → 进入登录页 → 用账号密码登录，或直接点三个演示账号按钮中的一个。
2. 登录成功后进入**首页工作台**，左侧是 11 个模块的侧栏入口，顶栏可切换城市、看未读消息角标、进个人中心。
3. 首页给出 6 张平台指标卡、附近驿站地图与列表、我的预约、我的诉求进度、政策资讯与近 6 个月趋势图。
4. 点侧栏任一模块即在首页右侧区域切换到该模块（用户端模块**不是独立页面**，而是首页内的视图切换）。

**规则**：

- 用户端的 11 个模块全部需要登录，未登录访问会跳转 `/login?redirect=<原地址>`，登录后自动回到原地址。
- 用户端接口共 36 个（22 个公开 + 14 个登录后业务接口）。越权、未登录分别返回 401 / 403，前端统一提示后端返回的中文消息。
- 用户角色不能进入管理工作台：路由守卫判定角色不在 `STATION_ADMIN / PLATFORM_ADMIN / SUPER_ADMIN` 时直接跳回首页。

**对应开题功能点**：为模块一至模块六提供用户侧入口。

## 1.2 用户注册与登录【已实现】

**玩法**：

- 登录页提供账号、密码两个输入框，密码可切换明文显示，支持回车提交。
- 页面内置**三个演示账号快捷按钮**：普通用户 `rider_xiaowang`（浏览服务）、驿站管理员 `station_admin_01`（管理驿站）、平台管理员 `platform_admin`（运营工作台）；点击即填入账号与固定密码 `password`，当前选中的按钮高亮。
- 登录成功后写入本地会话（token 与角色），按角色映射中文角色名：`USER→普通用户`、`STATION_ADMIN→驿站管理员`、`PLATFORM_ADMIN→平台管理员`、`SUPER_ADMIN→超级管理员`（未知角色回落「普通用户」）。

**规则**：

- **必填校验**：账号或密码为空 → 「请输入用户名和密码」。
- **凭证校验**：登录接口未返回 token → 本地报「登录接口未返回有效凭证」。
- **失败提示**：后端未启动 → 「无法连接服务端，请确认后端已启动（8080）」；凭据失效（401）→ 「登录凭证已失效，请重新登录」；其他 → 展示后端返回的中文消息或「登录服务暂时不可用，请稍后重试」。
- **会话策略**：任意请求返回 401 时，前端自动清除本地 token 与角色并整页跳回登录页。
- **注册说明**：后端已提供 `POST /api/auth/register`（用户名 + 手机号 + 密码，注册为普通用户），但**前端当前没有注册页面与调用入口**，属【已实现·前端未开放】；演示与答辩均以三个演示账号登录。

**对应开题功能点**：用户注册与登录功能。

## 1.3 个人中心（个人信息维护）【已实现】

**玩法**：侧栏「个人中心」→ 查看并修改本人资料 → 点保存。

**表单字段与规则**：

| 字段 | 控件 | 规则 |
| --- | --- | --- |
| 账号 | 只读文本 | 取自当前登录账号，不可修改 |
| 姓名 | 输入框 | 可改，前端无长度校验 |
| 手机号 | 输入框 | 可改，**前端未做手机号格式校验** |
| 职业类型 | 下拉 5 项 | 外卖骑手 / 快递员 / 网约车司机 / 驿站管理员 / 平台管理员 |
| 所属区域 | 下拉 | 取自当前城市的区域分布统计，兜底「全部区域」 |
| 角色 | 只读标签 | 显示当前角色中文名 |

- 保存成功提示「个人资料已保存」，并同步更新顶栏显示的姓名。
- 主按钮「刷新资料」→ 「资料已刷新」（重新拉取本人资料）。
- 用户端**只能修改自己的资料**；修改他人资料、启停他人账号属于管理员端能力。

**对应开题功能点**：个人信息维护功能。

## 1.4 首页工作台【已实现】

**玩法**：登录后的默认落地页，一屏看完平台概况、附近驿站、我的待办与最新资讯。

**页面构成与规则**：

1. **顶栏**
   - 侧栏折叠按钮；城市下拉（显示为「城市名（驿站数）」）；「管理工作台」按钮（仅管理角色可见）；未读消息铃铛（`:max="99"`，无未读时隐藏）；角色标签；头像下拉（个人中心 / 刷新数据 / 退出登录）。
   - **全局搜索框**：占位文案为「搜索驿站、服务、政策、资讯等」；【数据边界】该搜索框**实际只过滤首页「我的诉求进度」列表**（按诉求标题或状态匹配），不影响驿站列表、资讯或地图。
   - 定位未覆盖时会显示「未覆盖」提示标签，悬停显示降级说明（见 1.16）。
2. **数据提示条**：显示数据状态与口径，原文形如
   `当前城市：杭州（驿站查询与地图按该城市过滤）；统计口径：本系统数据库当前记录，为全平台汇总；生成时间 …。指标均为后端实时聚合结果。`
3. **6 张指标卡**（顺序固定，窄屏自动折行）

   | 指标卡 | 取值 | 副说明 |
   | --- | --- | --- |
   | 驿站点位 | 全平台驿站总数 | 全平台营业中 N 个 |
   | 预约总量 | 预约总条数 | 近 30 天 N 条 |
   | 诉求总量 | 诉求总件数 | 待处理 N 件 |
   | 诉求办结率 | 百分比（保留 1 位小数） | 已办结 N 件 |
   | 活动报名 | 报名总人次 | 活动 N 场 |
   | 服务评价均分 | 平均分 / 5 | 评价 N 条 |

   【数据边界】六张卡为**全平台口径**，不随顶栏城市切换而变化；驿站查询与地图才按城市过滤。
4. **友好驿站点位地图 + 附近驿站列表**
   - 地图标题副文案：有定位时「{城市} · 已标注 N 个点位 · 共 N 个 · 按离你最近排序」，无定位时「共 N 个 · 未获得定位，按平台顺序」。
   - 列表每行：驿站名称、距离（有定位时按 Haversine 计算，保留 1 位小数并升序）、营业状态标签、开放时间、两个按钮「地图定位」「提前联系」。
   - 「地图定位」→ 地图定位到该驿站；连续点击同一驿站也会重新触发定位。
   - **「提前联系」→ 直接跳到「服务预约」模块并自动选中该驿站、弹出预约表单**，这是首页到预约的最短路径。
5. **三个次要列表（各取前 5 条）**
   - 我的预约：服务事项、驿站、日期、状态标签；空态「暂无预约记录」。
   - 我的诉求进度：诉求标题 + 状态标签；空态「还没有提交过诉求」。
   - 政策资讯：资讯（取 4 条）与公告（取 3 条）合并按日期倒序取 5 条；空态「暂无资讯」。
6. **服务数据趋势图（近 6 个自然月）**
   - **默认收起**，点「展开」后绘制；可点「刷新」重取。
   - 系列：预约量（柱）、诉求量（柱）、办结率（折线，右轴 0~100%）；某月无诉求时办结率断线（不连零）。
   - 数据全为 0 时不画坐标轴，改为空状态文案：「还没有可统计的服务数据 / 平台尚无预约、诉求或报名记录。产生业务数据后，这里会按自然月自动聚合。」
7. **响应式**：窗口宽度 ≤ 900px 时侧栏自动收起为浮层，点击遮罩或导航后收起。

**对应开题功能点**：数据统计看板功能（用户视角）。

## 1.8 驿站服务预约【已实现】

**功能定位（重要）**：预约**不是**「预约使用饮水机、空调」这类设施，而是**有事需要提前和驿站沟通、确认某件事是否可行**。界面提示原文：「驿站服务预约用于有事需要提前和驿站沟通——例如借用场地、团体到访、咨询政策、志愿服务等，驿站管理员看到后会与你联系确认。」因此事项由用户**自行填写**，不从固定服务项目里选。数据库层面 `service_appointment.service_name` 由用户填写，`service_id` 仅为兼容历史数据保留。

**玩法**：

1. 进入「服务预约」→ 选择服务驿站（选后立即显示该驿站营业时间）。
2. 填写「想提前沟通什么」（不超过 100 字）。
3. 选填联系电话。
4. 选择希望联系的日期，再选一个方便联系的时段（时段按下拉驿站营业时间自动生成）。
5. 提交 → 提示「已提交，驿站管理员会联系你确认是否可行」→ 在下方「我的预约记录」中跟踪状态。

**表单字段与校验**：

| 字段 | 控件 | 校验与提示 |
| --- | --- | --- |
| 服务驿站 | 可搜索下拉（当前城市前 50 条） | 必选；缺失提示「请选择驿站和联系日期」 |
| 想提前沟通什么 | 多行文本，限 100 字并显示字数 | 去空格后必填 → 「请填写想提前沟通的事项」；超过 100 字 → 「事项说明请控制在 100 字以内」 |
| 联系电话 | 输入框，限 30 字 | 选填；一旦填写，后端按 `数字/空格/加号/减号/括号` 且长度 5~30 校验，不合法 → 「联系电话格式不正确，请填写数字、空格或 -() 组成的号码」 |
| 希望联系的日期 | 日期选择器（YYYY-MM-DD） | 必选（与驿站合并提示）；【数据边界】前端**未限制不能选过去日期**，后端解析失败时静默取今天 |
| 方便联系的时段 | 单选按钮组 | 必选 → 「请选择方便联系的时段」 |

**时段生成规则**：

- 驿站有可解析营业时间时，按营业区间以 **120 分钟为步长**切分，**最多 4 段**；窗口不足一个步长时直接给出整个窗口。
- 无营业时间、全天营业或文本无法解析时，回落为固定三段：`09:00-11:00 / 14:00-16:00 / 18:00-20:00`。
- 切换驿站后，若原选中时段不在新列表中，自动落到第一段。
- 未选驿站时提示「该驿站暂无可选时段，请先选择驿站。」

**预约时段校验规则（后端为准）**：

- 预约时段必须**完整落在驿站营业时间内**，超出返回 400 与中文提示，例如：
  `所选时段 22:00-23:00 不在该驿站的营业时间内（每日 8:30-22:00）`。
- **营业时间缺失或无法解析时不拦截**（判断不了就不挡），避免因数据缺失误拒正常预约。
- 界面上的营业状态是前端按当前时间**实时推算**的展示逻辑，每分钟刷新一次，与后端校验相互独立。

**预约记录与取消规则**：

- 记录列表展示：沟通事项、驿站、日期 + 时段、状态标签；空态「暂无预约记录」。
- **只有「待驿站确认」状态可以取消**（后端条件更新 `id + 用户本人 + 状态为待确认`），取消前二次确认「确认取消「{事项}」的预约吗？」。
- 取消的失败提示分别为：「预约不存在」「只能取消本人提交的预约」「只有待确认的预约可以取消」。
- 【数据边界】预约**没有重复提交拦截**（同一驿站同一日期可重复提交），前端仅用按钮 loading 防连点。

**对应开题功能点**：服务预约申请功能、我的预约记录功能。

## 1.9 诉求反馈（提交）【已实现】

**功能定位**：新就业群体遇到驿站服务不到位、设施缺失、权益相关问题时的反映入口，是「诉求反馈与响应」闭环的起点。

**玩法**：侧栏「诉求反馈」→ 填写标题、类型、区域、具体内容（可勾选匿名）→ 提交 → 右侧「我的诉求进度」时间轴立刻出现该诉求。

**表单字段与规则**：

| 字段 | 控件 | 规则 |
| --- | --- | --- |
| 诉求标题 | 输入框 | 占位「例如：希望增加夜间热饭服务」；**前端未设长度上限**；标题与内容共同必填 |
| 诉求类型 | 下拉 4 项 | 驿站服务 / 权益保障 / 设施建议 / 其他问题，默认「驿站服务」 |
| 所属区域 | 下拉 | 取自当前城市区域统计；进入页面时若为空自动取第一项，兜底「全部区域」 |
| 具体内容 | 多行文本 5 行 | 占位「请描述遇到的问题、发生地点和希望得到的帮助」 |
| 匿名提交 | 复选框 | 默认不勾选 |

- **必填校验**：标题或内容为空 → 「请先填写诉求标题和具体内容」。
- **提交成功**：提示「诉求已提交，可在"我的诉求"查看处理进度」；保留类型、区域、匿名选项，清空标题与内容，便于连续提交多条。
- **初始状态**：落库时状态固定为「待受理」，并**自动写入一条 `SUBMIT`（已提交）处理记录**，形成闭环的第一环。
- **匿名规则**：匿名只在**管理端列表**生效（展示为「匿名用户」）；用户本人查看自己的诉求不受影响。
- **受理方由类型决定**（界面原文说明）：「诉求受理方由类型决定：驿站服务与设施建议由驿站管理员处理，其余由平台协调。」对应的受理边界文案为「驿站职责范围内的服务与设施事项」/「平台协调或转办建议；不代表行政机关受理」。

**对应开题功能点**：诉求提交功能。

## 1.10 我的诉求与进度查询【已实现】

**玩法**：侧栏「我的诉求」→ 按状态筛选 → 点「查看进度」看四步流程与完整处理时间线。

**筛选与列表规则**：

- 筛选按钮 4 个：**全部 / 待受理 / 处理中 / 已办结**。
- 【数据边界】状态字典里还有「已分派」与「已关闭」两个状态，但**筛选按钮没有对应项**，这两类记录只能在「全部」中看到。
- 表格列：诉求标题、类型、区域、处理人、提交时间、当前状态、操作；空态「暂无诉求记录」。

**进度展示规则**：

- 四步进度条：**已提交 / 已受理 / 处理中 / 已办结**；映射关系为：已办结或已关闭 → 第 4 步；处理中 → 第 3 步；已分派 → 第 2 步；其余 → 第 1 步。
- 时间描述：提交时间取诉求创建时间；受理/处理时间取处理记录中 `ASSIGN` / `HANDLE` 动作的时间，缺失显示「待处理」；办结时间缺失显示「待办结」。
- 处理时间线逐条展示：动作中文名 + 处理说明（无补充说明时显示「无补充说明」）+ 处理人 + 时间。**这是诉求「全程留痕」在用户侧的体现**。

**对应开题功能点**：诉求处理回复功能（用户侧查看）、我的诉求记录。

## 1.11 诉求办结评价【已实现】

**玩法**：在「我的诉求」中，状态为**已办结**的诉求行会多出一个「评价」按钮 → 弹窗给办结评分（星级）+ 填写评价内容 → 提交。

**规则**：

- **前置条件**：只有**本人**提交、且状态为**已办结**的诉求才能评价；否则分别提示「只能评价本人提交的诉求」「诉求办结后才能评价」。
- **分值范围**：1~5 分，超出提示「评价分数必须在 1 到 5 之间」；默认 5 分。
- **评价内容选填**，占位「处理是否及时、结果是否满意」；空内容提交时处理记录记为「用户已评价」。
- **留痕**：评价后写入一条 `EVALUATE` 类型的处理记录，进入时间线。
- 提交成功提示「评价已提交，感谢你的反馈」。
- 【数据边界】诉求评价**没有「不可重复评价」拦截**，与驿站服务评价一致。

**对应开题功能点**：诉求评价功能（诉求闭环的最后一环：提交 → 受理 → 分派 → 处理 → 办结 → 评价）。

- 分类按钮 4 个：**全部 / 政策 / 通知 / 动态**；除「全部」外，选中文案同时作为资讯分类与公告类型两个接口的筛选条件。

- **分页**：资讯与公告两个接口各取 8 条，因此每页最多 16 条，总数显示为两者之和。
- 只能看到**已发布**（`PUBLISHED`）的内容，草稿不对外。
- 详情弹窗：标题 + `类型标签 · 日期` + 正文；正文为空时提示「该条内容暂无正文，请以官方来源为准。」。
- 类型标签颜色：政策=绿、通知=蓝、动态=橙、其他=灰；空态「暂无资讯」。
- 首页「政策资讯」区块同时展示资讯（4 条）与公告（3 条），取前 5 条。

**对应开题功能点**：资讯公告查看功能。

## 1.14 驿站服务评价【已实现】

**玩法**：侧栏「服务评价」→ 选择要评价的驿站 → 给 4 个维度打分 + 填写评价内容 → 提交；右侧展示该驿站的历史评价与平均分。

**评价维度与规则**：

| 维度 | 控件 | 分值 |
| --- | --- | --- |
| 综合评分 | 星级，默认 5 | 1~5 |
| 服务评分 | 星级，默认 5 | 1~5 |
| 环境评分 | 星级，默认 5 | 1~5 |
| 设施评分 | 星级，默认 5 | 1~5 |
| 服务评价内容 | 多行文本 4 行 | 去空格后必填 |

- 未选驿站 → 「请选择要评价的驿站」；内容为空 → 「请填写服务评价」。
- 后端逐项校验：驿站必填（「评价驿站不能为空」）、驿站必须存在（「驿站不存在」）、四个评分必须落在 1~5（提示形如「综合评分必须在 1 到 5 之间」）；未单独填写时服务/环境/设施评分回落到综合评分。
- 提交成功提示「评价已提交，感谢你的反馈」。
- **历史评价区**：标题右侧显示「N 条 · 平均 X 分」；列表显示评价人（无名称时显示「匿名用户」）、时间、只读星级、评价内容（未填时显示「未填写评价内容」）；固定展示第 1 页 10 条，无翻页控件；空态「该驿站还没有评价」。
- **汇总口径**：返回评价条数与综合、服务、环境、设施四个维度的平均分，平均分保留 1 位小数，无数据时为 0.0。
- 【数据边界】**没有「同一用户对同一驿站只能评价一次」的限制**。

**对应开题功能点**：驿站服务评价功能。

## 1.15 消息中心与未读角标【已实现】

**功能定位**：系统**没有独立消息表**，消息由用户自己的预约、诉求、报名记录**实时派生**，因此消息永远与业务数据一致。

**玩法**：点顶栏铃铛或侧栏「消息中心」→ 查看消息列表 → 点击某条即标为已读 → 或点「全部标为已读」。

**派生规则**：

| 消息来源 | 条数 | 标题规则 | 详情规则 |
| --- | ---: | --- | --- |
| 预约 | 前 4 条 | `预约{状态}：{沟通事项}` | `{驿站} · {日期} {时段}` |
| 诉求 | 前 4 条 | `诉求{状态}：{标题}` | `处理人：{处理人}`，无处理人时显示受理边界或「等待受理」 |
| 活动报名 | 前 4 条 | 固定「活动报名已提交」 | 固定「报名成功后可领取活动物资」 |

- 消息上限 **12 条**（3 类 × 4 条）；消息键包含状态（如 `appeal-12-RESOLVED`），状态变化会生成新的未读消息。
- 颜色语义：预约已确认=绿、已拒绝=橙；诉求已办结=绿、其他=蓝；报名=蓝。

**已读与角标规则**：

- 已读状态保存在**本机浏览器**（localStorage 键 `friendly_station_read_messages`）；解析失败按「全部未读」处理；写入失败（隐私模式）时仅内存生效。
- **顶栏未读角标与消息中心列表读同一份数据**（共享 store），保证两处数字永远一致；每次同步时清理已不在列表中的已读键，避免无限增长。
- 未读数为 0 时，按钮禁用且文案变为「已全部读完」；全部标为已读后提示「消息已全部标记为已读」。
- 【数据边界】换设备或清理浏览器缓存后，已读状态会重新变为未读。

**对应开题功能点**：为预约、诉求、活动三个模块提供消息触达（增强项）。

## 1.16 城市定位与城市切换【已实现】

**功能定位**：平台是**面向全国的多城市平台**，驿站名录按城市归属；不同城市对同类驿站叫法不同（杭州「小哥驿站 / 城管驿站」、北京「工会驿站 / 暖新驿站」、上海「户外职工爱心接力站」、深圳「暖蜂驿站」等），系统按来源原文记录名称与类型。

**首次进入的城市判断顺序（玩法规则）**：

1. 本地已保存过城市且该城市仍在城市列表中 → **直接采用，不再请求定位**。
2. 否则请求浏览器定位（高精度关闭、8 秒超时、10 分钟缓存）→ 调后端定位接口做逆地理编码：
   - 定位到的城市在平台覆盖范围内 → 使用该城市；
   - 不在覆盖范围内 → **降级展示最近的已覆盖城市**，并在顶栏显示「未覆盖」标签，悬停提示原文：
     `您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市。`
3. 定位被拒、超时或接口失败 → 回退平台的默认城市，**不阻塞首页渲染**，也不显示误导性的「未覆盖」提示。
4. 城市列表拉取失败 → 提示「城市列表加载失败」。

**切换城市规则**：

- 顶栏城市下拉可手动切换（显示为「城市名（驿站数）」），切换后重新加载首页数据、附近驿站与当前模块数据，并清空已定位的驿站。
- 切换城市会重置：驿站查询回到第 1 页、区域筛选回到「全部区域」、清空已选驿站与时段。
- **哪些按城市过滤**：驿站查询、地图、区域分布统计。
- 【数据边界】**哪些不按城市过滤**：6 张指标卡、数据统计模块与报表导出的统计口径是**全平台汇总**，首页已在提示条中明确标注这一点。

**对应开题功能点**：附近驿站查询功能（多城市扩展）。

# 第 2 章 驿站端（驿站管理员 STATION_ADMIN）

## 2.1 驿站端定位、账号与数据范围【已实现】

**功能定位**：驿站端是**本驿站**的运营台。驿站管理员只做两件事——**把用户提交的预约确认为可行**，**把落到本驿站职责范围内的诉求办结**；此外可以发布本驿站的活动、查看报名情况、导出本驿站台账。

**玩法**：

1. 用 `station_admin_01 / password` 登录（或在登录页点「驿站管理员 · 管理驿站」按钮）。
2. 登录后首页顶栏出现「管理工作台」按钮 → 进入 `/admin`。
3. 管理工作台顶部是 5 张概览卡，下方是**按角色显示的标签页**；驿站管理员能看到 **6 个标签页**：运营概览、预约审核、诉求处理、活动管理、报名记录、报表导出。

**数据范围规则（驿站端最核心的规则）**：

| 业务 | 过滤维度 | 判定依据 | 说明 |
| --- | --- | --- | --- |
| 预约 | 按**驿站** | `station.manager_id = 当前账号 id` | 只看到「我负责的驿站」的预约 |
| 诉求 | 按**驿站所在区域** | 我负责驿站的 `area` 去重集合 | 诉求表没有驿站字段，因此按区域收敛 |
| 其他 | 不限制 | — | 活动、报名、统计概览为全局视角 |

- 后台接口契约：`null = 不限制`，`空集合 = 范围内无可见数据`（返回空页而不是全部数据），这是防止越权看到全站数据的关键设计。
- 平台管理员与超级管理员**不做**范围收敛，看到全部数据；即「同一套界面、不同数据范围」。
- 界面上同步给出说明原文：「标签页按角色显示，后端接口另有权限校验；驿站管理员只看到自己所负责驿站的预约，以及负责驿站所在区域的诉求。」
- 若某账号未被分配到任何驿站（`manager_id` 为空），其驿站范围为空集合，预约列表将返回空页——这是**预期行为**而非故障。

**对应开题功能点**：角色权限管理功能（驿站管理员侧）。

## 2.3 预约审核【已实现】

**玩法**：标签页「预约审核」→ 用关键字或状态筛选 → 对「待驿站确认」的预约点「确认」或「拒绝」→ 需要了解细节时点「详情」。

**查询条件与列表**：

- 关键字（占位「搜索预约人、驿站或服务项目」，回车或清空即查询）；状态下拉 5 项：待驿站确认 / 已确认 / 已拒绝 / 已取消 / 已完成；「查询」「重置」；右侧显示「共 N 条预约」。
- 列：编号、预约人、服务驿站、服务项目（用户填写的沟通事项）、预约日期、预约时段、状态标签、审核说明（悬停查看全文）、提交时间、操作。
- 分页每页 10 条，可切 10 / 20 / 50；后端单页上限 200。

**审核动作与规则**：

| 动作 | 可点条件 | 交互 | 结果 |
| --- | --- | --- | --- |
| 确认 | 仅「待驿站确认」 | 二次确认弹窗 | 状态 → 已确认，审核说明留空 |
| 拒绝 | 仅「待驿站确认」 | 输入框要求填写拒绝原因（去空格后不可为空，否则提示「请填写拒绝原因」） | 状态 → 已拒绝，原因写入审核说明 |
| 详情 | 任意状态 | 只读弹窗，展示 9 个字段 | 不改数据 |

- **状态机规则**：只有「待驿站确认」可以流转到「已确认」或「已拒绝」；已确认、已拒绝、已取消、已完成都是终态，界面上不再提供操作按钮。
- **并发保护**：审核采用**条件更新**（`WHERE id=? AND status='待驿站确认'`），两人同时处理同一单时只有一人成功；失败时区分提示「预约不存在」与「该预约已处理，不能重复审核」。
- 【数据边界】后端**不强制**拒绝原因非空（缺省为空字符串），必填是前端交互约束。
- 【数据边界】「已完成」状态在代码中**没有任何入口可以置入**（属预留状态），因此实际可达的预约状态只有 4 个：待驿站确认 → 已确认 / 已拒绝 / 已取消；管理台也**没有**「完成」和「取消」按钮。
- 【数据边界】驿站端只能处理**本驿站**的预约（见 2.1 数据范围）。

**对应开题功能点**：预约审核与处理功能。

## 2.4 诉求接收与响应（驿站端核心功能）【已实现】

**功能定位**：驿站端是诉求闭环里「**办**」的一环。用户在用户端提交诉求 → 系统按**诉求类型**判定受理方 → 属于驿站职责范围的（「驿站服务」「设施建议」）由**驿站管理员**处理，其余由平台管理员协调；驿站端在自己负责的**区域**内看到这些诉求，并通过「分派 → 处理中 → 办结 / 关闭」把事办完。

**玩法（标准处理流程）**：

1. 进入「诉求处理」标签页 → 用关键字（标题 / 类型 / 区域）或状态筛选，看到落到本区域范围内的诉求。
2. 行内可直接看到：编号、诉求标题、类型、区域、提交人（匿名诉求额外挂「匿名」标签）、**受理边界**、状态、处理人、受理方、提交时间。
3. 点「分派」→ 弹出该诉求的摘要（诉求标题 / 当前状态 / 受理方 / 受理边界）+ 一个「分派说明」输入框，填写处理人与办理要求后提交 → 状态变为「已分派」。
4. 事情开始办时点「处理中」→ 填「处理进展说明」（可留空）→ 状态变为「处理中」。
5. 事情办完点「办结」→ **必须填写处理说明**（前端强制：未填会提示「办结诉求必须填写处理说明」，输入框占位「请填写处理说明，办结后不可修改」）→ 状态变为「已办结」，同时写入办结时间。
6. 若诉求不属于驿站职责或无法办理，点「关闭」→ 填「关闭原因」（可留空）→ 状态变为「已关闭」。
7. 任意状态的行都点得开「记录」按钮，查看完整处理时间线（谁、什么时候、做了什么、说了什么）。

**四种动作的规则对照表**：

| 动作 | 目标状态 | 说明字段 | 必填 | 字数上限 | 成功提示 |
| --- | --- | --- | --- | --- | --- |
| 分派 | 已分派 | 分派说明 | 否（可留空，后端默认记为「已分派处理人」） | 200 字 | 诉求已分派 |
| 处理中 | 处理中 | 处理进展说明 | 否（留空则记录为状态名「处理中」） | 300 字 | 诉求状态已更新为标记处理中 |
| 办结 | 已办结 | 处理说明 | **是** | 300 字 | 诉求状态已更新为办结诉求 |
| 关闭 | 已关闭 | 关闭原因 | 否（留空则记录为状态名「已关闭」） | 300 字 | 诉求状态已更新为关闭诉求 |

**状态机与边界规则**：

- 可继续处理的状态：**待受理 / 已分派 / 处理中**；「已办结」「已关闭」为终态，四个动作按钮全部禁用，只能看记录。
- 越界操作的提示语：「该诉求已办结或关闭，不能再次分派」「该诉求已办结或关闭，不能重复处理」。
- 处理状态白名单：处理接口只接受「处理中 / 已办结 / 已关闭」三个值，否则提示「诉求处理状态只能是 PROCESSING、RESOLVED 或 CLOSED」。
- **分派规则（重要）**：分派接口**没有指定处理人的参数**，`handler_id` 固定记为**当前操作人**。因此「要派给谁」是通过**分派说明文字**表达的（界面占位原文：「填写处理人、办理要求等（可留空，后端默认记录为已分派处理人）」）。这是当前实现的真实边界，答辩时不应表述为「支持指派给指定人员」。
- **受理方与受理边界由诉求类型决定**：

  | 诉求类型 | 受理方 | 受理边界文案 |
  | --- | --- | --- |
  | 驿站服务 | 所属驿站管理员 | 驿站职责范围内的服务与设施事项 |
  | 设施建议 | 所属驿站管理员 | 驿站职责范围内的服务与设施事项 |
  | 权益保障 | 平台管理员 | 平台协调或转办建议；不代表行政机关受理 |
  | 其他问题 | 平台管理员 | 平台协调或转办建议；不代表行政机关受理 |

  【数据边界】诉求类型在后端是**自由文本**（默认「其他问题」），只有「驿站服务」和「设施建议」被识别为驿站侧受理；用户端提供 4 个选项，接口文档记载的选项也是 4 项，二者一致。
- **匿名规则**：匿名诉求在管理端列表把提交人显示为「匿名用户」，**但诉求内容与区域照常可见**——因为区域是分派依据。
- **范围规则**：驿站管理员看到的是**本驿站所在区域**的诉求（不是本驿站专属），因此同一区域内多个驿站的诉求会同时出现；这是「按区域收敛」的必然结果。
- **落库与留痕**：提交、分派、处理、办结、关闭、评价每个动作都会写入一条处理记录，形成不可编辑的时间线。

**对应开题功能点**：诉求分派与处理功能、诉求处理回复功能。

## 2.10 延伸玩法设计：驿站爱心物资补给与「用完自觉回补」【设计延伸·待实现】

> **重要说明**：本节描述的是**业务玩法设计**，用于说明驿站端「接收诉求反馈」能力的自然延伸。
> 程序当前**没有**物资台账表、没有领取/回补接口、没有库存字段；数据库里与服务物资相关的仅是驿站服务项目中的名称文本（如「爱心雨具」「共享雨衣」「雨具借用」「补给区」等，
> 服务项目全库 6413 条中，名称含「雨」的记录约 69 条，另有一批「补给区」记录）。
> 因此本节内容**只能在答辩中作为设计延伸与改进方向陈述，不能声称已实现**。

### 2.10.1 场景来源

驿站常设「免费领取雨衣 / 共享雨具」这类便民物资。现实中会出现一个正向循环：

> 某驿站在服务项目里配置了「免费领取雨衣」→ 一名骑手在暴雨天取用了一件 → 事后这位骑手为了感谢驿站，自行购买了一批雨衣放到驿站，供后来的人继续取用。

这个循环把「**驿站提供服务 → 用户使用服务 → 用户反哺服务**」串了起来，是「新就业群体友好驿站」最有说服力的玩法之一。它天然落在驿站端的「接收诉求反馈」能力上：骑手的谢意与补货行为，本质上是一条**正向反馈**，需要被驿站接收、确认、致谢并公示。

### 2.10.2 玩法设计（面向驿站端）

| 环节 | 谁来做 | 玩法 |
| --- | --- | --- |
| 1. 物资上架 | 驿站管理员 | 在驿站服务项目里把「爱心雨具」标记为**可领取物资**（区别于「加水 / 充电」这类设施服务），设定初始数量与每人限领件数 |
| 2. 用户取用 | 用户端 | 在驿站详情页看到「可领取：爱心雨衣（余 N 件）」，点「我要领取」生成一条领取记录（不涉及支付） |
| 3. 库存提醒 | 驿站端 | 物资余量低于阈值或清零时，在驿站端出现「待补充」提醒，可一键转成一条**驿站内部诉求**（类型「驿站服务」、区域为本驿站所在区域） |
| 4. 骑手回补 | 用户端 | 用户可在该驿站发起「我要补充物资」，填写补充物资名称与数量（例如「雨衣 × 20」），提交后形成一条**正向反馈诉求** |
| 5. 驿站接收与致谢 | 驿站端 | 驿站管理员在「诉求处理」中收到该反馈，走既有闭环：分派 → 处理中 → 办结；办结说明里写明「已收到雨衣 20 件，已上架」 |
| 6. 公示与激励 | 驿站端 / 管理员端 | 驿站端可在驿站详情页展示「感谢 @爱心骑手 补充雨衣 20 件」；平台管理员可在概览中统计「物资补充次数」「爱心榜」 |

### 2.10.3 规则设计（建议值，落地时需重新评审）

- **领取规则**：同一账号对同一物资每日限领 1 件（可配置）；领取不消耗积分、不收费；领取记录不可删除，只可作废。
- **库存规则**：库存 = 上架数量 + 用户补充数量 − 已领取数量；不允许为负；余量为 0 时前台显示「暂已领完」而不是隐藏入口（隐藏会让后来的人以为驿站没有这项服务）。
- **回补规则**：补充物资由用户自愿发起，数量为正整数，需填写物资名称；驿站管理员**办结即视为确认收到**，未办结不增加库存。
- **反馈闭环规则**：物资类诉求沿用既有 5 状态与 6 动作（提交 / 分派 / 处理中 / 办结 / 关闭 / 评价），不新增状态；**结存数量变化必须留痕**（谁在什么时候补了多少、领了多少）。
- **匿名规则**：领取可匿名；**补充行为不建议匿名**（致谢与公示需要署名，且平台需要防止虚假申报），或提供「匿名补充 + 驿站仅公示数量」的折中方案。
- **边界规则**：平台只做「登记与公示」，不对物资质量与安全作承诺；建议在驿站详情页标注「物资由社会力量自愿提供，请按需取用」。
- **数据边界**：物资数量属于**运行时记录**，与驿站名录一样不代表真实库存；演示数据须明确标注。

### 2.10.4 落地所需改动（供后续开发参考）

| 层面 | 需要的改动 |
| --- | --- |
| 数据库 | 新增物资表（驿站、物资名称、上架数量、已领取、剩余、状态）与领取/补充记录表；或在 `station_service` 上扩展数量与限领字段 |
| 后端 | 物资查询与领取接口（需并发安全，参照活动报名的行锁 + 唯一索引做法）、补充申报接口、余量阈值提醒 |
| 前端 | 用户端驿站详情的「可领取物资」区与领取/补充入口；驿站端的「物资台账」区块与待补充提醒 |
| 统计 | 概览增加「物资领取次数 / 补充次数 / 参与人数」三项指标 |

### 2.10.5 与既有功能的衔接点（说明为什么这是自然延伸）

- **入口现成**：驿站服务项目里已有「爱心雨具 / 共享雨衣 / 补给区」等名称，扩展的是**数量与流水**，不是新概念。
- **闭环现成**：诉求的 5 状态 6 动作与处理记录留痕机制可以直接承接「回补反馈」，无需新增状态机。
- **范围现成**：诉求本来就按驿站所在区域收敛，物资反馈天然落在正确的驿站手上。
- **统计现成**：概览与报表导出框架可直接增加物资指标。

**对应开题功能点**：诉求反馈与响应模块的延伸（正向反馈子场景）；**不属于**开题已列出的 21 项功能。

**权限机制规则**：

- 注解可标在**方法**或**控制器类**上；同时存在时**方法级覆盖类级**。
- 校验顺序：先看有没有 `@RequireRole`——**没有注解的接口完全公开**（不需要 token）；有注解但无 token → 401「请先登录」；token 有效但角色不在白名单 → 403「当前角色无权执行此操作」；token 解析失败或过期 → 401「登录凭证已失效，请重新登录」。
- **前端隐藏标签页只是体验优化**，真正的门禁在后端；页面底部明确写着「前端按角色隐藏标签页只是体验优化，后端每个接口都带有 `@RequireRole` 校验，越权请求会被拒绝」。
- **会话规则**：登录发放 JWT，默认有效期 **120 分钟**；JWT 为无状态凭证，因此**修改角色或停用账号不会让已签发的 token 立即失效**（只影响下次登录）。
- 【数据边界】超级管理员与平台管理员**共用同一套界面与按钮**，代码里没有按「超级管理员」进一步区分按钮可用性；差异只体现在角色说明文案与账号/角色管理的授权范围上。

**对应开题功能点**：角色权限管理功能。

**数据范围文案（界面原文）**：

| 角色 | 数据范围 |
| --- | --- |
| 普通用户 | 仅本人数据：本人预约、本人诉求、本人报名与本人评价，不能进入管理工作台。 |
| 驿站管理员 | 本驿站范围：所属驿站的服务项目、预约审核、诉求处理、活动管理与报表导出。 |
| 平台管理员 | 平台全域：全部驿站、服务项目、预约、诉求、资讯公告、活动、账号与角色权限。 |
| 超级管理员 | 全系统最高权限：在平台管理员范围之上，可调整任意账号的角色与启用状态。 |

- 【数据边界】该页**纯只读**，没有编辑角色或权限的按钮；角色分配在「账号管理」页完成。
- 【数据边界】页面上「可见标签页」一栏是**前端硬编码的说明文案**，与管理工作台实际的 11 个标签页存在两处不一致（驿站管理员名下列了 5 项、缺「报名记录」；平台管理员名下列了 10 项、缺「报名记录」）。答辩时应以**实际标签页**为准。

**对应开题功能点**：角色权限管理功能。

## 3.12 报表导出与数据口径【已实现】

**玩法与规则**：与驿站端一致（5 类 CSV、单次上限 5000 行、UTF-8 带 BOM、需管理角色）。

**管理员端特有视角**：

- 可导出的数据在平台管理员处是**全平台全量**，与驿站端导出的内容相同（导出接口不做范围收敛）。
- 页面「数据口径说明」区展示 `dataScope`（数据口径）、`dataStatus`（数据状态）、`generatedAt`（生成时间）与 13 项指标口径表，是答辩时说明「统计怎么算」的直接依据。

**对应开题功能点**：诉求与服务数据分析功能（数据输出侧）。

# 第 4 章 三端协同的典型玩法场景

本章把三端功能串成可直接用于**答辩演示**的剧本。每个场景都标明「已实现」或「设计延伸」，避免把设计当实现讲。

## 4.1 场景一：雨衣补给 —— 从「驿站提供服务」到「骑手反哺驿站」

> **实现状态**：本场景的**主流程（提交 / 分派 / 办结 / 评价 / 统计）全部已实现**；
> 「物资领取与补给台账」部分为**设计延伸·待实现**（见 2.10），演示时须明确区分。

### 4.1.1 剧情

1. **驿站配置服务**：某驿站在服务项目里配置了「爱心雨具（免费领取）」。全库服务项目中，名称含「雨」的条目约 69 条（如「爱心雨具」「共享雨衣」「雨具借用」「雨衣雨伞」），并有一批「补给区」条目，说明这是驿站真实存在的服务形态。
2. **骑手取用**：暴雨天，骑手 `rider_xiaowang` 在用户端「驿站查询」搜到该驿站 → 打开详情 → 看到服务设施里有「爱心雨具」→ 取用了一件雨衣。
3. **骑手反馈**：骑手在用户端「诉求反馈」提交一条诉求，**类型选「驿站服务」、区域选该驿站所在区域**，标题如「感谢 XX 驿站免费雨衣，想补充一批」，内容写明「想自行购买 20 件雨衣放在驿站，供其他骑手使用」，可勾选匿名（**建议不匿名**，因为需要驿站回访确认）。
4. **系统判定受理方**：因为类型是「驿站服务」，系统把受理方判定为**所属驿站管理员**，受理边界文案「驿站职责范围内的服务与设施事项」，并给出状态「待受理」+ 一条「提交诉求」记录。
5. **驿站端接收**：驿站管理员登录 → 管理工作台 →「诉求处理」→ 在**本区域范围**内看到这条诉求（提交人显示为账号名；若匿名则显示「匿名用户」，但内容与区域照常可见）→ 点「分派」，在分派说明里写「请联系王师傅确认送货时间，收到后清点上架」→ 状态变为「已分派」。
6. **驿站端办结**：骑手把雨衣送到驿站后，驿站管理员点「办结」，**必须填写处理说明**（例如「已收到爱心骑手补赠雨衣 20 件，已上架补给区，感谢！」）→ 状态变为「已办结」，写入办结时间。
7. **骑手评价**：骑手在用户端「我的诉求」看到状态是「已办结」→ 出现「评价」按钮 → 给 5 星并留言「驿站很贴心」→ 评价写入，同时生成一条「用户评价」记录。
8. **数据沉淀**：平台管理员在「运营概览」看到诉求总数、已办结诉求、办结率随之变化；在「报表导出」导出 `appeals.csv`，这条记录的处理说明就是一份可公示的爱心留痕。

### 4.1.2 这个场景体现了哪些设计要点

| 设计要点 | 在系统中的体现 |
| --- | --- |
| 三端各司其职 | 用户端提交 → 驿站端办结 → 管理员端统计，一条数据贯穿三端 |
| 受理方自动判定 | 诉求类型决定受理方与受理边界，不需要人工分派到驿站 |
| 数据范围收敛 | 驿站管理员只看到本区域的诉求，不会看到全市诉求 |
| 全程留痕 | 提交 / 分派 / 办结 / 评价四个动作各写一条处理记录，时间线可回溯 |
| 闭环可评 | 只有「已办结」状态才出现评价入口，评价进入同一时间线 |
| 统计可复用 | 既有概览与报表框架可直接承接「物资补给」这类新玩法 |

### 4.1.3 演示话术（建议）

> 「驿站端最有价值的不是审核按钮，而是**接收诉求的能力**。比如这个驿站的免费雨衣被骑手用掉了，骑手自己买了一批送回来——这件事在我们系统里是一条走完整闭环的诉求：提交、分派、办结、评价、进统计。三端各做一件事，但数据是同一份。」

### 4.1.4 若要把它做成产品功能，还差什么

见 2.10.4 的改动清单：物资表 + 领取 / 补充接口 + 余量提醒 + 前台物资区 + 概览指标。这部分**尚未实现**，答辩时作为改进方向陈述。

## 4.2 场景二：骑手借用驿站场地开安全培训（预约玩法）【已实现】

1. 骑手在首页「附近驿站」列表找到目标驿站 → 点**「提前联系」** → 系统直接跳到「服务预约」并自动选中该驿站，弹出预约表单（这是最短路径）。
2. 表单填写：
   - 「想提前沟通什么」：`我们 10 人想借用驿站场地开一次安全培训，能否安排？`（100 字内）
   - 联系电话：选填，填了则必须符合号码格式。
   - 希望联系的日期 + 时段：时段由该驿站营业时间按 120 分钟切分生成，最多 4 段。
3. 提交 → 提示「已提交，驿站管理员会联系你确认是否可行」。
4. **若所选时段不在营业时间内**（例如驿站 `10:00-22:00`，用户选了 `22:00-23:00`）→ 后端返回 400，提示原文：
   `所选时段 22:00-23:00 不在该驿站的营业时间内（10:00-22:00）`。
   **若驿站没有营业时间或文本无法解析 → 不拦截**（判断不了就不挡）。
5. 驿站端在「预约审核」看到这条预约 → 点「确认」→ 状态「已确认」，提示用户可行；若当天场地已有安排 → 点「拒绝」→ 必须填写拒绝原因（如「当日场地用于体检活动，建议改为 15 日」）→ 状态「已拒绝」，原因展示在审核说明里。
6. 骑手在「服务预约」下方看到状态变化；**在驿站确认前**可以点「取消」撤回（二次确认后状态变「已取消」）；确认之后就不能再取消。
7. 三端消息：用户端消息中心出现「预约已确认 / 已拒绝」，点开即标为已读，顶栏角标同步减少。

## 4.3 场景三：匿名诉求反映设施缺失（匿名 + 区域分派）【已实现】

1. 快递员在用户端提交诉求：类型选**「设施建议」**，内容「XX 驿站充电插排不足，建议增加」，**勾选匿名提交**。
2. 系统判定：设施建议 → 受理方为**所属驿站管理员**，受理边界「驿站职责范围内的服务与设施事项」。
3. 驿站端列表里，这条诉求的**提交人显示为「匿名用户」**，但诉求标题、类型、区域、内容如实展示——因为驿站需要靠区域与内容判断该去哪个驿站核实。
4. 驿站管理员分派 → 处理中 → 办结（处理说明「已增加 2 个插排并测试可用」）。
5. 用户在「我的诉求」中看到自己的诉求（**本人查看不脱敏**）与完整处理时间线，并对办结结果评分。
6. 【数据边界】匿名只作用于**管理端列表的展示**，不是加密匿名；答辩时不宜表述为「提交人完全不可追溯」。

## 4.4 场景四：免费体检活动名额抢报（并发名额玩法）【已实现】

1. 平台管理员在「活动管理」新增活动：名称「免费体检」、举办驿站、活动时间、名额上限 30、状态已发布。
2. 骑手在用户端「活动报名」看到卡片，显示「报名中」与 `已报名 0 / 30` → 点「立即报名」→ 提示「已提交「免费体检」的报名申请」，按钮变为「已报名」并置灰。
3. 其他骑手同时抢报：
   - 报名时后端对活动行加锁（`SELECT ... FOR UPDATE`）后才校验名额，**不会超卖**；
   - 同一账号重复报名 → 提示「该活动已报名」（数据库唯一索引兜底，并发下也不会重复）；
   - 名额已满 → 提示「活动名额已满」，列表卡片改显示「已满」。
4. 平台或驿站在「报名记录」看到报名人、联系电话与报名时间，据此通知到场。
5. 【数据边界】当前**没有签到功能**，也没有报名审核环节；报名状态由系统写入为「已提交报名」。
6. 【数据边界】内存演示模式下**不校验名额**（只有重复报名拦截），因此并发名额演示需在数据库模式下进行。

## 4.5 场景五：跨城市骑手的驿站发现（定位与城市切换）【已实现】

1. 骑手首次打开系统，浏览器提示定位 → 允许 → 系统调用定位接口做逆地理编码。
2. 若用户在已覆盖城市（如杭州）→ 顶栏城市显示「杭州（267）」，首页地图与附近驿站按杭州过滤。
3. 若用户在**未覆盖城市**（如苏州）→ 顶栏出现橙色「未覆盖」标签，悬停提示原文：
   `您所在的城市（苏州市）暂未覆盖，已为您展示最近的上海市。`
   同时降级展示最近的已覆盖城市，功能可正常浏览。
4. 若用户拒绝定位或接口失败 → 静默回退平台默认城市，不显示误导性的「未覆盖」提示。
5. 用户手动切换城市 → 驿站查询回到第 1 页、区域筛选重置、已选驿站清空，列表与地图按新城市刷新。
6. 【数据边界】切换城市**不会**改变 6 张指标卡与「数据统计」的口径——它们始终是全平台汇总，首页提示条已明确标注。

## 4.6 场景六：月度服务质效复盘（统计与导出）【已实现】

1. 平台管理员进入「运营概览」，读 8 张统计卡：驿站总数、预约总数（近 30 天 / 待审核）、诉求总数、办结率、处理记录数、活动总数、活动报名、评价平均分。
2. 读「服务项目预约排行」Top 10，看哪类服务最被需要；读「月度趋势」看近 6 个月预约量、诉求量与办结率的走向。
3. 进入「报表导出」→ 导出 5 类台账 CSV（诉求 / 预约 / 驿站 / 报名 / 评价），在 Excel 中做二次分析。
4. 【数据边界】办结率的分母是诉求总数、分子只算「已办结」（不含「已关闭」），因此大量关闭的诉求会拉低办结率——汇报时要解释口径。
5. 【数据边界】导出上限 5000 行，且**不受数据范围限制**（驿站管理员导出也是全量），不宜表述为「按驿站权限导出」。

## 5.2 关键校验规则速查

| 主题 | 规则要点 |
| --- | --- |
| 预约时段 | 必须完整落在驿站营业时间内；全天营业放行；营业时间缺失或无法解析**不拦截**；跨区间（如 09:00-12:00 与 14:00-18:00 之间选 13:00-14:00）不通过 |
| 预约事项 | 必填，≤100 字 |
| 联系电话 | 选填；填写则需匹配数字 / 空格 / `+` / `-` / `()` 且长度 5~30 |
| 预约取消 | 仅本人 + 仅「待驿站确认」可取消 |
| 预约审核 | 仅「待驿站确认」可审核；只接受确认 / 拒绝；条件更新防重复审核 |
| 诉求办结 | 只有「已办结」可被评价；评价 1~5 星；必须本人 |
| 诉求终态 | 已办结 / 已关闭不可再分派或处理 |
| 分派 | 无指定处理人参数，处理人记当前操作人；说明可留空（默认「已分派处理人」） |
| 活动报名 | 名额上限校验 + 重复报名拦截 + 行锁并发安全；内存模式不校验名额 |
| 驿站新增 | 名称 / 区域 / 地址必填；强制标记为「后台录入」，不写坐标 |
| 驿站状态 | 只接受 OPEN / CLOSED；删除走逻辑删除，不能通过状态接口置 DELETED |
| 服务项目状态 | 只接受 1 / 0；删除为物理删除 |
| 账号角色 | 至少保留一个角色；主角色取列表第一个；内存模式只生效第一个 |
| 账号状态 | 接受 正常 / 1 / ENABLED 与 停用 / 0 / DISABLED；停用后无法登录，但已签发 token 在有效期内仍可用 |
| 鉴权 | 无 `@RequireRole` 的接口公开；有注解无 token → 401；角色不符 → 403；token 过期 → 401 |
| 数据范围 | 仅驿站管理员被收敛：预约按 `manager_id` 关联的驿站，诉求按这些驿站的区域 |
| 分页 | 驿站 1~50、预约与诉求后台 1~200、活动与资讯公告 1~100、评价 1~50；用户端每页 12（驿站、活动）、8×2（资讯公告）、10（评价） |
| 统计口径 | 近 30 天按创建时间；办结率 = 已办结 ÷ 诉求总数（分子不含已关闭）；趋势为近 6 个自然月；排行为 Top 10 相对占比 |
| 导出 | 5 类 CSV，上限 5000 行，UTF-8 带 BOM，不受数据范围限制 |
